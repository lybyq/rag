# 13｜Agentic RAG：规划、工具、状态与生产验收（Q97–Q108）

[返回目录](README.md) · [项目 Auto 计划](../../requirements/agentic-rag-auto-implementation-plan.md)。本章是尚未实现部分的详细设计训练；当前固定 LangGraph 工作流不能被包装成完整 Agentic 成果。

## Q97｜基础：Agentic RAG 和“检索失败再查一次”有何本质区别？

**回答：** 固定补检索按预设规则执行，Agentic 则根据已得到的证据选择下一步：缺定义就查定义，缺适用条件就读取章节，需要实时事实就调用已授权工具，条件缺失就问用户。区别不在于是否循环，而在于下一步动作是否依据 observation 动态决定，以及是否有可验证的目标和停止条件。

受控实现不让模型直接操作基础设施。模型返回结构化 action、目标事项和参数；代码检查 Schema、权限和预算后执行，观察结果再更新状态。最终仍回统一答案门禁。Anthropic 的公开经验也强调先采用满足任务的简单方案，工作流与 Agent 的复杂度应由需求驱动。[官方文章](https://www.anthropic.com/engineering/building-effective-agents)

**场景追问：为什么不直接让 LLM 自己决定循环次数？回答：** 它不能可靠承担资源和安全约束。总轮数、时间、Token、工具次数及取消必须由程序限制；模型即便说“再查一次一定能成功”也无权延长用户已约定预算。

**验收：** 设置两道不同缺口的题，验证选择了不同且合理的工具，而不是所有问题都固定“搜索—搜索—生成”。

## Q98｜进阶：Auto 怎么判断简单问题与复杂问题？路由错了怎么办？

**回答：** 先用低成本规则和现有路由筛出明显多事项/比较/依赖任务；普通问题先跑受限首轮检索，证据完整就走快路径，有明确缺口再升级。问题字数不是复杂度标准，短句“它呢”可能需要澄清，长句也可能只问一个明确事实。

Auto 需要两种纠错：误判复杂时及早结束，不用满决策预算；误判简单时根据证据覆盖升级，并复用首轮结果，不重查同样内容。模型路由可以用于疑难类别，但不能要求每个问题都多一次模型分类，违背简单题无额外决策调用的目标。

**场景追问：规则越来越多会不会不可维护？回答：** 维护可解释的路由特征和失败样本，避免为每道题加特判。复杂度评分只是调度信号，不是答案置信度。使用冻结评测集测漏升级和误升级，必要时用小分类器/模型替换局部判断，不改变工具安全边界。

**验收：** 分别统计简单题升级率、复杂题漏升级率、完整回答率和延迟差；记录决策原因码，不用模型长篇自述当路由证据。

## Q99｜资深：动态规划怎样表达依赖？能不能所有子问题同时查？

**回答：** 用待回答事项和依赖关系表达，不让模型输出任意可执行代码。例如“按我的职级看住宿额度”：先确定用户授权的职级和地区，再查对应规则；“住宿额度与审批流程”若条件已知，可并行检索。计划包含 taskId、目标、dependsOn、状态、所需条件和证据引用，代码验证无环及数量上限。

先计划再执行适合依赖明确的任务，但遇到新证据仍需有界修订；交替观察再行动适合探索，但容易反复。可以采用短计划+逐步观察的混合方式，不一次生成十几个假定动作。计划更新保留历史版本及原因，不把旧错误计划直接覆盖掉。

**场景追问：第一步查不到职级，模型能猜普通员工吗？回答：** 不能。缺失关键条件标 NEEDS_USER_INPUT，询问用户或调用允许的身份资料接口。不能把模型猜测填入工具参数，因为后续检索再准确也基于错误前提。

**验收：** 测依赖顺序、独立任务有界并行、计划循环、虚构 taskId 和条件覆盖；多事项总计不超过当前计划约定的上限。

## Q100｜资深：工具接口怎么设计，哪些东西绝不能交给模型？

**回答：** 工具表达业务能力，如 search_knowledge、search_document、expand_context，而不是 run_sql、execute_shell、任意 URL fetch。参数用严格 Schema 限定长度、枚举、范围；用户身份、有效空间和权限 Filter 从服务器上下文注入，不接受模型自行传一个更有权的 userId。

返回 observation 要有状态、证据 ID、版本、时间和错误分类；无结果、无权限、超时、格式错误不同，不能都返回空数组让模型误以为没有资料。大结果分页或压缩，正文仍视为不可信数据。工具说明解释什么时候用、何时不适用，避免多个含义重叠工具导致乱选。

**场景追问：MCP 接上工具就安全吗？回答：** MCP/工具协议解决连接方式，不自动提供企业授权。需要验证服务身份、允许工具列表、参数、返回大小和数据分类；第三方工具描述/返回也可能带提示注入。当前项目不要求引入 MCP 才能做 Agent。

**验收：** 每个工具测试成功、无数据、拒绝、超时、取消、429/5xx、版本不匹配及部分失败；拒绝时不泄漏隐藏对象名称或数量。

## Q101｜资深：Agent 怎样知道证据够了，不再查？

**回答：** 为每个待回答事项维护覆盖状态和支持证据，区分 SUPPORTED、MISSING、CONFLICT、NEEDS_USER_INPUT。判断不能只看“找到了十条”或模型自评90分，要核对地区、时间、主体等关键条件是否有证据，引用是否有效。新动作应针对缺口，结果更新覆盖表。

停止原因分成功完成、需要用户、冲突无法消解、预算耗尽、无增益、取消与故障。无增益既包括同一查询指纹，也包括候选虽然多了却没有新增有效证据。一次失败可允许不同合理路线，但不能无限改一个词继续查。

**场景追问：模型说证据完整，但漏了例外呢？回答：** 覆盖判断也会错，需保留父章节/适用条件检查和最终独立校验。用含例外、否定、版本冲突的金标检查过早停止；没有足够证据时输出部分答案或澄清，而不是强行完成整个任务。

**验收：** 测过早停止、重复行动、关键条件缺失和无答案题，报告“完成任务”与“用完预算”两种不同终态比例。

## Q102｜资深：最多三次决策调用，怎样控制真实总成本？

**回答：** 三次只是决策模型调用上限，不等于全部远程调用上限。一个搜索动作可能展开多个子问题×空间×Dense/BM25，还会有 Provider HTTP 重试、精排和最终生成。使用共享预算账本，分别记录决策调用、工具动作、实际检索请求、Token/响应大小和 Deadline；所有子图消费同一预算。

动作发起前预留额度，恢复/重试不重置；服务不返回 usage 时标未知，输入估算只能是保守保护。给生成和校验预留时间，达到预留线就停止补查。并发不改变总额度，独立动作并行时必须原子扣减，避免各自看到“剩余一次”却都发出。

**场景追问：模型格式错再重试，算次数吗？回答：** 算决策调用预算。429 等传输重试另有有限额度，也受总时间限制。预算不足时不能以“格式修复不算业务调用”为由无限重试；应按已获得证据安全退回部分回答或旧规则。

**验收：** 模拟子图嵌套、并发竞争、429、格式错误和恢复，检查调用上界。当前计划沿用已有总超时，不承诺 Agent 每个问题更快。

## Q103｜压轴：有 LangGraph checkpoint，还会重复调用或重复执行吗？

**回答：** 会。检查点保存的是某个时刻的执行状态，不与远端 API 副作用自动组成原子事务。调用已经成功但结果尚未持久化时进程崩溃，恢复可能重放。LangGraph 持久化能力可帮助保存图状态，但业务仍需定义幂等、事务和执行身份。[官方持久化文档](https://docs.langchain.com/oss/javascript/langgraph/persistence)

读工具可允许受限重放，但预算不能归零；写工具必须有远端支持的幂等键或对账查询。Checkpoint 至少关联 runId、策略版本、计划、证据身份、已用预算和动作执行记录；敏感正文不要直接放入公开日志。新的执行器取得租约后，旧执行器的迟到结果不能覆盖状态。

**场景追问：恢复后模型作出了不同决定，怎么复盘？回答：** 已完成动作及 observation 应持久化并复用，未完成决策可以重新运行但记录新的 attempt。复盘解释“当时看到什么、选了什么、实际做了什么”，不能保证随机模型字节级复现。工具结果时间和版本变化要可见。

**验收：** 在调用前、远端成功后、本地落库前、终态发布前分别模拟崩溃；确认不重复发布、不绕过预算、不接受旧租约写入。

## Q104｜资深：Agent 会调用工具，提示注入风险比普通 RAG 大在哪里？

**回答：** 普通 RAG 主要风险是错误/泄露答案，具备工具后还可能泄露数据到外部、读取额外资源或发起业务操作。文档和工具返回必须作为不可信 observation，不能把“请调用某工具导出全部资料”变成控制指令。模型上下文里不放长期密钥，身份在服务器安全边界管理。

对只读工具也要防 SSRF、越权 ID、超大响应和跨组织数据拼接。计划白名单约束“能做什么”，每次执行授权约束“本次能对哪个对象做”。公开搜索结果和企业机密不能无授权地混合后再次发到公网模型。

**场景追问：用户明确要求提交审批，能加入同一个 Agent 吗？回答：** 那是新的写操作范围。需要明确用户确认、操作预览、当前权限复核、幂等与撤销/补偿设计；不能沿用只读 RAG 的授权默认为允许。付款或删除等高影响动作需要额外业务审批，不由模型自行决定。

**验收：** 测恶意文档、伪造 API 返回、跨用户资源 ID、重定向和工具描述污染，验证即便决策模型被诱导也不能执行越权动作。

## Q105｜资深：短期对话状态、任务状态和长期记忆该怎样区分？

**回答：** 对话状态是当前话题、用户明确条件和最近指代；任务状态是计划、工具结果、预算和未完成事项；长期记忆是跨会话保留的稳定偏好或业务信息，需要独立授权、有效期和删除机制。三者混在一大段聊天摘要里容易把旧猜测永久变成事实。

压缩上下文时优先保留用户原始约束、待解决事项、来源 ID、重要观察和失败动作；可舍弃重复描述，但不能删掉否定条件。模型答案和假设要带来源类别，不作为用户确认。角色/空间切换后旧证据需再鉴权，不能从“记忆”绕过当前检索授权。

**场景追问：用户上次说是 P6，今天能直接继承吗？回答：** 职级可能变化，且它是业务事实，不是稳定偏好。重要决策应使用授权身份系统或当前确认；记忆可提示待确认，不能当永久真值。用户删除会话后衍生摘要是否仍保留要有清晰政策。

**验收：** 测跨话题、跨空间、事实更新、摘要丢否定、撤权与删除。长期记忆不是当前项目已具备的默认能力。

## Q106｜资深：单 Agent、多个 Agent、固定 Workflow 怎么选？

**回答：** 固定路径、强约束且可预期的任务优先 Workflow；少量动态资料查找用单个受控 Agent；真正可独立并行、工具权限或专业评估明显不同的任务才考虑多 Agent。多个角色 Prompt 不等于多个独立专家，也不保证结果更正确。

多 Agent 需要额外解决任务切分、共享证据身份、冲突合并、全局预算、取消、权限上下文和恢复。监督者不能只按多数投票，因为多个 Agent 可能共享同一错误来源或模型偏差。若目标只是降低并行检索耗时，普通有界并发通常更简单。

**场景追问：法务、财务、HR 各一个 Agent，能直接给一致结论吗？回答：** 它们可能适用范围不同，需输出来源与条件并保留冲突，由明确的业务裁决规则/人员处理。不能把三个不完整意见拼成一个无条件结论。独立检查有价值，但要证明确实增加了不同证据而非重复花费。

**验收：** 和单 Agent 同预算对比增益、重复行动、合并错误、延迟和成本。当前中型内网项目先做单个受控 Auto，没有证据就不增加部署复杂度。

## Q107｜资深：Agentic 如何评测？只看最终答对不够吗？

**回答：** 最终正确仍是首要指标，但同一答案可能靠越权工具、碰巧猜中或十倍成本获得。增加路由正确、事项完成、动作适当、参数合法、证据新增率、停止合理、预算遵守和恢复安全等过程指标。并非只有一条工具序列正确，评测应允许多条合法有效路径，不死背标准调用脚本。

数据集需要包含不应使用工具的简单题、需要澄清的题、可并行/必须串行的题、无答案、工具故障、注入、撤权和知识更新。质量与成本一起比较原 RAG、Auto 以及消融路径；用同模型/同知识版本并说明预算差异，避免不公平比较。

**场景追问：模型换版后最终正确率没降，可以上线吗？回答：** 还要检查工具调用频次、循环、拒绝率和权限失败处理是否变化。最终正确率可能暂时掩盖预算翻倍或错误外部访问。使用固定难例与故障测试，再小范围验证；真实业务效果没测完不能只凭单元测试放行。

**验收：** 给出按问题类型的质量、P50/P95、工具/决策次数、错误终态和安全违规报告。目标是有约束地完成任务，不是“思考过程越长越像 Agent”。

## Q108｜综合压轴：传统 RAG、Wiki、Agent、业务 API 如何一起回答一个真实问题？

**问题场景：** 员工问：“我下周去上海参加展会，按现在政策住宿能报多少？这次申请还需要补什么？”

**回答：** 先验证身份与选定业务范围，拆为住宿政策和当前申请两部分。日期“下周”按用户时区变为明确范围；住宿标准依赖职级、城市及展会例外，缺职级需授权资料或澄清；“这次申请”若对应多个申请，先确认，不能猜。

Wiki 如果已建设，只提供“出差办理指南”的流程地图；原始 RAG 取当前生效制度、金额表和展会例外。只读申请 API 查询该用户申请的状态及缺件清单，返回获取时间。Agent 根据已得到的事实补查缺口，而不是让每一步都由模型重新自由规划。检索仍可使用 Dense+BM25，Wiki 不代替二者，也不代替 API。

最终回答分开写：适用条件与标准、展会超标审批条件、系统目前显示的缺件、尚需用户确认事项。每个关键结论引用对应制度或授权 API 证据；API 超时可回答一般制度，但不能编个人状态。历史 Wiki 过期则绕过它取原文，主链路不应因此全部不可用。

**连续追问：工具全部成功就能输出吗？回答：** 不能。可能查错申请、用错生效期、漏掉例外或混入无权资料，仍需统一适用性、引用和权限校验。共享预算耗尽时说明已确认与未确认部分，取消后不继续补查。

**验收：** 用四组对照：职级已知/未知、单申请/多申请、API成功/失败、Wiki最新/过期，再加入撤权与新制度发布。当前系统只实现其中传统链路基础，Wiki、Agent 和业务工具集成为扩展方案，不能在面试中说成全部已上线。
