# 07｜评测、上线门禁与迭代（Q59–Q66）

[返回目录](README.md)。重要原则：指标名称不是证据，必须解释分母、粒度和实际评分实现。

## Q59｜基础：怎样建设一套能用于上线决策的金标集？

**回答：** 不从“让 LLM 随机生成一百题”开始。先按业务任务、文档类型、用户权限、时间范围和失败风险分层：单条制度、表格金额、跨文档、多轮指代、无答案、冲突旧版本、撤权、安全和实时数据问题。每题记录允许身份、空间、文档/版本、关键证据位置、必须包含/禁止包含的结论，以及是否应澄清或拒答。

将开发调参集和冻结验收集分开，按文档来源或时间做隔离，避免同一模板近似题泄漏到两边。人工标注允许多个正确证据和合理答案表达，重要样本双人复核并记录争议。合成题用于覆盖边界，真实脱敏题验证业务分布，两者不能混为一份“真实效果”。

**追问：没有时间标一千题怎么办？回答：** 先建小而分层的高价值集合，保证每个核心失败类型有样本，再从真实失败逐步扩充。几十题足以找到大问题，不足以证明极低错误率。报告样本数量和不确定性，不能在 30 题上宣称 99.9% 可靠。

## Q60｜进阶：Recall@K、Hit@K、MRR、nDCG 怎么算，有什么区别？

**回答：** 先约定评测粒度是文档、Chunk 还是证据事项。若相关集合为 {B,D}，返回前 3 名 [A,B,C]：Recall@3=1/2，Precision@3=1/3，Hit@3=1，RR=1/2。Hit 只问是否至少命中一条，不能证明回答所需证据都齐了；MRR 是多个问题 RR 的平均。

nDCG 同时考虑相关性等级和排名位置。常见 DCG@K=`Σ(2^rel_i−1)/log2(i+1)`，再除以理想排序 IDCG。不同实现可用不同 gain 定义，因此报告时写清。多跳问题最好再看所有必要事项是否被覆盖，避免一条背景资料让 Hit 看起来很好。

**追问：项目指标到底是哪一种？回答：** 当前 scorers.ts 的 ANSWERABLE_RECALL_AT_40 是按 expectedDocumentIds 对前 40 个文档身份算覆盖，HIT_AT_5 是前五是否命中。它不是标准的人工判定“答案必需 Chunk 全覆盖率”。要诚实说出实现口径，后续增加证据级和事项级评测，不能只背指标名称。

## Q61｜资深：引用精度、忠实度、正确率是不是一回事？

**回答：** 不是。引用精度检查引用是否合适，忠实度检查结论是否由给定上下文支持，正确率检查是否符合真实业务答案，完整性检查是否覆盖所有必要事项。错误 OCR 可以让答案忠实于错误上下文；真实文档引用也可能不支持具体结论；部分正确但漏掉例外的答案完整性不足。

Ragas 把 Context Precision/Recall、Faithfulness 等分开，是很好的指标组织参考，但引入框架不自动获得可靠标注。[Ragas 指标目录](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/) 微软也区分检索过程评估和端到端 groundedness 等评估。[官方评估说明](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators)

**追问：当前项目 CITATION_PRECISION 和 VERSION_SCOPE_ACCURACY 有什么局限？回答：** 当前纯评分器主要按引用 documentId 是否属于期望集合计算；同一 documentId 下引用了错误版本，若实际事实没有更细标注，该分数可能仍通过。因此不能声称这个指标已完整验证版本正确。应补 versionId、contentRevision、适用期和 Claim→证据支持关系；权限测试也应加入正文与元数据泄漏断言，而非只看 accessDecision。

## Q62｜资深：LLM-as-a-Judge 怎么用才不自欺欺人？

**回答：** 先定义可操作的评分标准和输入：正确答案/必要事实、允许证据、待评回答、具体错误类型。要求给出结构化判定及对应证据，不让模型凭“感觉像专家”评分。校准样本要含数字错、地域错、例外漏、引用伪造、空回答和看似流畅的错误答案。

与人工标注比较一致性，分析误判方向；固定模型、提示和版本，盲化系统名称，随机化候选顺序防位置偏差。LLM 评分失败/超时应显示缺失或失败，不能当 0 分/满分混进均值。生产评测成本也要算，离线内网不应调用公网 Judge。

**追问：一个模型评另一个模型不就客观了吗？回答：** 模型不同只能降低部分相关偏差，不保证业务常识正确。关键财务/法律规则需要专家金标和确定性断言。项目自身的 Claim supported 字段也要追问由谁产生，不能把被测系统自己的判断当独立真值。

## Q63｜资深：你如何证明这次优化有效，而不是碰巧改好了演示题？

**回答：** 固定数据、权限、文档版本、模型身份和测试时点，先跑基线；一次主要改变一个因素，记录变化。可做 Dense-only、BM25-only、双路 RRF、加专用 Reranker、加父块扩展、加可选 LLM 精排/语义校验的消融。每次同时看质量、拒答、延迟和成本。

对 Agentic 还需比较路由误判、额外模型/工具次数、复杂题完整性与简单题额外等待。不能因 Agentic 查得更久更广就宣布优于同预算基线；应同时给实际产品配置比较和相近预算比较。

**追问：平均分提高，但某部门变差？回答：** 分层报告部门、文档格式、语言、问题类型、风险等级和权限组，给出退化样本。关键业务的硬门禁优先于整体平均提升，不能用大量简单 FAQ 掩盖扫描合同错误。统计配对差异、重复运行波动，避免小样本过度解读。

## Q64｜资深：怎么设上线门禁和灰度？

**回答：** 门禁分四层：契约/单元与集成，权限/引用/版本强制安全，业务金标质量，容量和故障恢复。项目评分器有 Recall、引用等阈值，但代码中写着 0.95 不代表线上达到 95%。阈值需由业务风险、数据集和测量口径共同决定。

先在隔离测试空间或少量受控流量验证，再逐步扩大。影子对比可以不改变用户答案，但会额外消耗模型和处理敏感数据，需纳入权限和容量审批。回滚开关针对新请求，进行中 Run 遵循快照；发布知识和发布应用是不同变更，分别记录。

**追问：无法内网评测还能宣布完成吗？回答：** 可以明确宣布代码与本地契约交付完成，不能宣布业务效果和容量验收完成。提供脚本、样本模板、预期报告和失败定位方法，列出待执行门禁。用户确认联调通不是所有模型版本、负载和异常情形都通过。

## Q65｜资深：P95 怎么测？为什么一次压测很漂亮上线却很慢？

**回答：** 用与真实流量相近的输入长度、输出长度、复杂题比例、权限过滤和并发到达模式。分别测冷/热缓存、冷启动/稳定态、正常/拥塞、上传同时进行等情形。报告端到端分位数、错误率、排队时间、首个真实进度事件时间和完整答案时间，不能只报模型首 token。

固定并发测试会在慢请求时自动减小新请求到达，可能掩盖过载；开放到达率测试更容易暴露排队累积。不能把每阶段 P95 相加当总 P95，因为不同阶段的尾部不一定发生在同一个请求。失败请求也应计入体验统计，不能删掉超时样本美化图表。

**追问：保留日志太多会慢怎么办？回答：** 关键状态和事件持久化保证恢复，诊断日志分级/采样且脱敏；指标用低基数标签。采样不能丢掉权限失败等必须审计事项。将可观测性开销纳入压测，不能只在关闭监控时测“峰值”。

## Q66｜压轴：上线后效果逐渐变差，模型没换，为什么？

**回答：** 数据和查询会漂移：新增模板、OCR 质量下降、旧制度未失效、业务术语改变、分词词典变化、权限策略收紧、向量索引膨胀、缓存命中下降以及用户开始问更复杂问题。模型名不变也可能是服务权重或量化配置变了，需检查实际 revision。

建立失败分类和样本闭环：反馈→授权脱敏采样→人工确定目标证据→定位最早失败阶段→最小修复→回归集→小范围发布。每周看新格式、误拒答、来源错配和空召回的分层趋势，而不是仅看点赞率。文档维护负责人也应参与，知识失效不全是算法问题。

**追问：如何写复盘？回答：** 记录影响范围、时间线、检测方式、直接原因、系统性原因、临时止血、永久修复和验证证据。把“模型偶尔不稳定”继续拆成可验证机制；确实无法确定则标未知并补观测，不制造确定结论。所有改动需要验证没有把另一类错误放大。
