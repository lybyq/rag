# 01｜架构与项目陈述（Q01–Q08）

[返回目录](README.md) · 先看 [离线图](diagrams/offline.html) 和 [在线图](diagrams/online.html)。

## Q01｜基础：请用三分钟介绍这个项目，不要从技术栈开始背。

**回答：** 这是面向单企业内网的知识问答系统，重点是把制度、操作说明、表格等资料转成可授权检索、能回看原文的答案。离线链路负责让文件变成可信知识：接收、安全检查、格式解析、按需 OCR、统一 Block、结构切分、质量审核、向量化、候选索引验证和发布。在线链路根据用户身份、选定空间和问题检索，经过融合、精排、证据扩展及生成校验后返回答案。

我认为项目难点不只是“让模型回答”，而是三个一致性问题：发布的知识是否完整可查、查到的资料是否仍有权且有效、答案结论是否真的由引用支持。因此 PostgreSQL 保留业务事实和版本，Milvus 提供检索索引，任务与事件底座处理异步、重试和可追溯。

**追问：具体规模和收益呢？回答：** 说明项目按中型规模设计，但生产文档数、日查询数、P95 和正确率必须用实际监控填写。现有本地合成测试不是业务收益。可以展示测试报告及内网联调事实，不能现场编“百万文档、99% 准确率”。这是可信表达，不是回避问题。

## Q02｜进阶：为什么用 RAG，而不是长上下文或者微调？

**回答：** 我先看问题来源。若需要不断更新的企业事实、细粒度权限和引用，RAG 便于更新外部知识并在查询时鉴权。微调更适合稳定的任务行为、输出风格或领域适配，不能天然解决最新制度和可撤销权限。长上下文适合少量、明确范围的资料，但全量放入上下文会增加成本、噪声和权限审查面。

这不是三选一。比如固定几十页操作手册可以先用长上下文验证效果；大量多版本制度用检索缩小范围；稳定的分类或格式抽取任务若提示词长期不稳定，可另评估微调。模型能装下资料不代表会完整利用每条资料，仍需验证位置敏感、例外条件和成本。

**追问：RAG 不准就微调？回答：** 先判断原文是否解析出来、是否召回、是否被裁掉、是否生成失真。前三级错误，换生成模型或微调大概率治错地方。AWS 对 RAG 与微调也按知识更新和任务行为区分，而非把二者当互斥选项。[AWS 官方对比](https://docs.aws.amazon.com/prescriptive-guidance/latest/retrieval-augmented-generation-options/rag-vs-fine-tuning.html)

## Q03｜进阶：为什么分成这些服务？单体不行吗？

**回答：** 服务边界应由资源和生命周期决定。platform-api 负责业务管理接口；ingestion-worker 处理离线异步流程；document-parser-service 隔离大文件解析的 CPU、内存和崩溃风险；rag-query-service 保护在线延迟；scheduler-worker 负责定时扫描和恢复。前端是第六个应用，不是第六个后端微服务。

分开后可以单独限制解析并发、扩在线副本、隔离重任务。但代价是部署、版本兼容、监控和跨系统一致性复杂度。小团队、少文件、低并发完全可以从模块化单体起步。本项目不应该为每种 Chunker、每个模型再拆服务；它们适合代码模块和 Port。

**追问：你这个规模是不是过度设计？回答：** 用实际故障域回答：解析 CPU 阻塞是否拖慢问答？上传和在线模型是否争抢资源？独立伸缩是否真的使用？如果答案都是否，可以合并部署保留模块边界。资深工程师要能说明复杂度带来的收益，也能提出收敛方案。

## Q04｜进阶：什么是 Port/Adapter？为什么配置了 URL 还要写 Adapter？

**回答：** Port 是业务需要的能力和约束，例如 Embedding 输入 itemId、文本 Hash、调用预算，返回可对应的向量或分类失败。Adapter 才处理具体 URL、认证头、供应商字段、返回顺序和错误码。换模型应主要变 Adapter 或配置，而不是让 Controller 到处判断某厂商字段。

URL 相同风格不代表协议相同：OpenAI-compatible 也可能在 tool_calls、usage、流式事件或错误体上有差异。OCR 更可能返回字符串而不是 blocks。Zod 用于运行时验证，TypeScript 类型只约束编译时，不能保证远端真的遵守契约。

**追问：兼容不了就放宽校验？回答：** 不能把缺失关键字段当成功。先区分可选元数据和正确性必要字段：未知 OCR bbox 可以是 null，Embedding 缺项/维度错不能假装正常。增加显式响应适配模式和契约测试，并保留版本、超时、取消、429/5xx 等失败语义。

## Q05｜资深：数据库、对象存储、Redis、Milvus 各自是“真相”吗？

**回答：** 它们保存不同事实，不能笼统说只有一个系统重要。对象存储保存原始文件字节和派生产物；PG 保存身份、版本、任务、审核、发布指针和证据关系等业务事实；Milvus 是可重建的检索索引；Redis 承担队列、事件传递或缓存，不宜独立决定某版本已发布。

例如向量写入成功但 PG 尚未切换 Head，这批向量不能自动对业务可见。查询先从受控快照确定 Manifest，再搜索并回 PG 复核。这样 Milvus 中残留旧向量不会自动成为合法答案来源。

**追问：PG 挂了能不能只查 Milvus？回答：** 如果无法完成当前 ACL 和版本验证，就不应把普通降级理解为绕过鉴权。可以提供不含敏感信息的故障提示；若业务要只读灾备，必须建设经过验证的权限快照与失效策略，而不是临时去掉 PG 回源。

## Q06｜资深：LangGraph 给你带来什么？你是不是已经做了 Agent？

**回答：** 现有 LangGraph 把路由、计划、召回、证据、生成和校验组织成显式节点及条件边，便于追踪输入输出、重试和测试。现在节点路径总体由代码确定，模型只在特定位置改写或生成；有条件分支不等于模型自主规划。

真正新增的受控 Agentic 能力是根据事项覆盖和证据缺口选择下一步工具，并受共享预算、权限和停止规则限制。它目前在计划中，不能作为现有上线成果。LangGraph 是执行框架，不是自动得到正确性、幂等和权限的魔法。[LangGraph 官方区分](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents)

**追问：不用 LangGraph 能写吗？回答：** 能，用明确状态机和函数编排也可实现。选择它是为了统一图和观测，而不是算法依赖。业务规则留在纯函数/用例中，避免把领域逻辑锁死在框架 State；持久化恢复和终态仍需我们自己的工程约束。

## Q07｜资深：和 RAGFlow、Docling、GraphRAG 比，你为什么自己建设？

**回答：** 先区分它们解决的层次。Docling 重点是文档转换和结构表达；RAGFlow 是较完整的 RAG 平台；GraphRAG 强调图相关索引与检索方法。比较时要看“替换解析器”“采用整个平台”还是“增加一种检索方法”，不能放在同一列只比 stars。[Docling](https://github.com/docling-project/docling)、[RAGFlow](https://github.com/infiniflow/ragflow)、[GraphRAG](https://github.com/microsoft/graphrag)

本项目的优势是可按内网单身份、已有模型、现有 PG/Redis/Milvus 和业务接口进行集成；代价是我们承担解析、升级和可靠性维护。不能把自研说成天然更强。做方案验证时选相同脱敏资料，比较复杂表格保真、权限对接、离线依赖、处理成本与可追溯性。

**追问：什么时候愿意替换？回答：** 若现有解析器在核心文档类型上持续失败，而第三方在同集上显著提高质量，可通过 Parser Port 接入，不需要重写整个问答系统。如果团队没有维护完整平台的能力且开源平台符合业务，也应考虑整体采用。

## Q08｜压轴：你真正能讲的项目亮点有哪些？

**回答：** 我会挑可展示证据的三个：第一，Block/Chunk/Manifest 分层，使解析事实、检索策略、发布版本各自可演进；第二，多文件并发发布采用 Head CAS 与 rebase，避免晚发布者覆盖先发布文档；第三，检索回源与答案引用再校验，把“命中向量”和“可作为证据”分开。

讲亮点时按故障链解释，而不是报技术名：原来多个任务从同一 Head 构建，后一个覆盖成员；修复后发现 Head 变化就不发布陈旧候选，重新排队合并最新成员。接着说明幂等、饥饿、垃圾候选清理和集成测试边界。

**追问：你优化了多少？回答：** 目前可引用验收记录中的代码/合成测试事实，但真实业务 P50/P95 和质量改善尚需内网评测。没有数字时可以描述测量方法、已有证据和下一步指标，不能把公开论文或别家实验收益移到自己项目上。
