# 12｜LLM Wiki：编译、权限、同步与运营面试（Q85–Q96）

[返回目录](README.md) · [项目 Wiki 计划](../../requirements/llm-wiki-implementation-plan.md)。本章整体属于拟建设方案；描述的是推荐企业架构，不是某个第三方 SDK 已经替我们完成的功能。

## Q85｜基础：LLM Wiki 与传统 RAG、人工 Wiki 到底有什么区别？

**回答：** 人工 Wiki 是编辑和发布知识的载体，也可以直接成为 RAG 原始来源。传统 RAG 在提问时从资料中找证据；LLM Wiki 提前把多份资料编译成可持续维护的主题页、概念页和关系链接，把一部分整理工作从在线提问转移到离线。它是一层派生知识，不是更换聊天页面的名字。

例如差旅制度、审批办法、发票规范可汇总为“新员工差旅指南”。指南便于浏览和理解完整过程，但精确金额、地区例外和生效时间仍需回原文核验。在线问题可以先查主题页获得线索，再取原始证据，也应保留直接原文检索以免受摘要遗漏限制。

**场景追问：资料每五分钟变化一次，适合 Wiki 吗？回答：** 未必。编译和失效成本可能超过复用价值。稳定流程和术语适合编译，库存/状态/日志适合实时 API 或直接检索。收益要按页面复用、学习效率和复杂题覆盖衡量，不能承诺所有问题更快。

**验收：** 比较主题浏览任务、跨文档流程问答和单条事实问答，分别判断收益；后者不提升也可能合理，但不能因此声称全面替代原 RAG。

## Q86｜进阶：Wiki 编译谁来完成？第三方编译器和我们各负责什么？

**回答：** 推荐第三方编译内核执行概念提取、页面组织和关联生成；我们的服务负责提供已审核的来源快照、排队、预算、权限、版本、产物校验与发布。现有 ingestion-worker 可运行受隔离的编译执行器，platform-api 管理页面和审核，query-service 只读取已发布结果，scheduler 处理更新与恢复。

atomicstrata/llm-wiki-compiler 是当前候选，官方项目提供编译 Wiki 和 SDK 接入方向；这支持“先验证复用”，不证明它在本企业 GLM/中文语料上已验收。[官方仓库](https://github.com/atomicstrata/llm-wiki-compiler) 锁定发布包及依赖后应检查确切 API、运行时、模型协议、取消与增量删除语义，不能凭 README 直接当生产能力。

**场景追问：直接把整个 SDK Server 对用户暴露是不是最快？回答：** 会绕开既有身份、版本和审计边界，还可能重复建设存储和检索。优先通过 WikiCompilerPort 包装内核，把产物转成自己的受控契约。若公开扩展点不足，记录具体缺口，评估小补丁或替代，而不是偷偷重写全部算法。

**验收：** 用真实 GLM 协议、脱敏中文资料、删除更新、超时取消和完全断网环境验证。确定版本前，不把候选称为“最佳方案”。

## Q87｜资深：从已发布文档到 Wiki 发布，一次编译具体有哪些阶段？

**回答：** 先冻结允许的空间、Manifest 和文档修订，生成稳定来源输入；编译器识别概念与实体，形成页面草稿及引用；本地适配器把文件/行号引用映射回 documentVersion、Block/Chunk；再执行结构校验、事实支持/冲突检查、权限与新鲜度复核，最后审核并原子发布候选版本。

状态可设计为 QUEUED、RUNNING、VALIDATING、REVIEW_REQUIRED、READY、PUBLISHED，另有 FAILED/CANCELLED/STALE。状态不是百分比：编译器没报告页面数量时只显示真实阶段与耗时，不能模拟“完成80%”。来源入库成功不应等待 Wiki 编译成功才允许普通 RAG 查询。

**场景追问：编译期间源文件更新了怎么办？回答：** 草稿仍关联旧快照，发布前核对依赖是否仍有效。若内容或 ACL 已变化，应标过期、重编受影响部分或拒绝发布，而不是把新旧事实混在同一页面。不能只检查 compile job 成功状态。

**验收：** 在生成与发布间插入源版本更新/删除/撤权，验证旧草稿不能误发布；进度事件与状态迁移均要可重放和审计。

## Q88｜资深：概念合并怎么做？“账户”“客户”“项目”同名怎么办？

**回答：** 页面身份不能只由中文标题决定。需要稳定 conceptId、命名空间、别名、来源和概念类型；将同名候选相似性作为建议，结合组织、定义和适用范围判定是否同一概念。可先做规范化和候选检索，再让模型提出合并建议，高风险合并进入审核。

例如财务“账户”和登录“账户”应分开，两个部门同叫“项目A”也可能不同。页面 slug 只是展示路径，改名不能破坏身份；合并应保留旧 ID/链接的重定向关系，拆分需重建引用与依赖。错误合并比重复页面更危险，因为会把不同业务规则拼接在一起。

**场景追问：自动生成重复页是不是失败？回答：** 不一定，早期保守拆分比错误合并安全。可以把疑似重复放入维护队列，展示定义与来源差异，再人工确认。不能用“页面数少了”证明概念治理更好。

**验收：** 合成同名异义、异名同义、定义随时间变化和跨部门例子，测错误合并率、漏合并及引用迁移正确性。

## Q89｜资深：Wiki 引用如何做到可验证，文件行号够不够？

**回答：** 行号只有在对应的来源文件版本固定时才有意义。适配层应维护稳定导出文件、内容 Hash、行范围与原 Block/Chunk 的映射。不要每次导出都加当前时间或随机排序，导致全部行号变化和无意义全量编译。页面每个重要段落/Claim 记录依赖来源，不把文档级引用冒充逐句支持。

第三方如果只返回 Markdown，就保留原始产物，再规范化段落与引用；解析不到支持关系的段落进入待审核，不能自行补一个最近的 sourceId。Lint 可以确认链接和位置存在，但内容存在不等于支持结论，需要额外事实校验及适用条件核对。

**场景追问：引用三份原文，结论是模型“总结”出来的，算有依据吗？回答：** 要区分有明确支持的归纳与新增推断。可以展示“综合整理”并说明依据范围；若结论超出来源，标推断或删除。高风险规范不能把总结语气改成强制规则。

**验收：** 测引用存在、版本一致、原文跨度、结论支持和反例遗漏，不能只统计“每页都有脚注”。

## Q90｜资深：如何增量编译？改一个文件为什么可能影响很多页？

**回答：** 维护依赖图：源文档修订→抽取概念→页面段落→关联/汇总页。内容 Hash 没变可以复用稳定产物；某条规则变化要沿依赖找到受影响页面，重新生成或复核。概念名和页面链接变化也会传播，不能只找页面正文包含文件名的地方。

增量执行应从已发布依赖快照构建新候选，不原地修改活跃页面。第三方的文件 Hash 缓存可复用，但要验证删除、合并、模板/Prompt/模型升级是否触发正确失效。缓存键包含影响输出的版本，不能只看源文件是否变动。

**场景追问：模板改了一句话，是不是所有页都要重编？回答：** 看它是否改变语义输出。格式化展示变化可以只重新渲染；事实组织、引用要求或安全提示变化可能影响全部候选。记录变更类型和依赖，不能为了省钱继续用无法证明兼容的旧产物。

**验收：** 修改一条源规则，检查必要页面全部失效、无关页面没有无谓重建。用全量重建对照增量结果的语义/依赖一致性，而非要求随机模型输出逐字一致。

## Q91｜压轴：源文件撤权或删除，Wiki 已经总结进去的内容怎么办？

**回答：** 先阻断使用，再考虑重编。若页面依赖被删除或撤权的来源，就需要重新判断可见性；无法证明剩余内容完全由有效授权来源支持时，整个页面先标不可用/过期，不继续以“等待后台更新”为由对外展示。删除传播还包括 Wiki 向量索引、缓存、预览、导出和远端发布副本。

不总是必须销毁全部历史：审计留存应按组织政策受控保留，与普通用户可见性分离。对于被多个来源共同支持的事实，可以在重新校验来源和适用条件后发布新版本；不能因为其他文档出现相似字句就自动保留敏感推断。

**场景追问：删了引用链接但页面正文还在，是否足够？回答：** 不够，正文已经携带信息；只删脚注反而切断审计。需要内容级失效和访问控制。远端平台无法立即删除时，应告警并执行预先约定的封禁/撤回流程，不能声称已全链路完成撤权。

**验收：** 在浏览、问答、缓存命中和同步期间撤权，检查正文、标题、搜索摘要、计数与历史事件的可见性，并测撤回完成时延。

## Q92｜资深：混合权限文档编成一个 Wiki 页面，ACL 怎么算？

**回答：** 最保守是页面读者必须有权访问它所依赖的全部来源，即有效访问集合求交。不要机械地对 roles 字符串求交，因为 ACL 可能包含用户、角色、显式拒绝和动态规则；应使用统一授权服务判断。页面内容形成的新推断可能更敏感，也需业务分类。

若求交导致几乎没人能看，可以按权限一致的来源分开编译页面，或建立经过审查的公共版。段落级动态裁剪要求非常完整的段落依赖和推断边界，删掉一段可能让剩下标题或关联仍泄露事实，因此不是第一版的低成本方案。

**场景追问：公开薪酬制度和机密工资名单合成“薪酬指南”可以给所有人吗？回答：** 不能。即便最终没直接列名字，也可能包含由机密来源推出的分布、上限或例外。应只使用公开授权来源生成公共版，而不是生成后靠关键词脱敏。

**验收：** 构造多个权限集合及动态撤权，验证页面、链接图和推荐列表；权限不足时不能暴露“还有三份你无权看的来源”这类计数。

## Q93｜资深：人工修改与自动重编冲突怎么办？

**回答：** 明确内容所有权。可把模型生成区、人工备注区、已审核事实修正分开；人工修改记录 baseRevision 和 patch，不直接覆盖成无法区分来源的 Markdown。新编译候选与旧发布版、人工编辑版做三方比较，涉及同一段落或来源变化时进入冲突审核。

人工纠正事实不能只改 Wiki 表面，否则下次重编又回错。应链接对应源数据修订或维护一条审核过的补充来源。批准记录绑定具体候选 Hash；候选内容变化后旧审批失效，不能“这个页面以前审过”就跳过新校验。

**场景追问：全部人工修改都永久保留是否最安全？回答：** 不安全，人工备注也会过时，可能与新政策矛盾。保留修改历史，但按新来源重新判断内容；需要人工处理时暂停该部分发布，不静默覆盖也不永久冻结错误。

**验收：** 测同时编辑、审核后重编、源文档废止、人工修正与模型新增段落冲突，验证明确的版本提示和恢复能力。

## Q94｜资深：已有内网 Wiki，怎样导入和反向发布，避免循环？

**回答：** 把 SourceConnector 和 PublisherConnector 分开。导入维护 sourcePlatformId、remotePageId、remoteRevision、游标和 ACL；发布维护本地 pageId、发布版本、远端目标 ID/ETag 和 origin 标记。默认使用专用目录，并明确哪一侧是内容权威，不把任意页面做无规则双向合并。

导入应排除本系统生成目录，或依据 origin 和内容版本识别回流，避免“生成页→重新摄入→再次总结”放大错误。远端写入使用版本条件/ETag CAS，遇到人工更新则冲突而非覆盖。PG 发布和远端 API 不是一个事务，用 Outbox、幂等和同步状态表示最终一致。

**场景追问：本地发布成功、远端失败，页面算发布了吗？回答：** 分开报告本地 PUBLISHED 和远端 PENDING/FAILED，不能用一个绿色状态掩盖部分失败。重试按相同发布身份进行，不能创建多个重复页面；远端没有等价 ACL 能力时，拒绝发布受限内容，不能默认目标平台“内网所以安全”。

**验收：** 测重试、超时后实际已写成功、远端人工修改、删除、目录移动、权限差异和同步循环，保留两个系统的状态与关联 ID。

## Q95｜资深：Wiki 编译耗时长、贵、容易失败，如何运行和恢复？

**回答：** 在现有 Worker 中设独立队列、并发和模型额度，按空间/build/attempt 隔离工作目录；冻结输入快照，阶段产物带 Hash。只在持有租约的执行器上推进状态，重复投递不得重复发布。模型请求和工具重试使用总预算，不能每恢复一次就重置已消耗额度。

取消要停止后续调度并拒绝迟到结果；SDK 不支持彻底取消时可用隔离子进程终止本地执行，但远端推理是否终止需要模型服务配合。恢复可以复用已验证、输入一致的中间产物，不复用失败尝试留下的半写文件。离线模型编译不能挤占所有在线问答容量。

**场景追问：必须新增一个微服务吗？回答：** 不一定，先在现有 ingestion-worker 内用模块/执行器隔离，复用部署。若运行时、内存、吞吐和故障域需要独立伸缩，再拆服务；代码模块划分与资源隔离是两件事，不能只放不同目录就认为不会相互影响。

**验收：** 注入进程崩溃、部分页面成功、模型超时、磁盘满和租约换主，确认旧版本仍可用、失败候选不泄露、预算与状态可追溯。

## Q96｜压轴：怎样证明 Wiki 值得建设，而不是多一层幻觉？

**回答：** 分两类评测：产物质量和业务收益。产物看来源覆盖、引用支持、条件/例外保留、概念重复/错误合并、断链、更新失效和权限；业务看找到完整流程的时间、跨文档题完整性、重复问题成本与维护人力。漂亮页面和高链接数量都不是正确性指标。

和原 RAG 做同题对照，尤其加入单条事实题，确认 Wiki 没有增加错误和无谓延迟。对错误结果做归因：是编译遗漏、检索错页、来源过期，还是在线生成错。试点一个资料稳定且权限一致的空间，有明确退出条件，不一上来编译整个企业。

**场景追问：网页 lint 全通过，能自动发布吗？回答：** 只能说明 lint 覆盖的规则通过，例如链接存在；还需要事实、适用性、授权和风险策略。低风险目录页可自动化更高，高风险制度指南保留审核。编译器能力和企业放行规则不能混淆。

**验收：** 新增“源修订后旧错误存活时间”“编译失败下的可用性”“删除撤权传播”指标。面试可以讲这些设计与实验方案，但试点没完成前不讲成生产成果。
