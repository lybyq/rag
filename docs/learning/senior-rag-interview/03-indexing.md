# 03｜Embedding、Milvus 与原子发布（Q21–Q30）

[返回目录](README.md)。本章把“向量生成成功”“写入成功”“搜索可见”“业务发布”四件事分开。

## Q21｜基础：Embedding 是什么？为什么不能换个模型继续查旧向量？

**回答：** Embedding 把文本编码为数值表示，使相关表达在同一个表示空间中容易匹配。查询和文档必须使用兼容的模型/模板；维度相同只证明数组长度相同，不证明坐标语义相同。两个不同训练出来的模型，某个维度代表的关系不相同，直接混查会产生没有意义的距离。

项目通过 Profile 记录模型 ID、revision、维度、归一化及输出能力，通过内容 Hash 对应输入。模型迁移应构建新 Profile 和候选索引，使用同题对比与发布门禁切换，而不是覆写 env 后继续复用旧库。查询侧和文档侧模板可以不同，但必须是该模型支持且被版本化的配对。

**追问：模型名没变，运维换了权重呢？回答：** 这是必须防的“同名不同物”。部署应暴露明确 revision 或受控发布标识，响应、缓存、索引与运行快照关联该身份。没有版本信息时不能靠字符串 model 名保证兼容，需要部署流程冻结及契约样本验证。

## Q22｜进阶：你会怎么选 Embedding 模型，而不是直接说 BGE 好？

**回答：** 先定义语料和查询分布：中文制度、英文术语、产品编码、短问长文、表格还是代码。再检查内网硬件、最大输入、吞吐、许可证、量化和服务协议。候选模型用相同解析和切分结果比较 Recall@K、难负例区分、单位/数字条件、跨语言和成本。不能只看通用榜单平均分。

选择 BGE 系列可以结合已有内网服务和部署条件，但“模型支持 dense/sparse”不代表当前 endpoint 都支持。项目的 Adapter 能力要以真实响应为准。FlagEmbedding 官方同时提供检索和重排相关模型/工具，说明二者是不同任务，不意味着随便互换。[官方仓库](https://github.com/FlagOpen/FlagEmbedding)

**追问：量化后更快就上线吗？回答：** 用同一模型未量化版本做基线，检查短编码、近义否定、金额条件等难样本是否掉召回，再看吞吐/内存收益。模型推理吞吐快不代表端到端一定快，可能瓶颈在解析、PG 回源或生成。

## Q23｜进阶：成千上万个 Chunk 怎样批量向量化？

**回答：** 同时限制每批条数和总 Token，不是固定每批 100 条。短文本和长文本的资源消耗不同，项目 planEmbeddingBatches 按稳定顺序组批，单条超限明确失败。executeEmbeddingBatches 有有限并发、队列上限、可重试失败项重试和取消，避免瞬间把内网模型压垮。

返回必须按 itemId 和内容 Hash 对齐，不能假设远端顺序永远正确。漏项、重复项、维度错、非有限数值等需要契约层检查；成功项和失败项要独立记账。HTTP 整批失败与响应内部分失败不同，重试责任应明确，不能 Adapter 重试后应用层又无界重试。

**追问：多开 Worker 就会更快？回答：** 模型服务器总吞吐是共享瓶颈。并发过高会让队列时间、显存和 429 上升。应观测批次 Token、在途数、队列等待、推理耗时和失败率，采用背压及有上限重试；离线任务不能抢光在线查询所需资源。

## Q24｜进阶：为什么你缓存 Embedding，而不是缓存整个回答？

**回答：** 向量缓存的语义比较清晰：同一输入文本、模型 revision、维度、模板、归一化和输出模式对应同一种数值结果。项目 cache key 包含这些事实的 Hash，不把每次 Run 时间放进去，否则永远无法复用。实际问题文本不直接暴露在 key 中，但 Hash 不等于加密，缓存访问仍需保护。

向量缓存不代表用户可以读取任何文档；即使命中缓存，仍需当前权限、Manifest 和时间范围过滤。答案缓存更复杂，必须考虑角色/用户有效访问集、知识版本、提示词/模型版本、业务时间、工具数据新鲜度以及删除撤权。两者不能共用一个简单问题字符串 key。

**追问：跨用户缓存安全吗？回答：** 当前查询向量是输入的表示，不是检索结果，权限在后续检查。但缓存系统本身仍可能保存敏感表示，需要访问控制和保留期。检索结果和答案跨用户共享则必须证明权限等价；不能只因相同 roles 就忽略用户级授权变化。

## Q25｜基础：Dense、模型 Sparse、Milvus BM25 分别是什么？

**回答：** Dense 是固定长度的稠密向量，适合语义近似；模型 Sparse 是模型生成的稀疏词项/特征权重；BM25 是依据词频、逆文档频率及文档长度等计算的词法相关性。Sparse 是表示形态，BM25 是一种检索评分方法，两者不是同义词。

你内网目前是 Embedding 提供 Dense，Milvus 内置 BM25 接收原文/查询文本并完成词法处理，不要求 Embedding 的 /pooling。Milvus 官方要求相应文本字段、analyzer、BM25 Function 及稀疏索引配置。[全文检索官方文档](https://milvus.io/docs/full-text-search.md)

**追问：本地代码就是这样吗？回答：** 本轮审阅的本地 Adapter 接受 SparseVector，创建 sparse_vector 后使用 IP 路线，未核实内置 BM25 接入。应如实说明内网适配与本地需对齐。不能把函数名中有 Sparse 或测试注释写了 BM25 当成实际 BM25 已实现的证据。

## Q26｜资深：中文 BM25 效果差，从哪里调？

**回答：** 先看 analyzer 实际产出的词项，而不是立刻调权重。“差旅报销”“研发一部”“AB-1024”被怎样切分、符号是否丢失、中英混排是否统一、停用词是否误删，都可能决定能否命中。查询与索引处理必须兼容；BM25 不是天然理解同义词和指代的语义模型。[BM25 Function](https://milvus.io/docs/bm25-function.md)

再检查词法索引的文本是否保留标题、产品编码、单位和表头，是否只索引了短摘要。参数 k1 调节词频饱和，b 调节文档长度归一化，但不应先凭感觉修改。离线测试可以分别看精确编码、业务术语、普通问句，比较词法 Recall 和难负例。

**追问：词典更新只改查询端行不行？回答：** 若分词改变索引词项语义，旧索引未必兼容，通常要评估重建和新旧 Profile 切换。不能热改后宣称历史文档自动更新。规范化原文、别名扩展和用户精确字面量要分开，避免把两个产品型号混成一个词。

## Q27｜资深：Milvus 存哪些字段？为什么不只存向量和文件名？

**回答：** 文件名不唯一且可更名，不能作为引用身份。当前记录含 vector_id、manifest_id、space_id、document_id、document_version_id、content_revision、chunk_id、内容 Hash、Embedding Profile、标题路径和定位信息等。检索结果携带身份，正文和最终权限回 PG 核验。

Milvus 本地现有 Schema 保存短摘要，不以完整业务正文为唯一真相。内置 BM25 则需要可分析的检索文本字段，这正是与当前本地适配差异要核实的地方，不能只把旧 short_summary 字段随便当 BM25 全文，导致长文要点丢失。新增检索文本是索引副本，不替代源文档事实。

**追问：为什么不每个用户建一个 Collection？回答：** 权限组合变化大，会造成数据重复和更新困难。优先按模型 Profile/业务隔离需求组织，查询过滤与 PG 复核实施权限。只有明确隔离、规模或运维需求才分库/Collection，不能用物理分组替代完整授权检查。

## Q28｜资深：HNSW 怎么调？召回差就加 topK 吗？

**回答：** HNSW 用图结构近似搜索，M 影响连接和内存，efConstruction 影响建图质量/成本，查询 ef 影响搜索探索量及延迟。当前本地建索引是 HNSW/COSINE，M=16、efConstruction=256，这是代码参数，不是已证明最优的结论。查询 ef 的实际默认值和 SDK 支持要核实，不能凭印象填数字。[Milvus HNSW](https://milvus.io/docs/hnsw.md)

调参先用一部分数据的精确搜索或高质量基线估计 ANN Recall，再比较延迟、内存、构建时间和过滤场景。若目标块在精确搜索中也排很低，问题可能在模型/文本而非 ANN。TopK 增大会扩大候选，但不保证弥补搜索探索不足，也会拖累精排。

**追问：向量容量怎么估？回答：** 原始 float32 向量约 N×d×4 字节，还要加图索引、标量字段、文本、segment、复制和系统开销。举例 100 万条 1024 维，仅原始向量约 4.096 GB 十进制字节，绝不是整套服务内存需求；实际用压测和监控测放大系数。

## Q29｜资深：写入 Milvus 后为什么不能立刻宣布发布成功？

**回答：** 写入响应、持久化、索引就绪、读可见性和业务发布是不同阶段。项目先构建候选 Manifest，检查完整性和可检索条件，然后原子切换 PG Head。失败时保留旧有效版本，不把半套新索引暴露给用户。数量核对也不够，还要防止 Hash、成员或版本串错。

Milvus 有不同读一致性等级，可见性与延迟存在取舍；不能把 Strong 理解成业务事务，也不能把 flush 理解成权限和 Head 已正确更新。[Milvus 一致性](https://milvus.io/docs/consistency.md) 具体发布检查应与所用服务版本及 SDK 验证，而不是每次查询随手强制 flush。

**追问：换模型怎么回滚？回答：** 保留旧 Profile/Manifest，候选新索引验收后切换，查询使用冻结快照。回滚是切回仍有效的版本，但删除、撤权或法规失效后的资料不能因技术回滚重新开放。清理旧索引要考虑在途 Run 引用与保留窗口。

## Q30｜压轴：同一个空间同时上传 A、B 两份文档，为什么最后只查得到 B？

**回答：** 这是典型丢失更新：A、B 都从 Head H0 构建候选，A 发布 H0+A，B 随后发布 H0+B，A 成员被覆盖，即使 A 的向量仍在库里也不属于当前 Manifest。不能只给单个文档加锁，因为竞争资源是空间发布 Head。

项目已加入 base_manifest_id 和 rebase_count，发布事务锁定空间/Head并比较构建基线。发现 Head 已变就不发布陈旧候选，而通过 Outbox 重排，基于新 Head 重建再试。模型和 Milvus 调用放在事务外，避免长时间持锁。验收记录还明确：相关 PG 集成测试曾因本机数据库未运行无法现场复跑，不能说它当时已完成真实并发验收。

**追问：高并发一直 rebase 呢？回答：** 需要有界重试、按空间合并/串行发布或聚合构建，避免饥饿。追踪 rebase 次数、候选垃圾、队列等待与最终成员集合。最小测试是并发 A/B 完成后当前 Head 同时包含两者，而不是只检查两个上传接口都返回 200。
