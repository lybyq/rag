# 11｜传统 RAG 尚未实现的高级方案与困难场景（Q73–Q84）

[返回目录](README.md)。本章是扩展设计与选型训练，不表示本项目已经实现这些能力。每项都要回答“为什么用、何时不用、如何测”，不是新功能开发承诺。

## Q73｜进阶：用户问题太口语、缺少领域词，普通改写仍召回不到，怎么办？

**回答：** 先判断是词汇错配还是根本没有资料。词汇错配可增加业务同义词、缩写展开、受控多查询；保留原查询和精确型号，避免改写把范围改变。HyDE 则先生成一段假设性回答/文档，用它的向量寻找真实资料；生成文本只能是检索线索，不能作为最终证据。[HyDE 原论文](https://arxiv.org/abs/2212.10496)

实现上把原始问题、词法查询、语义扩展分开，记录每条查询来源与策略版本，对等价查询去重并限制数量。HyDE 若猜出不存在的法规编号或品牌，可能把搜索引到错误区域，所以应保留原问题的直接召回，并在真实证据阶段重新核对所有事实。权限范围不由扩展文本决定。

**场景追问：用户问“那个蓝色按钮点不动”，用 HyDE 合适吗？回答：** 若完全不知道产品和页面，应先澄清或获取授权截图；直接生成假设故障会把猜测固化。若已知产品、页面和错误码，术语映射与故障手册检索更可控。选择方法取决于缺的是表达还是关键条件。

**验收：** 分别测口语改写、精确编码、无答案问题；比较原检索、多查询、HyDE 的证据 Recall、错误扩展和额外模型延迟。当前项目的按需改写不等于已实现 HyDE。

## Q74｜资深：单向量压缩了太多信息，多向量、Late Interaction、Late Chunking 怎么分？

**回答：** 单向量把一个片段汇总为一个表示，成本低但可能弱化局部细节。多向量可给同一来源建立标题、摘要、关键问题等多个表示，或保存多个 token 级向量；这两类“多向量”不是同一种算法。Late Interaction 类方法保留较细表示，在查询时计算细粒度匹配；Late Chunking 则利用长文上下文生成 token 表示后再切分池化，通常仍得到片段向量。

选型看瓶颈：标题和正文语义差异大，可先试多表示；长段指代依赖前文，可评估 Late Chunking；细粒度术语对应很重要且能接受索引和计算成本，可评估 Late Interaction。不能把普通句向量 HTTP 接口当成已经暴露 token 级特征。[Late Chunking 论文](https://arxiv.org/abs/2409.04701)

**场景追问：同一段存五个向量，会不会在 RRF 中获得五倍优势？回答：** 会产生重复投票风险。必须区分 representationId 与 sourceChunkId，在表示层召回后合并回真实来源，限制同来源贡献，防止“向量多的文档”凭数量霸榜。最终引用仍回原始 Chunk，不引用合成问题。

**验收：** 比较相同证据预算下的召回、候选去重、索引体积、重建时间和 P95；不要只展示多花五倍空间后的最好样本。

## Q75｜资深：跨语言、部门黑话和产品别名怎么解决？

**回答：** 三种问题分别处理：跨语言需要评测查询语言与文档语言的匹配；部门黑话需要有来源的术语词典；产品别名需要绑定实体与版本，而不是无条件同义词替换。可以并行保留原语言词法路线与受控翻译/扩展路线，所有翻译生成物只作检索提示。

词典要记录适用组织、时间和消歧信息。例如“中台”在财务和技术团队可能不是同一概念，“Apollo”可能对应不同系统。查询中出现缩写时先用当前空间和上下文缩小候选，仍不确定则澄清。向量模型是否多语种只是能力起点，不保证企业专有名词准确。

**场景追问：英文学名翻译错了，为什么不统一把全部文档翻成中文？回答：** 全量翻译成本和维护量高，也可能破坏型号、法条和引用定位。更稳妥的是保存原文，必要时增加翻译检索表示并关联原位置；重要结论展示原语证据，译文标注为辅助解释。更新时原文和派生译文必须同步失效。

**验收：** 建立跨语言同义、同名异物、缩写多义和精确编号测试，统计消歧成功率与误扩展率，不能只看整体中文 Recall。

## Q76｜资深：领导问“总结所有制度的主要风险”，为什么 TopK 不够？

**回答：** TopK 是相关性抽样，不是全集证明。“所有”要求先确定文档集合、时间快照和处理覆盖。可以设计全量批处理：按文档/章节抽取风险 → 保留原证据 → 去重和分组 → 汇总；每步有完成/失败清单，最终报告哪些资料未处理，不把缺页资料也算审查完毕。

层次摘要检索（例如 RAPTOR 的树状摘要思路）或图社区汇总可以帮助宏观组织，但摘要会损失细节，不能自动保证穷尽。摘要节点须回链到原证据，查金额或例外时下钻原文；“趋势概览”与“审计确认没有遗漏”使用不同验收标准。[RAPTOR 原论文](https://arxiv.org/abs/2401.18059)

**场景追问：改成 Agent 多查几次不就覆盖全库了吗？回答：** 多轮搜索仍可能反复命中热门资料，不能证明访问了全部有效文档。全库审查应由可枚举的 Manifest 成员驱动，Agent 可以决定分析任务但不能代替覆盖计数。数据变化时应固定批次快照，避免处理过程中集合漂移。

**验收：** 检查成员覆盖、页/章节失败、风险事项召回和可复核引用。只能确认抽样时，必须在答案里限定范围。

## Q77｜资深：精确统计、关联表查询、报表分析为什么不能只用 RAG？

**回答：** “找到一条标准”和“计算全年总金额”是不同任务。后者需要完整集合、过滤口径、去重主键、关联关系、币种与时间边界，TopK 片段很容易漏行或重复。应把表格按受控流程转成结构化表/接口，RAG 检索指标定义和计算规则，数据库/计算工具执行统计，答案同时引用口径和结果来源。

不一定一开始就开放自由 SQL。固定业务问题优先参数化指标接口；灵活分析再评估受限 NL2SQL：只读角色、行列权限、允许表/函数、AST 检查、查询成本上限、超时和结果条数限制。数据库权限是真实安全边界，Prompt 不是。

**场景追问：表格是上传的 Excel，不在业务库怎么办？回答：** 创建隔离的结构化数据集，识别区域、列类型、主键、单位和公式缓存，完成质量审核后查询。禁止执行不可信宏/公式。若没有稳定表头或总计/明细混排，先人工确认语义，不能让模型自行猜后输出精确统计。

**验收：** 用已知总额与多币种、重复行、空值、跨表关联反例验证。必须能从结果回查使用的数据集版本及计算口径。

## Q78｜资深：流程图、示意图、图表，OCR 能取出字就够了吗？

**回答：** 不够。流程图关键信息是箭头、分支条件和节点关系；折线图包含坐标轴、图例、刻度与曲线对应；设备示意图可能依赖相对位置。OCR 只识别字会丢关系。可选择结构化视觉解析、图像/文本多模态检索或先定位原页再做受控视觉问答。

工程上保存页图/区域、原始文本和视觉派生结果，明确来源与模型版本；视觉描述是候选解释，不是未经验证的原文事实。图像检索的相似度与文本向量分数同样需要融合策略，不能直接相加。高风险数值读图要检查坐标轴单位和缩放方式。

**场景追问：纯文本 PaddleOCR 能不能推导审批箭头？回答：** 当前接口无法可靠提供这一结构，不能宣称已支持。需要供应商返回版面/关系信息，或新增视觉模型 Adapter；能力不足时返回原图辅助审核。不能拿文字出现顺序冒充流程执行顺序。

**验收：** 测相同文字不同箭头、相同曲线不同坐标尺度、双轴图和遮挡图，评价关系/数值正确率，而不仅是 OCR 字符准确率。

## Q79｜资深：如何回答“当时有效的制度是什么”，而不是永远取最新版？

**回答：** 要区分业务生效时间和系统获知时间。文件可能今天录入，但上个月已经生效；也可能发布了但下月才生效。基本方案记录 effectiveFrom/To、发布/入库时间、替代关系和适用主体；审计类问题还需支持“截至某个系统时点，当时知道哪些资料”的双时间语义。

问题时间应来自用户明确输入或业务默认，并记录在 Run。查询在对应快照和业务有效期下执行；旧制度可以回答历史问题，但不能用于当前指导。删除、撤权与历史审计访问是不同政策，保留历史版本不等于所有用户一直能读。

**场景追问：制度后来被追溯修正，旧答案还能复现吗？回答：** 保存原 Run 使用的版本和快照用于审计，当前问答使用更正后的事实并说明时间基准。复现旧输出不是重新授权旧内容；访问历史答案同样需要当前权限与保留政策。

**验收：** 覆盖未来生效、追溯生效、重叠期间、局部条款修订和时区边界。当前存在版本/生效期基础，不等于完整双时间数据库已实现。

## Q80｜资深：数据每天更新，怎样增量同步而不全量重建？

**回答：** 根据来源能力选择 CDC、Webhook 或带游标轮询，维护稳定外部对象 ID、版本/ETag、内容 Hash 和同步水位。事件允许重复和乱序，用来源版本判断是否接受，删除用 tombstone 传播。一次抓取成功不等于整个来源快照完整，不能将“本批没看到”直接当删除。

内容变化后重做受影响文档的解析/切分和 Embedding；模型/模板变化则可能需要整个 Profile 重建。可对稳定内容 Hash 复用向量，但最终来源位置和身份要随新版本重新关联；内容相同不意味着 ACL 相同。发布仍走候选与 Head，而不是对活跃索引边删边写造成半成品窗口。

**场景追问：Webhook 丢了怎么办？回答：** 定期做受控对账，比较来源清单、水位和本地状态；对账有分页和缺失重试。更新失败不能悄悄保留旧文并显示“已同步”。新鲜度要有明确时间戳和告警，删除/撤权优先于普通增量更新。

**验收：** 测重复、乱序、漏事件、部分分页失败、源对象移动/重命名和权限变更。本项目已有外部文档身份与批次幂等基础，不等于所有连接器和 CDC 已完成。

## Q81｜资深：高频相似问题能否使用语义答案缓存？

**回答：** 可以评估，但比 Embedding 缓存危险。两个问句向量很近，可能只差一个“不”、地区、职级、年份或金额。缓存匹配不仅看相似度，还要核对任务、关键条件、权限范围、知识版本、模型/Prompt 版本和实时数据时效；高风险或实时业务可直接禁止复用最终答案。

较保守方案先缓存检索计算或已验证证据，命中后仍重新核验权限/版本并生成；真正答案缓存以精确规范化请求作为第一步。语义缓存命中返回必须包含有效引用，来源更新、撤权和删除时失效，不能只等 TTL。缓存访问本身也要受控，避免通过命中时间推测敏感问题是否出现过。

**场景追问：“P6 的标准”和“P7 的标准”相似度极高怎么办？回答：** 精确条件签名不同，不允许直接复用；无职级的问题也不能复用某个职级的答案。宁可少命中，也不能把缓存优化变成业务串答。

**验收：** 构造近似但结论相反的 hard negatives，测错误复用率、撤权失效时延和实际成本收益，而不是只报命中率。

## Q82｜资深：什么时候值得微调 Embedding 或 Reranker？怎么避免负样本伤害？

**回答：** 只有在解析、切分、过滤、指标口径都正确后，仍持续出现领域语义错配，且有足量可靠标注时再考虑。构建 query-positive-hard negative 数据：例如同条款不同地区、相同术语不同产品、旧版本与现行版本。负样本应由业务规则或人工确认，不能把没被点击的结果全部当不相关。

训练集与评测集按来源/时间隔离，防止同模板泄漏；比较基础模型和新模型在领域集与通用保留集上的表现。若用点击日志，要校正曝光/位置偏差，保护用户敏感问题，确认数据使用授权。先改模板、词典和候选池可能更便宜，微调不是默认起点。

**场景追问：训练后领域题好、普通题变差？回答：** 说明可能过拟合或遗忘。可以混合训练数据、调整目标或分场景路由，但必须计入多模型运维成本。新 Embedding 需要重新索引并版本切换；新 Reranker 主要改变排序和阈值，也必须重新校准，不沿用旧置信阈值。

**验收：** 同预算测域内/域外 Recall、排序、延迟、内存和误拒答，报告分层退化，不只展示训练损失下降。

## Q83｜资深：复杂流程手册必须跨章节，什么时候用知识图谱？

**回答：** 先区分显式文档关系和抽取出的业务关系。章节引用、附件链接、父子块可以用普通关系表实现，不必上图数据库。若用户常问供应商—合同—产品—责任部门等多跳实体关系，且关系类型稳定，图结构可以帮助探索路径，仍需关联原文证据和时效。

图也会错：同名实体合并、关系方向颠倒、否定关系丢失、跨时间关系混用。为实体保留规范 ID、别名、组织/时间范围；每条边保留来源与版本，不能把模型抽取的一次猜测永久变成事实。推理路径可解释不意味着每个节点和边都真实。

**场景追问：加入 GraphRAG 就能问全公司所有关系吗？回答：** 不能。先明确抽取覆盖、实体消歧质量和授权路径；图上的中间节点也可能敏感，不能只过滤最终节点。可以先用关系表+受控遍历验证业务价值，再决定图数据库和全量构建成本。

**验收：** 测多跳答案、路径来源、同名实体和撤权传播，并与普通多查询 RAG 同题对比。LangGraph 工作流本身不提供企业知识图谱。

## Q84｜压轴：不知道用哪种高级技术时，你的决策流程是什么？

**回答：** 先按最早失败层分类：原文丢失修 Parser；条件丢失修切分/上下文；术语错配试词典和查询扩展；准确词命中差查 analyzer/BM25；局部语义弱试检索表示/模型；全量统计用结构化查询；动态业务用 API；宏观组织试层次摘要/Wiki；按证据动态找资料才考虑 Agentic。

每个候选方案写清预期修复的错误类型、额外依赖、成本、权限影响和最小对照实验。给自己一个退出条件：若复杂度明显增加但核心指标没有改善，就停用，而不是因为已写代码就扩大部署。一个企业平台可以组合方法，但每条路径应有明确任务边界。

**场景追问：老板说同行都有 Agent，我们也要？回答：** 可以提供受控试点，但把验收从“有 Agent 按钮”改为复杂题完整性、简单题延迟、工具调用成本和安全。先用现有 RAG 做基线，避免把本来可以靠数据治理解决的问题包装成模型升级。

**验收：** 对每个失败样本说明最小必要方案和不采用的替代方案，能够复现实验、解释退化并回滚；这比背诵十个算法名称更体现资深能力。
