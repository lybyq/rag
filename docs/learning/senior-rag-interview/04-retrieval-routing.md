# 04｜问题理解、路由、混合召回与精排（Q31–Q42）

[返回目录](README.md) · [在线图](diagrams/online.html)。当前已实现与扩展方案会分开描述。

## Q31｜基础：用户输入后，第一步是不是马上计算向量？

**回答：** 不是。先验证身份、请求结构、用户选择空间、Run 配置和取消/超时上下文，再判断是否知识问题。当前 routeQuery 返回 CHAT、KNOWLEDGE、CLARIFY、REJECT：问候用规则识别，缺少上下文的模糊指代可澄清，明显越权要求拒绝，其他走知识路线。简单短查询没有必要先付一次改写模型延迟。

规则只负责有限入口判定，不能识别所有恶意请求，也不是完整意图分类器。知识查询进入计划时冻结范围和 Profile，模型可以建议查询词但不能生成 SQL/Milvus Filter。空问题和非法输入在契约边界拒绝，而不是让模型自由猜。

**追问：用户说“你好，报销上限多少”呢？回答：** 不能因为出现你好就判闲聊，应按整句规则和任务信号判断。要测试带寒暄的真实问题、短产品编码、模糊代词、否定问法。当前正则路线有边界，扩展到复杂意图应做分类评测，不把规则命中率当全场景理解能力。

## Q32｜进阶：上下文指代消解如何做？“那上海呢”怎么办？

**回答：** 保留结构化历史实体和当前问题，让当前明确条件覆盖同类历史条件。例如前一轮问“北京 P6 住宿标准”，下一轮“那上海呢”，可以继承住宿事项和 P6，把城市替换为上海，而不是把北京和上海同时强塞进检索。项目 query-plan 合并实体时采用当前优先，并按需调用改写。

但不是所有上一轮信息都能继承。用户切换知识空间、话题或询问对象后，旧实体应失效；模型生成的答案不能自动成为可信用户条件。记录实体来源、轮次和适用范围，复用最少上下文，不把整段聊天历史不断累加。

**追问：“他能报销吗”前面有两个人？回答：** 应反问具体对象，而不是按最近一个名字猜。指代候选多、权限范围不明或金额受职级影响而职级缺失时，需要澄清。答得快但错误归因不是好的交互；当前历史实体规则不等同于完整对话状态机，复杂场景属于扩展设计。

## Q33｜进阶：问题拆分和查询改写有什么区别？

**回答：** 改写通常保持一个任务，换成更适合检索的表达；拆分把多事项变成可分别验证的子问题。例如“试用期能否出差、住宿多少、谁审批”至少有资格、标准、审批三项。项目已有受限子问题建议和最多四个子问题计划，但不等于已实现任意动态依赖图。

要保护精确字面量：产品型号、日期、金额、否定词不能被漂亮的自然语言改写掉。原查询应保留用于召回/核验，并记录改写版本。如果一个子问题依赖另一个结果，如先查员工职级再查标准，不应未经确认并行假定职级。

**追问：拆得越多召回越全？回答：** 不是。子问题越多会增加检索请求、噪声和 RRF 重复投票。应设上限、语义/规范化去重、保留每个事项覆盖表，必要时在事项层先融合再总体选择。看最终完整回答率和调用成本，而不是“生成了多少查询”。

## Q34｜资深：闲聊、知识库、联网和业务 API 怎么动态路由？

**回答：** 先按信息性质，而不是按工具名字。制度解释查知识库；当前库存、报销进度、订单状态查授权业务 API；公开时效资讯只有在允许联网时才用外部搜索；一般寒暄不消耗检索。混合问题可以拆成规则证据和实时事实两个子任务，最终注明各自时间与来源。

当前项目只有受控知识路线等入口，联网/API 动态选择未实现。内网默认无外网，因此不能让知识库查不到就自动发去互联网。未来工具注册需声明输入 Schema、权限、数据分类、超时、允许域名/接口和只读属性，模型返回工具建议，由代码执行白名单检查。

**追问：用户给 URL 就抓取？回答：** 不应直接抓。要防 SSRF、重定向到内网敏感地址、DNS 变化、超大文件和凭证泄漏；外部内容也必须防提示注入。业务 API 使用用户授权范围，不用一个管理员 Token 替所有人绕过权限。失败时明确缺少实时信息，不用模型编一个状态。

## Q35｜资深：什么时候反问，什么时候先回答一部分？

**回答：** 若缺失信息会实质改变结论且无法安全推断，反问最少必要条件，例如地区、职级、时间或适用主体。若三个事项已有两个有充分证据，可以先回答确定部分并标明剩余需要什么信息；不要把“没检索到”伪装成“问题不清楚”。

澄清必须区分三类：用户条件缺失、文档相互冲突、系统能力/检索失败。第一类问用户，第二类说明版本或适用范围冲突并找权威来源，第三类排错或补检索。降低模型温度不能解决这些类别判断。

**追问：怎么评测反问过多？回答：** 金标记录该题是否必须澄清和最少缺失槽位。统计不必要澄清率、澄清后完成率和用户放弃率。若多数问题已可从原文条件直接回答却反问，应检查路由与覆盖判定，不要为了“安全”把所有问题都推回用户。

## Q36｜基础：Dense 与 BM25 为什么要一起用？

**回答：** Dense 对近义表达有优势，如“报销多久到账”与“费用支付时限”；BM25 对原词、条款号、产品编号和罕见术语有优势。两者互补，但不是“一个懂语义一个完全不懂语义”的绝对二分。文档与查询处理、模型训练和分词都会影响结果。

在你内网，两条路线分别使用查询向量和查询文本，限定相同的允许空间及版本范围；返回统一 Chunk/向量身份，再融合。不能 Dense 查全库而 BM25 只查选定空间，然后寄希望于后面过滤救回质量。最终仍需 PG 回源防止旧或无效来源。

**追问：缺一条路线还能回答吗？回答：** 按业务策略降级并记录，不假装混合成功。产品编码类问题失去词法路线可能风险高；普通语义问题 Dense 仍可用。降级后不能沿用双路分布设定的置信阈值而不评测，更不能因超时解除权限过滤。

## Q37｜进阶：写出 RRF 公式，现场算一遍。

**回答：** 加权 RRF 对文档 d 的分数是 `Σ w_i / (k + rank_i(d))`，只在 d 出现的列表上求和。rank 从 1 开始，k 是排名平滑常数，不是 topK；w 是路线权重。它解决不同路线原始分数量纲难比较的问题，但丢弃了原始分数差距信息。

以下为教学数据，k=60、两路权重均为 1，候选去重后排名如下：

| 候选 | Dense 排名 | BM25 排名 | 计算 | 融合分 |
| --- | --- | --- | --- | --- |
| A | 1 | 未出现 | 1/61 | 0.016393 |
| B | 2 | 1 | 1/62 + 1/61 | 0.032522 |
| C | 3 | 2 | 1/63 + 1/62 | 0.032002 |
| D | 未出现 | 3 | 1/63 | 0.015873 |

最终 B、C、A、D。这里共同被两路支持的 B 超过 Dense 第一的 A；这不是证明 B 一定正确，只是候选优先级。项目 weighted-rrf.ts 做路线内去重，并用稳定 ID 打破最终平分。微软的混合搜索也公开使用 RRF 融合这一思路。[官方说明](https://learn.microsoft.com/azure/search/hybrid-search-ranking)

**追问：分数 0.032 就是 3.2% 置信度？回答：** 不是，它只是排序分。列表数增加、权重改变、查询扩展都会影响数值上界；不能把固定 RRF 分直接当是否能回答的概率阈值。

## Q38｜资深：RRF、加权分数融合、直接取交集，怎么选？

**回答：** RRF 是良好的起点，不需要对 cosine 和 BM25 分数校准。若有足够带标注的数据，可以把路线分数归一化/校准后做加权融合，甚至学习排序，但要防分布漂移和过拟合。取交集可能提高某些样本精度，却会丢掉仅语义或仅精确词命中的重要证据，不适合作为普遍召回策略。

RRF 也有代价：Dense 第一大幅领先第二的优势被弱化；多条高度相似改写会重复给同一段投票。当前实现可以累加多个列表贡献，但诊断里的首个 denseRank/sparseRank 不代表保留了每个子查询完整排名。全面审计应关联各子查询路线，而不是只看汇总字段。

**追问：怎么调 Dense/BM25 权重？回答：** 按问题类别做分层验证：编码、制度短句、口语改写、跨语言等，固定候选预算比较。不要只为演示失败的一道题调到最好。若在 Milvus 端已融合又在应用端再次融合，需明确语义，避免重复计算同一投票。

## Q39｜资深：召回 topK、融合候选数、rerank topN、最终上下文条数一样吗？

**回答：** 不一样。每路线 topK 决定召回池，融合候选数决定多少候选进入更昂贵的精排，rerank topN 决定精排后保留多少，最后还受子问题覆盖、去重和上下文 Token 预算限制。早早把候选裁成最终 10 条，可能让 Reranker 根本看不到正确答案。

项目优化记录包含“检索交付 15 个候选，精排后取 10”的回归示例，这是测试配置，不是内网最优值。候选数应由 Recall-延迟曲线决定，同时观察正确目标在哪一层掉出。跨多个空间和子问题时，请求数还会乘起来，需要全局并发上限。

**追问：干脆取 1000 条？回答：** 会增加检索传输、PG 回源、精排模型和上下文成本，并可能稀释相关性。先定位漏召回原因：如果正文根本没入库，加 topK 毫无意义；如果 ANN 漏掉再调搜索参数；如果融合截断才调候选预算。

## Q40｜进阶：最终应该 BGE Reranker 精排，还是 LLM 精排？

**回答：** 专用 Reranker 对问题和候选联合打相关性分，适合对一个受限候选池做较稳定、可批量的精排。LLM 精排可以综合多个条件或证据，但有额外 Token/延迟、列表顺序偏差和结构化输出失败风险。不是模型参数越大就越适合每次排序。

项目已有专用 Reranker，另有可选 LLM Evidence Rerank；后者不是替代所有精排的必经步骤。普通问题先用专用模型，复杂歧义证据再按预算尝试 LLM，或者关闭该可选环节。ANSWER_LLM_EVIDENCE_RERANK_ENABLED 与语义 Judge 是两回事，不应该绑定开启。

**追问：Reranker 分数能直接用于拒答吗？回答：** 不同模型分数可能是 logit、归一化值或自定义分，不能统一解释为概率。应按模型版本与业务标注校准阈值，结合覆盖、适用条件和来源有效性判断。模型返回顺序/索引也需验证，否则会把某段分数错贴到另一段。

## Q41｜资深：精排最高的是正确主题，却是错误地区或旧制度，怎么办？

**回答：** 相关性不等于适用性。用户问上海，北京住宿制度可能也高度相关；新发布日期也不一定代表当前生效。应保留地区、职级、时间等条件，使用可信元数据收窄并在证据阶段核对适用范围。模型抽出的元数据如未审核，不宜直接作为排除所有候选的硬条件。

处理冲突时区分已废止/未生效、特定人群例外、不同组织制度和真正矛盾。召回多个版本可以用于解释历史变化，但当前答案要明确基准时间。不能靠标题含“最新”就自动盖过其他正式文件。

**追问：没有结构化地区字段呢？回答：** 先在原文证据里核对，必要时扩大父章节或查定义部分；缺条件就澄清。长期可新增来源可追溯的元数据抽取与审核，但须评估误标造成的 Recall 损失，不能把一次模型猜测变成永久过滤规则。

## Q42｜压轴：原文有答案，系统仍说证据不足，完整诊断怎么做？

**回答：** 固定 runId、身份、知识版本和问题，再依次检查：①源内容和 Chunk 是否存在；②Dense/BM25 各自是否命中；③RRF 后是否保留；④PG 是否因权限/版本剔除；⑤Reranker 是否降序或阈值误杀；⑥父块/表头扩展是否补齐；⑦上下文是否被 Token/每文档限额截掉；⑧证据路由和最终校验哪个原因拒绝。

记录各层候选 ID 和安全原因码，不能仅看最后一条模型日志。如果证据在 Context 中且支持结论，却被 Judge 拒绝，检查 Judge 提示、版本与样本；如果关键例外没进 Context，则是组装问题，不应先关掉所有校验。

**追问：客户催着要结果，能先去掉阈值吗？回答：** 可以对独立的可选昂贵校验按已批准策略降级，但不能跳过权限和引用有效性。先做小范围对照，观察误拒答和无依据回答的共同变化；保留回滚开关与原失败样本，比“全开或全关”更可控。
