# 02｜离线解析、切分与表格（Q09–Q20）

[返回目录](README.md) · [离线流程图](diagrams/offline.html)。本章解析事实对应 document-parser-core、parser-core、contracts/document-parsing 和 chunking。

## Q09｜基础：为什么先解析成 DocumentBlock，不直接把文件切成字符串？

**回答：** Block 表达“原文是什么、在哪里”，Chunk 表达“为了检索怎样组织”。同一段原文可以在不同策略下组成不同 Chunk，但原文位置不应因此丢失。直接扁平化字符串会丢掉表格、标题层级、图片位置、页码和来源方法，后面再追溯几乎是在猜。

项目 Block 除 text/originalText，还有类型、ordinal、pageNo/sheetName/slideNo、可空 bbox、表格二维结构、parserRevision、ocrRevision、documentVersionId、contentRevision 和 Hash。originalText 保留原事实，标准化 text 用于处理。这个层让更换 Parser 和更换 Chunk 策略解耦，也支持质量审核定位问题。

**追问：是不是信息越多越好？回答：** 不是。字段必须有可靠来源；DOCX 没有固定物理分页时 pageNo 应未知，纯文本 OCR 不能捏造 bbox。增加字段要定义单位、坐标原点、空值语义和版本兼容。统一模型不是强迫所有格式提供同样丰富的数据，而是表达能力与不确定性。

## Q10｜基础：各种格式到底怎么切？给一个明确策略表。

**回答：** 先按格式提取结构，再按结构分组，最后以 Token 上限兜底，不是“一刀 500 字”。下表区分已存在的边界和能力局限。

| 格式/内容 | 当前组织方式 | 必须注意 |
| --- | --- | --- |
| DOCX/HTML/Markdown | 标题路径、段落、列表、表格、代码块 | 嵌套结构不能重复抽取；DOCX 页码不伪造 |
| PDF | 阅读顺序、标题推断、装饰过滤、表格及按需 OCR | 多栏、脚注、扫描表格仍可能不可靠 |
| XLSX/CSV | Sheet/区域、结构化表格、表头与行组 | 格式化数值、公式缓存、合并单元格、超宽行 |
| PPTX | 幻灯片与图文结构，保留 slideNo | 不把文件名数字当真实页序 |
| 制度/FAQ/代码 | 条款边界、问答组、代码块优先原子化 | 超长单元仍需兜底拆分，不能声称 AST 级切分 |
| 图片/TXT | OCR 或文本段落，再做结构与预算处理 | 图片无结构响应时只知道文本，TXT 编码需检测 |

**追问：每种格式独立 Chunker 会不会太乱？回答：** Parser 负责格式差异，结构恢复把它们映射成有限内容类型，Chunker 按内容类型选策略。类型策略不同于为每个文件扩展名复制一整套流程。遇到不支持的复杂结构返回 Issue 或人工审核，而不是静默拼接后宣称成功。

## Q11｜进阶：PDF 双栏、跨页段落和页眉页脚怎样处理？

**回答：** PDF 往往是绘制指令，不天然是段落树。要从带位置的文本项恢复行、栏和阅读顺序，结合字体大小、目录等线索推断标题，识别重复页眉页脚。项目代码中有定位 TextItem、栏信息、标题推断和装饰识别，并对近似表格顺序产生 warning。

跨页文本不能只按页号直接粘合：检查前后章节、句子是否完整、是否切到另一个栏或表格。当前结构链允许在共同边界下组织连续段，但不能承诺任意 PDF 的语义续接都正确。跨页表格尤其要核对列数、表头、单位和表注，不是看相邻就合并。

**追问：恢复错了怎么办？回答：** 先做最小样本：保存原页、解析 Block 顺序和 bbox，区分坐标转换、栏排序还是表格识别问题。规则无法稳定覆盖时接版面模型/专用 Parser，并用同一 Block 契约返回。扫描件选 OCR，原生清晰文本优先原生解析；所有文档强制 OCR 会增加成本并可能损坏本来正确的数字。

## Q12｜进阶：PaddleOCR 只返回纯文本，你怎么保证质量？

**回答：** 首先不作错误承诺。纯文本可以恢复可搜索文字，但不能证明行列关系、阅读顺序、单元格坐标或置信度。项目 Adapter 将文本映射到真实请求目标，bbox/confidence 留空并给出结构能力告警，不生成虚构坐标。混合 PDF 中原生文字和 OCR 应按目标/区域合并，避免整页覆盖或重复。

高风险资料，如金额表、盖章日期、流程箭头，仅靠 OCR 字符串不够。可保留原图供审核，把疑似结构丢失内容降为人工审核，或者要求 OCR 服务升级结构化输出。unknown 不是 0 分，更不是 100% 正确；指标要把有置信度覆盖率和平均值分开。

**追问：原文金额 800 识别成 300，LLM 能修好吗？回答：** 不应靠语言模型猜数字。应该回到图像核验、结构化 OCR 或人工确认，并保留修订记录。后续答案校验只能检查“答案与错误 OCR 一致”，无法凭空发现原图真值，因此质量门禁必须前移。

## Q13｜进阶：你有没有表格序列化？具体怎么做，不要只说转 Markdown。

**回答：** 有。Block 保留 rows、headerRowCount、mergedCells；Chunk 构建先取表头，再按 Token 预算累积数据行，分组后重复表头。当前 renderTableRow 是将单元格用 ` | ` 连接，不等于完整 Markdown 表语法，也不是自动的“字段名=字段值”语义转换。标题路径再进入 embeddingText。

例如合成表：`城市 | 职级 | 上限（元/晚）`，下一行 `上海 | P6 | 800`。即便拆为多个行组，每组应能看出 800 对应哪个城市、职级和单位。原始 rows 用于结构事实，展示文本用于阅读，embeddingText 用于检索，三者不能相互冒充。

**追问：数字多的表这样就够了？回答：** 不一定。可评估额外生成“上海，P6，住宿上限 800 元/晚”的检索表示，但必须由原单元格确定性映射，不能补造含义；原文展示不被改写覆盖。比较行组文本和键值序列化的召回/精排效果，兼顾索引体积和多级表头，不应无条件多索引一份。

## Q14｜资深：合并单元格、多级表头、跨页表格、超宽单行分别怎么办？

**回答：** 合并单元格先保留起始坐标和 rowSpan/colSpan，必要时在检索表示中向下传播明确的分组标签，但保留“传播值”与原始空单元格的区别。多级表头可规范成列路径，如“国内差旅/住宿/上限”，同时保留脚注和单位。跨页表只在表头兼容、版面连续、业务范围一致时合并。

超宽单行不是简单调大 Chunk。可以按列主题切分但每段重复行主键和关键维度，或转结构化查询；长备注单独子块并回链。当前项目对超限单行存在 Token 兜底切分，不能保证每段都保持完整行语义；mergedCells 被保留也不等于合并语义已全部重建。这是明确的后续优化点。

**追问：怎么证明没切坏？回答：** 合成表测试要覆盖二级表头、空列、单位变化、跨页重复标题、某格含分隔符，以及恰好超过预算的行。断言不仅看快照，还看主键/表头/单位/异常条款是否跟数据共同出现；无法保证时必须告警或审核，不能以“没有报错”作为保真验收。

## Q15｜资深：Excel 公式、日期、百分比、多个表区域和隐藏信息怎么处理？

**回答：** 区分单元格存储值、格式化显示值和公式。例如 0.15 可能显示 15%，日期可能是序号；直接字符串化底层数值会改变业务含义。当前 XLSX Parser 保留公式事实与缓存结果状态，缺少缓存结果会产生告警，不在服务端随便执行 Excel 公式。

工作表不一定是一张连续表。空行分隔、标题和不同列结构可能意味着多个区域；项目有区域提取及源位置事实。对于隐藏 Sheet/列、批注和外链，应制定显式采集政策：隐藏不等于无权限，也不等于必须摄入；对不支持内容要记录，而不是假定已完整解析。

**追问：用户问全年总支出能直接 RAG 求和吗？回答：** TopK 召回不是完整扫描，可能遗漏行或重复计入父子块。精确汇总应使用受控结构化表/数据库查询，固定筛选条件、单位、去重主键和统计截止时间。RAG 适合解释口径和引用规则，SQL/API 负责全量计算，两类证据要分别返回。

## Q16｜进阶：Chunk 多大、overlap 多大？有标准答案吗？

**回答：** 没有脱离资料和问题的万能参数。小块定位精确但容易丢条件，大块信息完整但会稀释向量、增加噪声和 Token。先以结构单元为边界，用模型输入上限和下游上下文预算约束，再通过真实查询集比较几组大小，而不是从博客抄一个数字。

Overlap 适合在连续长文本硬切时保住边界，不适合所有表格、独立 FAQ 都重复一遍。代价包括向量数上升、重复命中、上下文浪费与引用重复。项目在类型策略后使用 Token 兜底，并保存 splitReason；超限不是静默截断。

**追问：更换 BGE 后 Chunk 限制还是准确的吗？回答：** 当前本地 cl100k_base 是真实 BPE，但不是 BGE/GLM 的精确 tokenizer。要接模型 tokenizer 或使用实测保守裕量，并在 Provider 校验长度。字符数、cl100k token 数和模型 token 数不能混称；标题拼接后的最终输入还要重新计数。

## Q17｜资深：父子块和相邻块有什么区别？为什么不一开始检索大块？

**回答：** 子块用于找准具体证据，父块提供章节上下文，相邻块用于补局部承接关系。典型情况是“住宿上限 800”命中子块，而适用地区、职级或特殊批准条件在前后段。项目建立 PARENT_CHILD、邻接、TABLE_HEADER、来源和脚注等关系，后续可受控扩展。

一开始只用大块做向量检索可能让某条短规则淹没在长章节中；只用小块生成又容易遗漏例外。因此检索粒度和生成粒度不必相同。但父块不能无条件整个放入：要去掉重复子段，限制总预算，避免跨不相关章节扩展。

**追问：多子块命中同父块怎么办？回答：** 按父块 ID/内容版本去重，保留每个子问题的直接证据，然后只补新增上下文。既要避免同一文档占满，也不能用“每文档只留一块”丢掉三个不同事项的证据。扩展后还需重新检查当前权限、版本和 Token 预算。

## Q18｜资深：语义切分、Contextual Retrieval、Late Chunking 何时使用？

**回答：** 结构切分优先用于标题、条款、表头明确的资料，便宜且易解释。语义切分根据段间语义变化选择边界，适合弱结构文本，但需额外模型计算，阈值受领域影响，仍要处理上下限和引用位置。当前项目不能声称已经实现通用语义切分。

Contextual Retrieval 是给片段补充与其对应的文档上下文后再建检索表示；项目已有标题路径，不等于已经做了 LLM 上下文补写。Anthropic 的公开方法可以作为候选，但补写内容必须和原文事实分开，错误上下文会同时污染词法和向量路线，不能照搬其实验收益。[公开方法](https://www.anthropic.com/engineering/contextual-retrieval)

**追问：Late Chunking 呢？回答：** 它通常先让长文本通过支持的模型获得上下文相关 token 表示，再按边界池化，要求模型/服务暴露合适的 token 级表示；普通只返回一条句向量的 HTTP 接口不能直接做到。评估时把它当替代检索表示方案，比较上下文收益、长文截断和重建成本，不说成当前现成功能。[原论文](https://arxiv.org/abs/2409.04701)

## Q19｜进阶：切分完如何判定能发布？

**回答：** 项目不是非空即通过。质量规则检查文本覆盖、乱码、缺页、标题结构、OCR 可用事实、表格结构、重复比例、负责人和 revision 一致性，输出 PASS、MANUAL_REVIEW 或 REJECT。缺 owner 或内容版本冲突属于业务硬门禁，不能由模型说“质量不错”覆盖。

规则也有限：高非空率不代表阅读顺序正确；置信度未知不能当高分；一页只有装饰文字可能掩盖正文缺失。门禁要结合格式样本和业务风险，而不是把一个全局平均分当质量。解析警告应能定位 parseRun、页或 Block，支持人工判断。

**追问：阈值调松是不是就不拒答了？回答：** 会让更多错误知识进入索引，最终可能从“拒答”变成“有依据地说错”。先看误阻断样本，按错误类型调整规则或 Parser；将改变前后的误放行率和误审核率一起记录。不同风险空间可有不同 policy，变更必须有版本。

## Q20｜压轴：客户说“这个文件有答案，但系统没有”，先查哪里？

**回答：** 先拿问题、正确文档版本和允许访问的用户身份，不让客户把敏感正文贴日志。沿离线链查：原文件内容是否确实存在 → 对应页/单元格是否进入 Block → 是否被当页脚/重复内容剔除 → Chunk 是否保留条件 → 审核是否通过 → 该版本是否进入已发布 Manifest。到此之后才查召回。

如果 Block 中已丢内容，调 topK 没用；如果 Chunk 断开金额和单位，应修切分而不是反复改 Prompt；如果候选索引写完但未发布，应查任务和 Head；如果用户无权，不应通过扩大搜索绕过权限。每步保留最小复现和明确失败原因。

**追问：如何做回归？回答：** 使用可分享的合成文件复现同样版面结构，断言目标原句、数值、表头和定位都保留；再加从提问到引用的端到端样本。修 Parser 要升级修订并重新处理受影响资料，不能假定历史向量会自动变好。
