# 08｜企业场景压轴与模拟面试（Q67–Q72）

[返回目录](README.md)。下面是面试官要求你在新业务约束下现场设计的题，属于方案能力，不应冒充当前上线经历。

## Q67｜场景：上万份扫描合同，表格多、章印遮挡，领导要求“不能漏任何违约条款”。你怎么承诺？

**回答：** 我不会承诺 TopK RAG 能证明全库无遗漏。先把业务分成“找某份合同的某条款”与“审查全部合同是否存在条款”。前者可检索，后者需要全量受控扫描/抽取、处理覆盖审计和人工复核。系统必须知道哪些页失败或不确定，而不是仅展示成功找出的结果。

扫描合同需要版面/OCR 质量验证，遮挡和手写进入人工队列，保留原页证据与抽取位置；条款切分保留定义、例外和附件关联。抽取结果形成结构化任务记录，逐文档标注已处理页数、缺失页、低质量区域和审核状态。高风险“没有违约条款”只有在约定覆盖条件成立时才可给出。

**连续追问：为什么不用更强的多模态模型全看？回答：** 可作为受控抽取/复核候选，但仍有漏读、幻觉、成本和吞吐问题。要用标注扫描样本比较 OCR+结构解析与视觉模型，错误率按页/条款分开；不能因为模型能看图就取消覆盖审计。当前纯文本 OCR 接口不足以证明复杂合同结构保真，需要能力升级或明确人工流程。

**验收思路：** 准备遮挡、歪斜、跨页条款、附件引用、多级表头样本；测条款级召回、错提取、定位正确和必须人审的识别率。向业务明确剩余风险，不以“答案有引用”替代法律审核。

## Q68｜场景：员工问“按报销制度，我上周申请为什么还没到账？”

**回答：** 这是制度知识和实时业务状态的组合。制度 RAG 找支付时限、审批条件和例外；受控报销 API 用用户身份查询申请状态、提交/审批时间、付款批次等。先确定具体申请，不能在多个申请之间猜一个。最终把“制度规定”和“系统当前状态”分开说明，并带获取时间。

业务 API 需按 userId 的授权校验申请归属，而不是相信模型传来的员工 ID。所有工具只读、参数 Schema 验证、超时有分类；API 故障时可以解释一般流程，但必须说无法确认个人申请状态。不能从知识库旧导出表或模型记忆里编造实时进度。

**连续追问：那让模型直接生成 SQL 呢？回答：** 优先选已经封装好的只读业务接口。若确实做 NL2SQL，要限制数据库角色、表列白名单、行级权限、查询预算、参数化和结果脱敏；AST 校验不能替代数据库权限。涉及付款、审批等写操作需要独立确认与授权流程，不应塞进第一版 RAG。

**验收思路：** 测多申请澄清、跨员工越权、状态更新、API 超时、制度失效和日期口径。该能力当前未实现，应作为新模块接入，不把传统 routeQuery 说成已经能完成。

## Q69｜场景：系统扩展到多个子公司、跨语言和不同地区法规，你如何演进？

**回答：** 首先确定隔离和数据归属，不先换向量库。当前是单企业 userId+roles 模型，不应直接宣称满足多租户隔离。需要组织/租户作用域、来源责任、细粒度 ACL、区域存储与保留策略，以及每次检索和工具调用都不可绕过的服务端范围。

跨语言检索要用真实语言对评测模型；必要时增加查询翻译/术语词典，但原查询、翻译和原文引用都保留。法规则按地域、主体和生效期约束，禁止用总部新制度盖过当地特殊规则。统一概念可以帮助导航，事实适用性不能被统一摘要抹平。

**连续追问：每个子公司一个 Collection 最安全吗？回答：** 物理隔离能减少某些误配置影响，但带来数量、容量和迁移成本；逻辑隔离必须有完备 ACL 和测试。选择依据风险、运维和规模，不能把分 Collection 当万能权限方案。多租户改造是显著范围变更，不只是新增一个 tenantId 字段。

**验收思路：** 用跨组织同名文档、不同适用期、多语言术语和撤权样本验证。测试统计数量、引用标题、缓存和导出也不泄漏，不能只测最终正文。

## Q70｜场景：要加 Agentic RAG，如何证明不是增加几个模型调用？

**回答：** 先明确新增能力是“根据当前证据缺口选择下一步”，而不是把固定两轮改成固定五轮。Auto 简单题使用原快路径；复杂题形成待回答事项、覆盖表和有限动作集：补查某个缺口、指定文档检索、补上下文、核对适用元数据或询问用户。每个动作都有真实结果和停止条件。

当前计划规定单开关、沿用总超时、复杂题最多额外三次决策模型调用，并共享工具/检索预算，不能让 Agent 循环乘以旧图补检索。生成仍回原引用与规则门禁；Agent 不能根据文档指令绕过身份，也不能擅自联网。微软公开的 agentic retrieval 同样包含查询规划、多查询检索和结果合成，但这只是对照，不证明我们已经实现。[官方概览](https://learn.microsoft.com/azure/search/agentic-retrieval-overview)

**连续追问：三次机会用完仍没答案？回答：** 按证据输出部分答案、澄清或明确不足，不无界重试。去重指纹防止同一问题反复查；必须保留生成时间预算。复杂题完整性、错误路由率、每题动作次数、简单题延迟退化是验收重点，不用“有 Agent 节点”作为成功标准。

**验收思路：** 同预算对比原 RAG 与 Auto；选择一个必须先确认地区再查标准的依赖题，以及一个不该调用规划的简单精确题。Agentic 当前仍是计划，不伪造上线收益。

## Q71｜场景：你为什么暂不先做 LLM Wiki 或 GraphRAG？何时会值得？

**回答：** 当前首要痛点是问答正确性和延迟，先确认检索/证据链的短板。LLM Wiki 更适合把稳定资料编译成主题页面、指南和导航，适用于入职学习或反复跨文档整理；GraphRAG 类方案适用于关系探索、跨实体连接或某些全局归纳任务，但引入额外索引、抽取和更新成本。它们不是“更高级所以必上”。

Wiki 页面是派生知识，不能自动升格成权威事实。来源更新、删除、撤权时相关派生内容需要失效或重编译；多个来源合并后权限应更谨慎，不能把多个部门都不能完整访问的信息拼成公共摘要。用户已有人工 Wiki 可以先作为原始来源接入，与 LLM 自动编译是两回事。

**连续追问：能帮问答提速吗？回答：** 对重复主题预整理可能减少部分在线工作，但多一个检索步骤也可能更慢。让 Wiki 提供资料线索，再回原文核验重要事实，同时保留直接检索。用同批问题证明覆盖/成本收益。GraphRAG 和 LangGraph 中的“图”不是同一个概念，后者是执行流程图。

**验收思路：** 先选权限一致、资料稳定的一个空间，比较主题浏览和跨文档题，不以单条金额查询证明 Wiki 价值。原始检索可用不能等待 Wiki 编译成功。

## Q72｜综合压轴：演示时“来源错、证据不足、等待很久”同时发生，你作为负责人如何处理？

**回答：** 先按影响止血：若疑似越权，停止受影响功能并保存脱敏审计；若只是质量/延迟，限制新复杂路径、保留原稳定链路和取消入口。获取一个确定 runId、正确来源版本、用户权限和时间，避免在现场不停改多个参数让证据丢失。

然后分三条调查，不能合并成“模型不好”：

1. **来源错**：核对 vectorId→chunkId→documentVersion 的映射、Manifest 成员、PG 回源、同名文件和引用绑定。如果身份映射错，先修代码/数据，换模型无效。
2. **证据不足**：看目标内容最早在哪层消失；检查解析、发布、双路召回、融合、精排、上下文和 Judge，定位误拒答还是资料真的不够。
3. **等待久**：查看排队/模型/检索阶段时长、重复查询、额外 LLM 精排和 Judge、超时重试链及上传是否争抢资源。

**连续追问：怎样给领导解释和后续验收？回答：** 用可验证的三句话：目前影响哪些问题、已确认哪层原因、什么时候给哪种验证结果。不要把假设说成根因。形成最小失败样本、修复记录、同题前后对比和并发回归；实际收益没有测完就明确待验证。最终整理成事故复盘和回归集，而不只是把演示题写入特殊规则。

## 90 分钟模拟面试安排

| 时间 | 面试官任务 | 高分信号 |
| --- | --- | --- |
| 0–10 分钟 | Q01、Q08：讲业务与三个真实难点 | 有边界、有代码证据，不虚构量化成果 |
| 10–30 分钟 | Q09、Q13、Q14、Q20：拿一张复杂表追切分 | 能区分原文事实、检索表示、失真与审核 |
| 30–45 分钟 | Q25、Q28、Q30：索引和发布 | 不混淆 BM25/Sparse；说清 CAS/rebase |
| 45–60 分钟 | Q32、Q37、Q40、Q42：检索实战 | 会手算、知道候选在哪里丢失 |
| 60–75 分钟 | Q51、Q55、Q60、Q61：生产与评测 | 讲清分母、版本粒度、取消与权限 |
| 75–90 分钟 | 随机选 Q67–Q72 | 能根据新约束改变方案，不盲目复用当前架构 |

## 五个必须自己完成的练习（只在隔离测试空间）

1. 构造多级表头和超宽单行，查看 Block、Chunk 和 embeddingText，判断丢失什么。
2. 用 Q37 的四条候选手算 RRF，再修改路线权重，解释排序如何变化。
3. 构造两份并发发布文档，确认最终 Head 包含两者，并理解 rebase 日志。
4. 构造当前制度/旧制度/不同地区三份近似资料，追踪哪个阶段消除不适用证据。
5. 关闭一个可选模型校验，在同样本上同时记录延迟、误拒答和错误放行，不只看“变快”。

以上是教学实验建议，本轮没有替你运行故障注入、生产压测或内网业务评测。
