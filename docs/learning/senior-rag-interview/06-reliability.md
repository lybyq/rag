# 06｜可回溯性、异步可靠性和性能（Q51–Q58）

[返回目录](README.md) · [回溯图](diagrams/trace.html)。

## Q51｜基础：你说可回溯，每个环节具体查什么？

**回答：** 对一次提问，从 runId 查身份/允许范围、配置快照、Manifest、节点起止、模型版本、召回路线、候选及剔除原因，再查最终证据包和引用。离线从 chunkId 回到 source block、parseRun、documentVersion、contentRevision 与原始文件 Hash。Trace ID 连接调用，业务 ID 连接持久化事实，二者作用不同。

建议诊断时列出一行阶段事实：阶段、输入 ID/Hash、输出 ID/数量、耗时、失败码、预算、版本。不要把完整问题、证据、密钥和预签名 URL 写进普通日志。确需保存正文用于复盘，使用受控敏感存储、权限和保留期限。

**追问：用了 OpenTelemetry 就都有了吗？回答：** 没有。OTel 的 Trace/Span 提供调用因果和时间结构，跨进程需要正确传播上下文；业务版本、Chunk 关系、候选快照仍需项目设计。[OTel Traces](https://opentelemetry.io/docs/concepts/signals/traces/) 本项目已有运行审计不等于已经在每个外部系统完成端到端 OTel 接入，部署覆盖需实测。

## Q52｜资深：为什么 BullMQ 不能保证你的任务只执行一次？

**回答：** Worker 拿到任务后可能调用远端成功，却在确认完成前崩溃；恢复后队列不知道副作用是否成功，只能重试。事件循环长时间阻塞还可能导致锁续期失败，任务被重新处理。因此设计应允许重复投递，用幂等执行保证最终业务结果，而不是宣称 exactly-once。[BullMQ stalled 机制](https://docs.bullmq.io/guide/jobs/stalled)

项目把解析独立服务化、任务事实放 PG，用状态/版本/幂等键限制副作用。索引向量身份应稳定，重复写不能产生一堆新业务记录；一个任务每阶段是否完成可查询。队列里的 jobId 去重不是永久业务幂等，任务清理或不同入口可能绕过它。

**追问：CPU 密集 Parser 放在同进程有什么坏处？回答：** 会阻塞 Node 事件循环，影响 HTTP 响应、心跳和取消。可用独立服务/进程、资源限制和任务预算；不要通过无限延长锁超时掩盖根因。锁时间调整必须与最长正常工作及失败恢复目标一起评估。

## Q53｜资深：Outbox、幂等键、乐观锁分别解决什么？

**回答：** Outbox 解决“PG 状态提交了但消息没发”的双写裂缝：同一事务保存业务事实和待发送事件，发布器再投递，允许重复。幂等键解决同一业务请求重放，需绑定规范化请求 Hash；相同 key 不同参数不能直接复用旧结果。乐观锁/CAS 解决并发写入基于旧状态覆盖新状态。

它们不能互相替代。Outbox 投递仍可能重复，需要消费者去重；幂等请求也可能与另一个合法请求竞争空间 Head，需要 CAS；CAS 失败还需要重试/重建策略。[BullMQ 幂等建议](https://docs.bullmq.io/patterns/idempotent-jobs) 是同样的基本思想：重试不改变最终业务含义。

**追问：怎么定义外部批量导入幂等？回答：** 批次 key 对应同一批请求，clientFileId 对应批内单文件，长期来源身份用 externalSourceId+externalDocumentId，内容 Hash 决定复用旧版本还是生成新版本。这四个概念混用会造成重复文档或把更新误判为重试。

## Q54｜进阶：你有两套 Redis，分别怎么规划？Redis 丢了怎么办？

**回答：** 两套 Redis 的实际职责先看配置，不能仅因有两个地址就声称已实现高可用。推荐队列/可靠事件与可丢缓存隔离，因为队列不能接受缓存随意淘汰策略；AOF、复制和内存策略按运维约束确定。Redis 副本不等于备份，队列延迟和持久化也需监控。

项目应以 PG 状态和 Outbox 对账恢复未完成任务，缓存丢失主要影响性能，队列丢失需要重新投递而不是重做已经完成的副作用。SSE 事件有序号与恢复通道，浏览器断线不能被解释成 Run 必须重新开始。

**追问：消息顺序怎么办？回答：** 区分全局顺序和单任务顺序。多数场景只需同一 Run/Job 的单调序号、状态合法迁移及重复忽略；不同任务之间没有必要全局串行。重放时客户端用游标补缺，后端避免把旧状态事件覆盖新终态，并重新处理撤权后的可见信息。

## Q55｜资深：用户点取消，模型请求真的停了吗？

**回答：** 取消有三个层次：业务不再接受结果、应用不再发起后续操作、远端计算实际停止。AbortSignal 可中止本地等待/连接，但第三方服务可能继续计算；不能把浏览器关闭页面当作已停止 GPU。项目应取消 Run、传播 signal、拒绝迟到结果，并记录终态。

总 Deadline 贯穿整个调用链，单次 timeout 是其中一个限制。检索、重排、生成和修复都要用剩余时间，不能每一步重新获得完整 60 秒。用户取消和权限拒绝不是可重试 Provider 故障，不能在 catch 中又发一次兜底调用。

**追问：Worker 换主后旧 Worker 返回呢？回答：** 提交时检查租约持有人或 fencing 身份以及乐观版本，旧执行器不能覆盖新结果。读操作可有界重放，但完成事务/事件需幂等。恢复策略必须说明是从哪个持久化状态继续，不能只说框架支持 checkpoint 就认为全自动可靠。

## Q56｜资深：回答慢，你怎么找瓶颈并优化？

**回答：** 先拆端到端延迟：排队、路由/改写、Embedding、Dense/BM25、PG 回源、精排、扩展、生成、语义校验、最终发布。分别看 P50/P95、并发、输入输出 Token、失败/重试以及冷启动，不能只观察一个示例秒数。并行分支耗时近似由最慢分支决定，不应直接把所有 Span 求和。

项目已有查询向量缓存、有界召回并发、跳过无变化第二轮、合理候选池、可选 LLM 精排/语义校验预算和槽位调度优化。下一步看真实模型 prefill/decode、长上下文、排队和资源争抢。增加 Worker 可能只把堵塞从应用队列挪到 vLLM。

**追问：优先关哪个开关？回答：** 依据分阶段数据和同题对比。若大量耗时来自可选 LLM Evidence Rerank，先评估是否只对歧义题启用；Semantic Judge 类似。专用 BGE Reranker、引用权限校验与 LLM 校验不是一回事。关闭后必须同时测误拒答和错误放行，不用主观“看起来快了”验收。

## Q57｜资深：怎么避免多用户查询或大批上传把系统拖垮？

**回答：** 每个依赖都需要容量边界：解析进程数、OCR 并发、Embedding 批次与在途请求、Milvus 请求数、PG 连接池、在线生成槽位。只在最外面限制 HTTP 并发不够，一个请求可能拆成多个查询×空间×路线。项目已经对召回扇出做有限并发，但端到端容量仍需测。

排队应有最大长度/等待时长和可见状态，超负载时明确拒绝或降级，避免所有请求都卡到超时。在线与离线竞争模型时要设置独立额度或调度优先级，重要业务也应防单用户长期占满。使用大文件“恶意样本”压资源边界，不能只压短文本。

**追问：QPS 目标怎么确定？回答：** 先从活跃用户、峰值比例、思考间隔和平均请求时长建立估计，再以负载测试校准。Little 定律可用 L≈λW 估算稳态在途量，但不替代峰值、长尾和 GPU 调度实测；不要把固定并发测试结果直接当开放到达率容量。

## Q58｜压轴：外网能跑，带内网只改 env 就一定能跑吗？

**回答：** 只有在镜像/依赖完整、CPU 架构兼容、数据库迁移匹配、证书 DNS 可用、模型协议已验证、挂载目录与权限正确的前提下，env 才是环境切换手段。不是一个配置文件就能弥补缺少模型 tokenizer、OS 库、图片字体或错误的返回结构。

部署验收分层：容器启动 → 依赖连接 → Schema/迁移 → Provider 契约样本 → 合成文件入库 → 发布后真实检索 → 带引用答案 → 取消/恢复/备份。准备镜像 digest、配置样例、数据库前滚与应用回滚说明，秘密值另行安全注入。

**追问：GLM 是 OpenAI-compatible，为何仍 500？回答：** 可能是返回缺字段、结构化输出不兼容、认证/证书、超时映射、模型长度或代码错误。先用脱敏最小请求确定哪一层失败，把上游 429/超时与本地 500 区分。不能把所有故障都推给“缺模型”，也不能为了调通打印完整密钥和正文。
