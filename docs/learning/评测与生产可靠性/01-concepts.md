# 评测与生产可靠性：核心原理

## 为什么不能只看“回答看起来不错”

企业 RAG 的失败可能发生在解析、切块、召回、版本、权限、引用、生成或最终校验任一层。只用一个答案分数，会把权限泄漏和少量极差样本埋在平均值里。本模块把 Case、实际事实、逐项评分、均值、方差、失败码和不可变 Baseline 分开保存。

PR 中的 `pr-selected.json` 是快速、确定性的关键回归；真实模型、Prompt、Profile、Flow 或 Manifest 变化则必须运行完整 Evaluation Run。两者互补，前者反馈快，后者防止离线 fixture 与真实链路脱节。

## 可靠性边界

- 在线 Run、用户、角色、空间都有独立限流键和并发舱壁，防止一个热点空间拖垮全体用户。
- 远程调用统一接受 Deadline、单次超时和 `AbortSignal`；只对允许的错误分类退避重试。
- 连续故障由熔断器快速失败，恢复窗口只放少量探测请求。
- 在线 Redis、离线 BullMQ Redis、数据库连接池和队列优先级分离，资源争用不再是隐式行为。
- Milvus 是可重建索引而不是事实源；PG、MinIO 和版本化配置才进入备份闭环。

## 三个常见误区

1. “有重试就可靠”：没有 Deadline 的重试会放大雪崩。
2. “有备份就能恢复”：没有摘要校验、恢复演练和固定查询验收的备份只是希望。
3. “压测脚本写完就是达标”：24～72 小时 Soak、Chaos、RPO/RTO 和容量指标必须由真实报告证明。
