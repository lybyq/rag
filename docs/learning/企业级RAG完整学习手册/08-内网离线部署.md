# 08：无网络内网切换与离线部署

## 1. 先给准确结论

满足下面条件时，业务代码无需修改，只配置 env：

- 内网 LLM 是 OpenAI-compatible `/chat/completions`。
- Embedding、Reranker、OCR 满足 [Provider HTTP 契约](../../contracts/provider-http-contracts.md)。
- Embedding metadata、维度、Dense/Sparse、Tokenizer 与配置一致。
- Milvus SDK 协议兼容 2.6.4，数据库/认证/TLS 信息明确。
- PostgreSQL、Redis、MinIO 的网络、账号、TLS 和 DNS 可用。
- 企业认证网关能可信提供 userId/roles。

如果只是 URL、Key、modelId、revision 不同，改 env；字段不同就写 Adapter/Gateway；能力缺失则调整方案并重新评测。不能用 env 把“不兼容协议”变兼容。

## 2. 两种离线概念

```text
构建离线：内网是否需要 npm/Docker Hub
运行离线：容器启动后是否访问公网
```

本项目交付的 `images.tar` 已在外网完成应用构建。内网直接 `docker load`，不需要 Node、pnpm、npm 或 Builder 镜像。运行时只连接你配置的内网 PostgreSQL、Redis、MinIO、Milvus、OCR、Embedding、Reranker 和 LLM。

若公司要求在内网从源码重建，则使用 `.offline/pnpm-store` 和 Airgap Dockerfile，这是另一条更重的供应链流程。

## 3. 离线包内容

```text
enterprise-rag-airgap-<date>/
  images.tar                  应用和基础设施运行时镜像
  SHA256SUMS.txt              文件完整性清单
  IMAGE_MANIFEST.txt          镜像 Tag、Image ID、大小
  docker-compose.airgap.yml   不含 build、不会拉公网
  images.env                  Compose 镜像标签
  runtime.env.example         运行配置模板
  load-images.ps1/.sh         校验并导入镜像
  preflight.ps1/.sh           拒绝占位符并检查 Compose
  start.ps1/.sh               启动
  status.ps1/.sh              状态和关键日志
  stop.ps1/.sh                停止但不删数据
  docs/                       Provider 契约和部署/验收说明
```

## 4. 内网操作顺序

### 4.1 核验和导入

Windows：

```powershell
.\load-images.ps1
```

Linux：

```bash
bash load-images.sh
```

脚本先校验 `images.tar` SHA-256，再 `docker load`。不要跳过校验，因为移动硬盘/跨网摆渡可能损坏文件。

### 4.2 配置

复制：

```powershell
Copy-Item runtime.env.example runtime.env
```

至少填写：

- 数据库密码和 DATABASE_URL。
- MinIO Key/Secret、浏览器和容器都能解析的 FQDN。
- 企业认证网关 Header、可信网段或签名。
- PaddleOCR URL/model/revision/protocol。
- LLM URL/key/model/revision。
- Embedding URL/model/revision/dimension/Dense+Sparse/Tokenizer。
- Reranker URL/model/revision。
- 企业 Milvus 地址、认证、TLS、database。
- Base64 编码的 32 字节 Run 内容加密密钥。

生成加密密钥的 PowerShell 示例：

```powershell
$bytes = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[Convert]::ToBase64String($bytes)
```

Linux：

```bash
openssl rand -base64 32
```

不要把真实 runtime.env 提交 Git 或放入学习材料。

### 4.3 选择 Milvus

公司已有 Milvus：

```text
MILVUS_ADDRESS=milvus.company.internal:19530
```

直接启动，不加 profile。

临时环境没有 Milvus：

```text
MILVUS_ADDRESS=milvus:19530
```

Windows：`.\start.ps1 -BundledMilvus`

Linux：`BUNDLED_MILVUS=true bash start.sh`

随包 Milvus 适合验证和中型单机起步；正式集群的副本、备份和容量由企业平台负责。

### 4.4 预检和启动

```powershell
.\preflight.ps1
.\start.ps1
.\status.ps1
```

Compose 会：启动 PG/Redis/MinIO → 执行一次 migration → 创建 MinIO Bucket → 启动 Parser、API、Worker → 启动 Web。Migration 使用 advisory lock 和 checksum。

## 5. 网络和认证的关键要求

默认只暴露 Web 8080 和 MinIO 9000/9001，后端应用仅在 Docker 网络内。生产应由企业网关访问 Web：

```text
用户 → SSO/认证网关（删除伪造 Header，注入 userId/roles）→ Web Nginx
                                                          ├→ Platform API
                                                          └→ Query API/SSE
```

仅因为“在内网”不能信任浏览器 Header。若网关无法保证隔离，启用 Header HMAC 签名或切 JWT/JWKS。

## 6. 为什么 MinIO FQDN 很重要

API 在容器内为浏览器生成预签名 URL。若 `MINIO_ENDPOINT=http://minio:9000`，容器能解析，但用户电脑通常不能；若写一个容器不认识的宿主机名，API 自己又连不上。

因此配置一个内网 DNS 名，例如 `rag-minio.company.internal`，同时：

- Docker 容器可解析并访问；
- 用户浏览器可解析并访问；
- 证书 SAN 包含该域名；
- `PARSER_ALLOWED_SOURCE_HOSTS` 包含该域名；
- CORS 只允许 Web 域名。

## 7. Provider 上线验收

配置成功启动只说明 URL 可达。上线前依次验证：

1. Health/metadata 的 modelId/revision/protocol/维度真实一致。
2. Contract 正常、超时、取消、429/5xx、Schema、版本和部分失败。
3. 合成九格式 Parser/OCR。
4. 批量 Embedding 数量、Hash、Dense/Sparse 和维度。
5. Reranker 返回全集且排名合理。
6. LLM 稳定输出 JSON、Citation ID 和拒答。
7. 真实脱敏 Golden 达质量阈值。
8. 构建全新 Manifest，不能复用 Fixture 索引。
9. k6、Soak、Chaos、备份恢复和 RPO/RTO。

## 8. 切换真实 Embedding 的特别提醒

外网 Fixture 生成的向量不能带入生产继续使用。配置内网 Embedding 后：

1. 建新的 `EMBEDDING_PROFILE_ID/revision`。
2. 确认 Query/Document 模板和维度。
3. 为所有有效文档触发 rebuild。
4. 新 Collection 对账和 Golden。
5. Canary/Promote。
6. 旧 Fixture Manifest 保留审计但不作为生产 ACTIVE。

## 9. 镜像治理

离线包使用不可变版本 Tag + `images.tar` SHA-256 + Image ID 清单，支持直接 `docker load`。正式企业流程建议导入内网 Registry 后：漏洞扫描、签名、SBOM、推送、取得 registry digest，再把 `images.env` 改为 `registry/repo@sha256:...`。

镜像归档校验保证“运输文件没变”，Registry digest/签名保证“部署引用的镜像没变”，二者解决不同环节。

## 10. 回退和数据安全

- 应用回退：恢复上一版本镜像 Tag/digest 和 env，再 Compose up。
- 配置回退：恢复上一份不可变配置；进行中的 Job/Run 保留原快照。
- 索引回退：使用 previousManifestId/历史版本，不手工切未知 Collection。
- 数据库：只前滚 Migration；破坏性变更前备份并演练恢复。
- 停止：`stop` 不删除数据。
- 严禁日常执行 `down --volumes` 或删除 `data/`，这会永久删除 PG、Redis、MinIO 和随包 Milvus 数据。

## 11. 能否“直接部署”的最终判断

离线包可以直接导入和编排，不需要网络和源码构建；但第一次生产启动前必须拿到真实内网 Endpoint、协议版本、模型元数据、凭据、DNS/证书和认证网关信息。系统故意拒绝带占位符启动，这是保护，不是部署缺陷。

换句话说：交付物已经具备“改 env 即切换”的工程条件，能否一次启动成功取决于内网 Provider 是否满足约定契约；效果能否上线仍取决于真实 Golden 和生产门禁。
