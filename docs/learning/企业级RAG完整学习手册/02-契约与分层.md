# 02：契约、Port/Adapter 与分层架构

## 1. “契约”到底是什么

大白话：契约就是两个模块合作前写下的“双方都不能猜”的约定。它不只是 TypeScript 接口，还应包含：

- 字段：叫什么、类型、是否必填、长度和取值范围。
- 语义：这个字段代表配置值还是服务实际值，时间和单位是什么。
- 版本：哪一版协议、模型、Tokenizer、模板和算法。
- 行为：是否允许部分成功、是否幂等、排序是否稳定。
- 错误：哪些可重试，哪些是输入错误，哪些是版本不兼容。
- 时限：Deadline、单次超时、取消如何传播。
- 安全：是否含正文/密钥、可否记录日志、调用方是否有权访问。

只有字段没有语义，会出现两个服务 JSON 一样但理解相反；只有 TypeScript 没有 Zod，网络收到坏数据时类型检查救不了你。

## 2. 本项目的五类契约

### 2.1 API Contract

浏览器或其他业务系统与 API 的约定。使用 Zod + OpenAPI，统一 Envelope、错误码、分页、幂等键和 Request ID。

例：创建 Run 必须携带合法 conversationId、spaceIds 和 `Idempotency-Key`；重复请求返回同一个业务结果，而不是多启动一次问答。

### 2.2 Event Contract

PG Outbox、BullMQ、Redis Stream 和 SSE 中事件的约定。核心字段包括 eventId、eventType、aggregateId、sequence、occurredAt、schemaVersion 和 payload。

事件版本为什么必要？生产者先升级、消费者后升级是常态。没有 `schemaVersion`，旧 Worker 会把新字段当成旧语义处理。

### 2.3 Provider Contract

项目与 Parser、OCR、Embedding、Reranker、LLM、Milvus 的协议。它既要校验响应形状，也要校验模型身份和 revision，避免网关悄悄切模型。

完整 HTTP 示例见 [Provider HTTP 契约](../../contracts/provider-http-contracts.md)。

### 2.4 Data Contract

PostgreSQL 表、Milvus Schema、MinIO Key 和缓存 Key 的约定。例如向量必须带 chunkId、spaceId、documentVersionId、contentHash、Manifest/Profile 信息；Milvus `VARCHAR` 按 UTF-8 字节限制，不是 JavaScript 字符数。

### 2.5 Port Contract

Application 层描述“我需要什么能力”，例如：

```ts
interface EmbeddingPort {
  embedDocuments(inputs, options): Promise<EmbeddingBatchResponse>;
  embedQueries(inputs, options): Promise<EmbeddingBatchResponse>;
}
```

它不说能力由 HTTP、SDK、Fixture 还是本地模型实现。Adapter 才负责翻译供应商协议。

## 3. Contract、Port、Adapter 各自解决什么

| 概念     | 大白话                  | 本项目例子                     | 最常见错误                   |
| -------- | ----------------------- | ------------------------------ | ---------------------------- |
| Contract | 跨边界的数据和行为约定  | `EmbeddingBatchResponseSchema` | 只写 TS 类型，不校验网络数据 |
| Port     | 业务层需要的能力插座    | `EmbeddingPort`                | Port 暴露厂商专有参数        |
| Adapter  | 把具体厂商插头转成插座  | `HttpEmbeddingAdapter`         | 在 Adapter 里决定业务策略    |
| Use Case | 按业务规则编排多个 Port | `IndexingService`              | Controller 直接调用多个 SDK  |
| Domain   | 不依赖框架的硬规则      | 授权、Run 状态机               | Domain import Nest/PG/Milvus |

换内网 Provider 时先比较契约：

1. URL 和密钥不同，但请求/响应完全一样：只改 env。
2. 字段名不同，但语义可一一映射：新增 Adapter。
3. 缺少模型 revision、部分失败或取消能力：在内网模型前加 Gateway 补齐。
4. 能力根本不同，例如只返回 Dense 而配置要求 Dense+Sparse：调整检索方案并建立新 Profile/索引，不能伪造字段。

## 4. 为什么按 contracts → domain → application → adapters → apps 分层

```text
contracts ← domain ← application ← adapters ← apps
```

- contracts 只描述可传输事实，任何进程都能复用。
- domain 放最稳定的业务不变量，不依赖 Nest、SQL、Redis、Milvus。
- application 用 Use Case 编排事务和 Port，不读取供应商专有配置。
- adapters 实现远程调用、SQL、SDK、错误翻译。
- apps 负责 Nest 模块装配、Controller 和进程启动。

好处不是“目录整齐”，而是变化被关在局部：换 Milvus SDK只改 Adapter；改权限规则只改 Domain；改 HTTP 字段先改 Contract 和 API Mapping。

代价是文件更多、初期写得慢。小型一次性 Demo 可以简化；多人维护、内外网双环境、供应商频繁变化时，这个成本很快回本。

## 5. 版本到底要版本化什么

RAG 结果受很多隐藏变量影响：

- 原始 DocumentVersion
- contentRevision
- Parser/OCR revision
- Chunk 策略版本
- Embedding 模型、Tokenizer、Query/Document 模板、维度和归一化
- Sparse 格式
- Milvus Schema/Index 参数
- Retrieval Profile、RRF 权重、TopK
- Reranker revision
- Prompt、Policy、Validator、LangGraph flow
- LLM model/revision

这些合起来才是“答案的生产配方”。项目用 Profile + Manifest + Run Snapshot 保存配方，而不是只记录一个模糊的模型名。

## 6. Deadline、Timeout、AbortSignal 的区别

- Deadline：整条业务链路最晚什么时候必须结束，是绝对时间。
- 单次 Timeout：某一次远程尝试最多等多久。
- AbortSignal：用户取消、上游断开或 Deadline 到期时，把取消传播到正在进行的请求。

假设 Run 剩 8 秒，Provider 单次超时配置 30 秒，真正允许的等待是 `min(8s, 30s)`。重试前还要看剩余 Deadline，不能“每次都等 30 秒”导致总耗时无限增长。

## 7. 错误分类为什么是契约的一部分

| 错误                        | 是否重试               | 原因                       |
| --------------------------- | ---------------------- | -------------------------- |
| 429、短暂网络错误、部分 5xx | 有限重试               | 状态可能很快恢复           |
| 单次 Timeout                | 看剩余 Deadline 后重试 | 不能突破总时限             |
| 401/403                     | 不重试                 | 密钥或权限错误不会自己变好 |
| Schema Error                | 不重试                 | 代码/协议不兼容，重试仍错  |
| Version Mismatch            | 不重试并拒绝启动/任务  | 静默使用错误模型会污染索引 |
| Invalid Input               | 不重试                 | 应修输入或进入人工审核     |
| Cancelled                   | 不重试                 | 尊重调用方意图             |

不要靠供应商的中文错误字符串判断。Adapter 应归一化成稳定错误码，再由 Application 决定重试、降级或失败。

## 8. 幂等契约

幂等不是“接口返回 200”，而是相同业务意图重复执行，最终只产生一个业务结果。

本项目常见做法：

- API 使用 `Idempotency-Key`。
- Job ID 由 documentVersionId/contentRevision/pipelineVersion 确定性组成。
- Outbox 有唯一约束。
- BullMQ 使用稳定 jobId 去重。
- Worker 写 Inbox/Consumer Receipt。
- PG 状态更新检查当前状态、revision 和 leaseOwner。
- MinIO Complete 后先 HEAD 实际对象。
- Milvus 用稳定 vectorId upsert，并在发布前对账。

单靠其中一层不够。队列去重记录可能过期，数据库唯一约束和状态机仍是最终防线。

## 9. 如何评审一个新契约

逐条问：

1. 输入是否有长度、枚举、数量和嵌套深度上限？
2. 未知字段是拒绝还是忽略？会不会掩盖版本漂移？
3. 时间、字节、Token、置信度的单位是什么？
4. 批量调用允许部分失败吗？如何关联 itemId？
5. 是否返回实际 modelId/revision，而不是调用方配置回显？
6. 重复请求如何识别？结果能否安全重放？
7. 取消和 Deadline 能到达最底层 SDK 吗？
8. 错误能否稳定分类，是否泄漏正文、URL 或密钥？
9. 权限和资源归属由谁确认？
10. 版本变化是向后兼容、需要 Adapter，还是必须重建数据？

能回答这些，才叫“契约详细”，不只是贴一段 JSON。
