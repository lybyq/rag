# 11：架构选型、参数判断与换场景决策手册

> 面试官问“为什么选 Milvus/BullMQ/LangGraph”时，不是在考产品说明书，而是在看你能否从约束推导方案。本章给出一套可重复使用的决策算法。换一家公司、换一批数据，也能重新得出答案。

## 1. 任何选型先问 20 个问题

### 1.1 业务目标

1. 用户要查事实、总结文档、执行流程，还是生成创意？
2. 答错一次的损失是什么：体验差、工单增加、资金/合规风险？
3. 无答案时允许模型猜、必须拒答，还是转人工？
4. 是否要求每个结论可引用、可审计、可复现？

### 1.2 数据

5. 文档量、页数、预计 Chunk/向量数和年增长？
6. 增量频率是月、天、分钟还是实时？
7. PDF、Office、HTML、图片、音视频、代码、数据库各占多少？
8. 扫描件、表格、图表、公式、多栏版面占多少？
9. 是否有版本、有效期、部门、产品、地区等可靠 metadata？

### 1.3 查询

10. QPS、峰值系数、并发和期望 P95/P99？
11. 问题偏自然语义，还是编号、错误码、人名、金额？
12. 单跳、对比、多跳、计算问题各占多少？
13. 是否需要多轮会话和代词消解？

### 1.4 安全与合规

14. 权限是系统级、空间级、文档级、行级还是字段级？
15. 权限变更多快，能否接受缓存延迟？
16. 问题和答案是否敏感，保留多久，谁能审计？

### 1.5 资源与组织

17. 已有 PostgreSQL、Elasticsearch、Milvus、Kafka、Redis 哪些平台？
18. 团队会维护什么，谁负责备份、升级和夜间故障？
19. 内网 GPU、CPU、存储和模型吞吐是多少？
20. 是否完全离线，供应链扫描/镜像签名要求是什么？

如果这些问题没有答案，就不应宣称“某个技术一定最好”。可以给安全默认值，但必须把未知项标成需要测量。

## 2. 用一张因果链解释本项目为什么这样选

```text
单企业内网 + 中型规模 + userId/roles
  → 不建设复杂多租户，但权限默认拒绝且 Space 隔离

多格式文档 + 扫描件 + 表格
  → 独立 Parser、选择性 OCR、统一 Block、结构感知 Chunk

上传/解析/Embedding 耗时且会失败
  → 管理 API 与 Worker 分离，PG Outbox + BullMQ + Lease

中文语义 + 制度编号/金额并存
  → Dense + Sparse + Weighted RRF + Reranker

知识更新但要求回答可复现
  → 不可变 Profile/Manifest + Run Snapshot + 原子 Head

企业答错/越权风险高
  → PG 回源、Evidence、Citation 白名单、Validator、拒答

内外网 Provider 不同且内网无网络
  → Port/Adapter + Zod Contract + ENV Profile + 离线镜像包
```

这段因果链比“我们用了很多先进组件”更有说服力。

## 3. 单体、模块化单体和微服务怎么选

| 条件                                | 推荐                      | 原因                             |
| ----------------------------------- | ------------------------- | -------------------------------- |
| 小团队、低 QPS、PoC                 | 模块化单体 + 后台 Worker  | 部署简单，先验证价值             |
| 在线/离线 SLA 明显不同              | API、Query、Worker 分进程 | 独立扩容和隔离故障               |
| 多团队独立发布、技术栈/合规边界不同 | 进一步微服务化            | 团队边界能覆盖分布式成本         |
| 只是“看起来企业级”                  | 不拆                      | 网络、契约、运维和一致性成本不值 |

本项目选择“共享 Monorepo 的多进程模块化架构”。Domain、Contracts 和通用 Adapter 复用；管理、查询、入库、调度、解析按资源/SLA 分进程。它比单进程更可运营，又避免每个小模块都成为网络服务。

### 3.1 何时继续拆

- Parser 有高风险依赖、需要沙箱或独立扩缩容；本项目已经独立。
- Query QPS 远高于管理流量；本项目已经独立。
- 不同知识域由不同团队、不同合规区维护；可按域拆索引/Provider，但要统一身份和 Evidence 契约。
- 只有数据库表变多，不是拆服务理由。

## 4. PostgreSQL、MongoDB、搜索引擎怎么选事实源

### 4.1 本项目为什么用 PostgreSQL

核心数据是强关系和状态机：用户授权、Space、Document Version、Job/Step、Outbox、Manifest Head、Run/Citation。需要事务、唯一约束、条件更新和审计。PostgreSQL 很适合当事实源。

### 4.2 什么时候 MongoDB 合适

如果主要数据是大量形状多变的解析 Artifact，关系和跨实体事务少，MongoDB 可作为派生结构存储。但权限、发布指针、任务状态仍要认真设计原子边界；“JSON 多”不自动代表 MongoDB 更好。

### 4.3 搜索引擎不是订单总账

Elasticsearch/OpenSearch 擅长全文和聚合，但更新可见性、事务和关系约束与 PG 不同。常见组合是 PG 存真相，Search/Vector 存可重建投影。不要把关键 ACL 只放搜索索引而没有回源机制。

## 5. BullMQ、Kafka、RabbitMQ 和数据库任务表怎么选

| 方案                      | 优点                            | 代价/局限                             | 适合场景                    |
| ------------------------- | ------------------------------- | ------------------------------------- | --------------------------- |
| PG 任务表 + `SKIP LOCKED` | 少一个组件、事务自然            | 延迟/调度功能需自建，轮询压力         | 小中规模后台任务            |
| BullMQ                    | Node 生态好、延迟/重试/并发方便 | Redis 不是事实源，仍需幂等/Outbox     | Node 中型异步作业           |
| RabbitMQ                  | 成熟路由、ACK、工作队列         | 运维和消息模型成本                    | 企业已有 RabbitMQ、复杂路由 |
| Kafka                     | 高吞吐、可回放事件日志          | 任务调度/延迟/单 Job 语义不如队列直观 | 多消费者事件流、大数据平台  |

本项目是 Node/NestJS、中型文件任务、需要延迟重试和并发 Worker，BullMQ 的开发效率高；又因为不能把 Redis 当事实源，所以使用 PG Outbox、Receipt 和 Lease 补上业务可靠性。

### 5.1 换场景如何改

- 每天只有几十个任务：可以只用 PG `SKIP LOCKED`，BullMQ 可能过重。
- 每秒数万事件、多个下游需要独立回放：Kafka 更合适。
- 公司已有统一 RabbitMQ 运维且禁止 Redis 队列：实现新的 EventPublisher/Consumer Adapter，业务用例不变。
- 任务需要精确日历调度和复杂 DAG：考虑专门工作流调度器，而不是让 BullMQ 承担全部编排。

## 6. MinIO、数据库大字段和文件系统怎么选

| 方案         | 何时合适                                | 主要问题                    |
| ------------ | --------------------------------------- | --------------------------- |
| 本地文件系统 | 单机开发、临时测试                      | 多副本不可共享、备份/扩容差 |
| PG `bytea`   | 很小附件且必须和行强事务                | 数据库膨胀、备份恢复慢      |
| MinIO/S3     | 大文件、Multipart、对象生命周期、多副本 | 对象和 PG 之间需补偿/对账   |

本项目大文件直传 MinIO，PG 只存对象 Key、Hash、大小和状态。预签名 URL 降低 API 带宽，但必须短 TTL、限定对象和方法，并保证 Endpoint 同时能被容器和浏览器解析。

## 7. Parser/OCR 选型

### 7.1 Parser 评价维度

- 支持格式和复杂样本覆盖；
- 标题/段落/表格/图片/页码/坐标是否保留；
- 扫描和混合 PDF 的处理方式；
- CPU/内存、吞吐和单文件延迟；
- 错误分类、取消、超时和协议版本；
- 许可证、离线部署、漏洞响应；
- 是否能输出稳定 Block ID/定位。

### 7.2 OCR 评价维度

- 中文、英文、数字、小数点、印章和手写体；
- 表格/版面检测能力；
- confidence 是否可用；
- GPU 显存、并发和批量；
- 图片/PDF 输入限制和返回定位；
- 内网服务契约和 revision。

### 7.3 决策例子

- 原生 PDF/Office 为主：Node Parser + 选择性 PaddleOCR 足够，成本低。
- 大量复杂扫描表格：版面分析/OCR 是核心，应投入 Golden，可能采用专用文档理解服务。
- 财务报表需精确单元格：考虑结构化抽取和人工审核，不能只靠通用 OCR 文本。
- 音视频知识库：增加 ASR、说话人和时间戳契约，不应硬塞进现有 PDF Parser。

## 8. Chunk 策略选型

### 8.1 决策矩阵

| 数据形态  | 推荐策略                               | 不推荐               |
| --------- | -------------------------------------- | -------------------- |
| 制度/手册 | 标题层级 + Parent/Child + 适量 overlap | 只按字符硬切         |
| FAQ       | 问答对作为原子 Chunk，可扩同义问       | 把多个 FAQ 拼成大块  |
| 合同      | 条款/定义/附件结构，保留版本和主体     | 跨条款随机切         |
| 表格      | 表头 + 行/逻辑组，必要时结构化 SQL     | 每个单元格孤立向量化 |
| 代码      | symbol/AST/file/调用关系 + lexical     | 只按自然语言段落     |
| 工单      | 问题、诊断、解决方案分字段，清洗 PII   | 整个会话不分角色塞入 |

### 8.2 什么时候用 Semantic Chunking

Semantic Chunking 能按主题变化分界，但计算贵、结果随模型变化、对表格/代码未必好。结构可靠的制度优先结构边界；无结构长文本可把 Semantic 作为候选 Profile，用 Golden 证明收益。

### 8.3 什么时候用 GraphRAG

需要跨实体、多跳关系、全局社区总结时可考虑 GraphRAG，例如供应链依赖、科研人物/机构关系。简单制度查条款时构图成本和更新复杂度可能得不偿失。先证明普通 Hybrid RAG 的多跳上限，再引入图。

## 9. Embedding 模型怎么选

### 9.1 不要只看排行榜

先用公开榜单筛 2～4 个候选，再用企业 Golden 对比：

- 中文/中英混合；
- 行业术语和缩写；
- 精确编号/数字；
- 长文本截断；
- Query/Document 指令；
- Dense/Sparse 是否同时支持；
- 维度和向量库存储/内存；
- GPU/CPU 吞吐、批量、P95；
- 许可证和离线模型文件。

### 9.2 维度不是越大越好

粗略存储量：

```text
向量原始字节 ≈ chunk_count × dimension × 4(float32)
```

1000 万个 1024 维向量，仅原始 Dense 数据约 38.1 GiB；加索引、metadata、副本和临时构建会更多。768/1024/1536 维的选择要看 Recall 增益是否值得存储、内存和带宽。

### 9.3 归一化和距离度量

Cosine、Inner Product、L2 的选择要与模型训练和 normalize 规则一致。单位归一化后 Cosine 与 Inner Product 排名关系相近；不能文档归一化而查询不归一化。该规则进入 Profile 和启动校验。

### 9.4 模型升级流程

不是改 `MODEL_ID`：离线评测 → 新 Profile → 新 Collection → 全量/增量构建 → 对账 → Baseline 对比 → Canary → Promote → 观察 → 可回滚 → 延迟清理。

## 10. Milvus、pgvector、Elasticsearch/OpenSearch 怎么选

### 10.1 关键维度

| 维度         | pgvector           | Milvus                       | Elasticsearch/OpenSearch   |
| ------------ | ------------------ | ---------------------------- | -------------------------- |
| 运维复杂度   | 低，复用 PG        | 中高，独立向量系统           | 中高，搜索集群             |
| 强项         | 小中规模、事务邻近 | 大规模向量吞吐/索引          | 全文、过滤、聚合、混合搜索 |
| 全文能力     | 需 PG FTS/扩展     | 不是主要强项                 | 强                         |
| 向量生命周期 | 与 PG 数据耦合     | 独立 Collection/Profile 友好 | 索引级管理                 |
| 团队前提     | 熟 PostgreSQL      | 有向量平台运维               | 已有搜索平台               |

### 10.2 本项目为什么是 Milvus

用户明确内网已有 Milvus；中型规模需要独立向量生命周期、Candidate Collection 和 Profile 发布；因此实现 Milvus Port。同时 PG 仍保存 Manifest、权限和文档事实，避免把 Milvus 当数据库。

### 10.3 换场景

- 20 万 Chunk、低 QPS、只有两名后端：优先 pgvector，少维护一个系统。
- 5000 万向量、高并发、独立索引团队：Milvus 更有价值。
- 产品 SKU/日志搜索，精确词和过滤占主导：OpenSearch 可能是主召回，向量是辅助。
- 企业已有稳定搜索中台：复用已有平台往往优于新建 Milvus。

## 11. Dense、Sparse、Hybrid 和结构化检索怎么选

| 问题类型                | 主策略            | 补充                         |
| ----------------------- | ----------------- | ---------------------------- |
| “出差住宿标准是多少”    | Dense             | Sparse 锁定金额/标题         |
| “FIN-2026-017”          | Sparse/精确匹配   | Dense 找解释                 |
| “库存为 0 的华东商品”   | SQL/过滤          | RAG 解释规则，不负责实时库存 |
| “A 与 B 制度差异”       | 多子问题 Hybrid   | Evidence 对齐版本/条款       |
| “故障码 E1027 怎么处理” | Sparse + metadata | Dense 找相似描述             |
| “这三家供应商关系”      | 图/SQL + RAG      | 取决于结构化实体质量         |

Hybrid 的价值是覆盖不同问题分布，但多一条路线也带来延迟、维护和融合参数。若业务 99% 是标准编码精确查询，Dense 可能只是低权补充。

## 12. RRF、分数归一化和 Learning-to-Rank

### 12.1 为什么本项目先选 RRF

Dense、Sparse、不同 Provider 的分数尺度不同且升级后会漂移。RRF 只使用排名，稳健、容易解释、无需大量标注。Weighted RRF 允许根据业务问题分布调整路线贡献。

### 12.2 什么时候升级到归一化或 LTR

- 有足够且稳定的点击/标注数据；
- 需要利用第一名远高于第二名的分数间距；
- 能在模型/索引升级后重新标定；
- 能监控特征漂移和解释权限/版本特征。

LTR 不是免费精度：特征管道、训练偏差、回滚和解释成本都要算。

## 13. Reranker 怎么选和什么时候跳过

### 13.1 评估维度

- 对企业 Query/Document 的 TopN Recall/NDCG 提升；
- 最大 Token、长文截断方式；
- 批量和 GPU 吞吐；
- P95、429/5xx 和并发；
- 中英、数字、表格序列化表现；
- revision 和协议可固定。

### 13.2 路由策略

- 明确的精确 ID 且 Sparse 第一名唯一命中：可跳过或轻量 Rerank。
- 多路候选、同义问题、长条款：Reranker 价值高。
- 高 QPS FAQ：可对高置信缓存结果跳过，但 Cache Key 必须包含知识/权限版本。
- 高风险制度：即便慢一些也保留 Reranker 和强校验。

## 14. LLM 怎么选

### 14.1 不只看“聪明程度”

- 中文指令、结构化 JSON、长上下文；
- Evidence 忠实度和 Citation 行为；
- 无答案时是否愿意拒答；
- P95、吞吐、并发和 Token 成本；
- 内网部署、量化、显存、许可证；
- API 协议、取消、revision、日志隐私。

### 14.2 分级路由

可用小模型做 Query Rewrite/分类，强模型做复杂生成/Judge；简单 FAQ 用模板或小模型。高风险答案未必一定用最大模型，而是“可靠检索 + 严格证据 + 合适模型 + 校验”的组合。

### 14.3 温度 0 也不等于可复现

底层并行、模型 revision、Serving 实现仍可能变化。可复现依赖 Run Snapshot、结构化输出、Hash、测试和版本固定，不只靠 Temperature。

## 15. LangGraph、普通代码、工作流引擎和 Agent 怎么选

| 需求                                 | 推荐                          |
| ------------------------------------ | ----------------------------- |
| 固定线性调用                         | 普通函数/Pipeline             |
| 有有限分支、循环、节点状态和模型路由 | LangGraph                     |
| 跨小时/天、人工审批、强持久化补偿    | Temporal/Camunda 等工作流引擎 |
| 开放探索、工具选择、低风险研究       | 受限 Agent                    |
| 权限/资金/合规决策                   | 确定性规则，LLM 只能建议      |

本项目问答是秒/分钟级、存在有限分支和一次修复，因此 LangGraph 合适；入库是跨系统持久任务，使用 PG 状态机/Outbox/BullMQ，而不是硬把所有后台生命周期塞进内存 Graph。

## 16. 缓存怎么选

### 16.1 可以缓存什么

- Query Embedding：Key 包含模型/Profile/模板/query hash；
- 检索结果：还必须包含 Manifest、auth scope、Retrieval Profile；
- 公开 FAQ 答案：需要知识版本和策略版本；
- Provider metadata：短 TTL，并在启动/调用关键点校验。

### 16.2 不能随便缓存什么

- 不带权限版本的答案；
- 当前余额/库存等实时事实；
- Validator 失败的草稿；
- 跨用户包含敏感正文的 Context；
- 权限不确定时用旧缓存“保可用”。

安全缓存失效策略是 fail closed：无法确认授权时绕过缓存或拒绝，不是返回可能越权的旧结果。

## 17. 容量规划的计算方法

### 17.1 入库吞吐

```text
daily_chunks = daily_documents × avg_pages × avg_chunks_per_page
embedding_requests = daily_chunks / effective_batch_size
required_embedding_qps = daily_chunks / ingestion_window_seconds
```

还要乘重建峰值。日常增量能跑完不代表模型升级时能在窗口内全量重建。

### 17.2 在线 Provider 并发

近似 Little's Law：

```text
concurrency ≈ QPS × average_latency_seconds
```

例如峰值 20 QPS、Reranker 平均 0.4 秒，平均在途约 8；再考虑 P95、突发、重试和安全余量。LLM 还受 Token/s 而不只是请求数限制。

### 17.3 Redis/BullMQ

关注等待 Job 数还不够，关键是 oldest job age：如果一直有 1000 个任务但 5 分钟清完可以接受；只有 20 个任务却最老等 2 小时才是真问题。结合 arrival rate、service rate、stalled、retry 和 DLQ。

### 17.4 PostgreSQL

总连接上限不能等于“每个 Pod 默认池 × Pod 数”后超过数据库容量。需要为平台、Query、Worker、Scheduler 分配预算；长模型调用不能占着不必要的数据库事务。

## 18. 十二个换场景推导

### 18.1 银行制度与合规问答

特点：答错损失高、权限/审计严格、更新有生效时间。

选择：条款结构 Chunk；Dense+Sparse；有效期 Filter；强 Reranker；Evidence/Citation/确定性规则/Judge；严格流式；高拒答率可接受；人工升级。缓存保守。

### 18.2 制造业设备维修

特点：扫描手册、图表、错误码、设备型号和版本。

选择：重点投入 OCR/版面/图号；型号/version metadata Filter；错误码 Sparse；步骤语义 Dense；答案引用页码和图号；可能增加多模态检索。不是先换更大 LLM。

### 18.3 高频客服 FAQ

特点：QPS 高、问题重复、风险中等、可转人工。

选择：FAQ 原子 Chunk；语义缓存；轻量 Embedding/Reranker；高置信模板答案；低置信转人工；反馈闭环。可按风险跳过昂贵 Judge，但不能省权限键。

### 18.4 法务合同库

特点：主体、定义、条款、附件、版本和引用要求强。

选择：按条款/定义 Chunk，保留合同主体和有效期；对比问题拆子问题；引用到条款/页；重要数值规则校验；文档级 ACL；冲突时不给单一结论。

### 18.5 代码知识库

特点：精确符号、调用关系、commit 版本。

选择：AST/symbol Chunk；lexical code search + Dense；依赖/调用图辅助；权限按仓库；Citation 到 commit/path/line。自然语言固定切片不是主方案。

### 18.6 BI 指标问答

特点：数字实时、口径定义在文档、实际值在数仓。

选择：RAG 找指标定义和口径；受控 SQL Tool 查数；语义层限制表/字段；答案同时引用口径和查询时间。不要把昨日 CSV 向量化后声称实时。

### 18.7 医疗知识辅助

特点：高风险、指南版本、患者隐私。

选择：用途限定为辅助；强权限/脱敏/审计；权威来源和版本；高拒答和免责声明；临床决策需专业人员。不得把普通客服式答案当诊断。

### 18.8 新闻/舆情

特点：高时效、重复和来源可信度差异。

选择：增量索引、时间衰减、来源 authority、事件聚类、冲突展示；过期阈值和时间戳。Manifest 发布窗口可能要缩短。

### 18.9 百万行产品表

特点：高度结构化、精确过滤、聚合。

选择：数据库/Search 为主，RAG 解释字段和自然语言转受控查询。不要给每一行都生成大段 Embedding 后用向量回答库存。

### 18.10 跨部门知识门户

特点：多个域、不同 ACL、不同文档形态。

选择：先按权限和 Query Route 缩小 Space；域内可用不同 Chunk/Embedding Profile；统一 Evidence/Citation 契约。不能全库召回后再过滤。

### 18.11 个人小型知识库

特点：单用户、几万 Chunk、低风险。

选择：SQLite/PostgreSQL + pgvector、单进程、简单任务队列即可。保留版本/引用，但可以删去复杂 RBAC、独立 Milvus 和多服务运维。

### 18.12 超大规模公共搜索

特点：亿级文档、高 QPS、公开数据。

选择：分片 Search/Vector、多级召回、近线特征、缓存/CDN、独立 LTR；权限简化但反滥用和成本重要。此时本项目的中型默认参数需要重新压测和分层服务化。

## 19. 面试现场的选型回答模板

面对“你为什么选 X”，按下面六句回答：

1. **约束**：“我们的数据/流量/风险/团队条件是……”
2. **目标**：“最需要保证的是……”
3. **候选**：“比较过 A、B、C，它们分别……”
4. **决策**：“所以当前阶段选择 X，因为……”
5. **代价**：“它的成本/缺点是……我们用……控制。”
6. **演进阈值**：“如果规模/场景变成……我会换成 Y，并用……指标决定。”

示例：

> 我们是 Node 技术栈的中型内网文档任务，需要延迟重试和独立 Worker，团队已有 Redis，所以选择 BullMQ；但 Redis 和 PG 没有共同事务，BullMQ 也不能消除重复，因此用 PG Outbox 保证任务事实、Receipt/稳定 Job ID 保证幂等、PG Lease 防迟到 Worker 覆盖。如果只有几十个日任务，我会直接使用 PG `SKIP LOCKED` 降低运维；如果需要多消费者高吞吐回放，则评估 Kafka。

这类回答同时具备业务背景、候选比较、真实实现、风险和演进，不像背产品广告。

## 20. 典型错误选型信号

- 先定向量库，再问数据量和查询类型；
- 只看模型公开榜单，不做企业 Golden；
- 用大模型补 Parser/权限/版本错误；
- 把所有数据都向量化，包括实时结构化事实；
- 为了“Agent”允许无限循环和自由工具调用；
- 把内网当安全边界，不做认证 Header 防伪；
- 把 Kafka/BullMQ 当数据库事实源；
- 认为 Reranker 一定提升，不测延迟和 TopN；
- 模型升级只改 ENV，不重建索引；
- 用“高可用、可扩展”回答，却说不出指标、失败模式和恢复路径。
