# 10：真实代码、数据表与 LangGraph 全链路导读

> 本章把第 9 章的概念钉到真实代码。阅读方式是：先按本章顺序打开文件，不要从目录随机看；每走一步，回答“输入从哪来、输出去哪、失败写到哪里、谁可以重试、用户能看到什么”。

## 1. 先认清四层代码

```text
Controller / Worker / Scheduler
        ↓ 输入映射、调用
Application Use Case
        ↓ 依赖抽象能力
Port 接口 + Domain/Algorithm
        ↑ 由基础设施实现
PG / Redis / MinIO / Milvus / HTTP Provider Adapter
```

### 1.1 为什么这样分层

- Controller 只处理 HTTP 形状，不能直接拼 SQL 或 Milvus Filter。
- Application 负责业务编排、事务语义、权限和重试决策。
- Domain/算法保存最稳定的不变量，不依赖 NestJS、数据库 SDK。
- Adapter 负责把第三方协议转换成 Port 所需形状。

例如答案图只依赖 `RerankerPort`、`AnswerModelPort`，并不知道内网用什么模型服务。真正 HTTP 转换在 `libs/model-gateway`。这使外网 Fixture 和内网模型切换不会污染业务图。

### 1.2 读代码时先找什么

对一项功能按下面顺序找：

1. `libs/contracts`：外部/跨模块数据形状；
2. `apps/*/controller` 或 Worker：入口；
3. `libs/application/*service.ts`：用例；
4. 同名 `*.ports.ts`：需要哪些外部能力；
5. `libs/domain` 或专用算法库：规则；
6. `libs/persistence-*`、`libs/model-gateway`：实现；
7. `database/migrations`：持久化不变量；
8. `*.spec.ts`：哪些行为被证明。

## 2. 启动阶段：ENV 怎样变成可信配置

入口配置是 `libs/config/src/app-config.ts`。

### 2.1 执行过程

```text
process.env
  → AppEnvironmentSchema.safeParse
  → 环境组合 refine
  → loadAppConfig
  → 类型化 AppConfig
  → ConfigModule 注入各 Adapter/Service
```

Zod 不只是检查“字段存在”，还检查组合：`PROVIDER_PROFILE` 必须与 `APP_ENV` 匹配；内网 Profile 不能继续使用 Fixture；生产模型地址不能误指 localhost；关键 Profile ID 和 revision 不能空缺。

### 2.2 为什么不能在业务代码里到处 `process.env`

如果每个 Service 自己读取 ENV：

- 启动时无法一次发现全部错误；
- 同一变量可能被不同模块解释成不同类型；
- 测试难以注入配置；
- Domain 被供应商字段污染；
- 热更新时一次 Run 可能读到两套版本。

所以 ENV 只在配置边界读取，业务拿到已经校验的结构。Run 创建时再把影响答案的版本冻结成 Snapshot。

### 2.3 建议你动手做

在本地临时把 `EMBEDDING_DENSE_DIMENSION` 改成非法值 0，观察应用在启动阶段拒绝，而不是处理到第 100 个 Chunk 才由 Milvus 报错。然后恢复配置。

## 3. 身份与知识空间链路

### 3.1 入口和契约

- 认证 Guard：`libs/auth/src/authentication.guard.ts`
- Trusted Header：`libs/auth/src/trusted-header-auth.adapter.ts`
- JWT：`libs/auth/src/jwt-auth.adapter.ts`
- 角色映射：`libs/auth/src/role-mapper.ts` 与 `config/role-mapping.yaml`
- 权限领域规则：`libs/domain/src/authorization.ts`
- 应用服务：`libs/application/src/authorization.service.ts`
- PG 实现：`libs/persistence-pg/src/postgres-knowledge-space.repository.ts`

认证回答“你是谁”，授权回答“你能做什么”。系统接收到的 `userId/roles` 只是企业身份上下文，业务角色还要映射成语义角色。

### 3.2 权限收窄的核心不变量

```text
客户端 requestedSpaceIds ∩ 服务端当前 allowedSpaceIds
```

客户端只能缩小，不能扩大。未传 `requestedSpaceIds` 也不等于“无过滤”，而是使用服务端显式授权集合。之后该集合被编译成受控 Milvus Filter，用户输入不能直接拼接表达式。

### 3.3 为什么查询后还要再查 PG

向量索引携带的是发布时授权/状态投影。Run 创建后可能撤权，旧向量可能还未清理。`source_recheck` 和 `expandAndRecheck` 从 PG 读取当前事实，剔除无权、已撤销、版本不符的候选。Citation 获取详情时还会再次授权。

### 3.4 面试时怎样证明不是口号

不要只说“我们做了 RBAC”。指出四道边界：认证适配 → Space ACL → 服务端 Filter → PG/Citation 再授权；再指出缓存 Key 必须包含授权版本，否则撤权后旧缓存会泄漏。

## 4. 文档上传链路：从 HTTP 到持久任务

### 4.1 入口文件

- 上传 Controller：`apps/platform-api/src/document-ingestion/uploads.controller.ts`
- 文档 Controller：`apps/platform-api/src/document-ingestion/documents.controller.ts`
- Job Controller：`apps/platform-api/src/document-ingestion/ingestion-jobs.controller.ts`
- 用例：`libs/application/src/document-ingestion.service.ts`
- Port：`libs/application/src/ingestion.ports.ts`
- PG：`libs/persistence-pg/src/postgres-document-ingestion.repository.ts`
- MinIO：`libs/persistence-minio/src/minio-object-storage.adapter.ts`
- 状态机：`libs/ingestion-core/src/ingestion-state-machine.ts`

### 4.2 为什么先创建上传会话

API 先做：身份、Space 权限、文件数量/大小/类型策略、随机对象 Key、短时预签名 URL。文件字节随后由浏览器直传 MinIO，避免大文件穿过 Node API 占满内存和连接。

对象 Key 由服务端产生，不能直接使用用户文件名，否则可能对象路径穿越、冲突或覆盖其他用户文件。

### 4.3 Complete 的不确定窗口

浏览器调用 Multipart Complete 后网络断开，它不知道 MinIO 是否已经合并成功。安全做法不是盲目再 Complete，而是先 `HEAD` 对象：

- 对象存在且 size/hash 符合：补记数据库完成；
- 对象不存在：继续恢复或报告失败；
- 对象存在但事实不符：进入异常处理，不能把错误文件发布。

这叫“先查询外部事实，再决定补偿”。

### 4.4 PG 表怎么协作

迁移 `20260816130000_document_ingestion.sql` 中的关键表：

| 表                                 | 角色                              |
| ---------------------------------- | --------------------------------- |
| `documents`                        | 逻辑文档，例如《差旅制度》        |
| `document_versions`                | 一次不可变内容版本                |
| `document_files`                   | MinIO 对象、Hash、MIME 等字节事实 |
| `upload_sessions` / `upload_files` | 上传会话与各文件状态              |
| `ingestion_jobs`                   | 业务任务总状态、lease、attempt    |
| `ingestion_job_steps`              | 每阶段真实状态和进度              |
| `ingestion_job_events`             | 用户可见事件历史                  |
| `outbox_events`                    | 待发布的跨系统事件                |
| `outbox_consumer_receipts`         | 消费幂等凭证                      |

### 4.5 事务里到底写什么

上传确认用例在同一个 PG 事务中写入：Document Version、Job、初始 Step/Event、Outbox。事务提交代表“业务事实已经存在，任务最终必须被调度”；它不要求 Redis 此刻可用。

如果把 `queue.add()` 放在事务前，PG 回滚后会出现幽灵任务；放在事务后，进程可能在提交后、发队列前崩溃。Outbox 就是为这个失败窗口存在。

## 5. Outbox、Scheduler 与 BullMQ 精讲

### 5.1 发布链路

- Outbox 服务：`libs/application/src/outbox-publisher.service.ts`
- 调度器：`apps/scheduler-worker/src/ingestion-maintenance.scheduler.ts`
- BullMQ Publisher：`libs/persistence-redis/src/bullmq-ingestion-event.publisher.ts`
- Worker：`apps/ingestion-worker/src/ingestion-queue.consumer.ts`

执行顺序：

```text
PG 事务写 outbox(pending)
  → Scheduler 周期领取一批记录
  → BullMQ add(stableJobId, eventEnvelope)
  → 发布成功后标记 published
  → Worker 收到 Job
  → PG 插入 consumer receipt / 领取业务 lease
  → 调 Application Use Case
  → 更新 Step、Event 和后续 Outbox
  → BullMQ ACK
```

### 5.2 为什么发布仍可能重复

Scheduler 成功 `queue.add()` 后，在 PG 标记 published 前崩溃。恢复后它会再次发布。因此 Outbox 只能保证“不轻易丢”，不能让传输天然 Exactly Once。

本项目用稳定 Job ID 和 Receipt 消化重复。数据库唯一约束是最后一道并发保护，不能只靠“先查询是否存在”，因为两个 Worker 可能同时查到不存在。

### 5.3 BullMQ 的 Lock 和 PG Lease 不同

| 机制           | 保护对象              | 失效后果                               |
| -------------- | --------------------- | -------------------------------------- |
| BullMQ Lock    | Redis 中的 Job 消费权 | Job 可被判 stalled 后重新投递          |
| PG Lease       | 业务记录的写入资格    | 新 Worker 可接管，旧 Worker 写入被拒绝 |
| Unique/Receipt | 重复业务效果          | 第二次插入或推进被识别为已处理         |

### 5.4 重试分类

`ingestion-queue.consumer.ts` 不应该对所有错误统一重试：

- 网络、429、部分 5xx：有限重试；
- 取消事件：消费后终止，不再次入队；
- 文件格式不支持、Schema 不匹配：重试不会变好；
- 可疑文件：进入拒绝/人工审核，不是基础设施失败；
- Lease 丢失：旧 Worker 停止，不覆盖接管者；
- 达到上限：持久化失败原因并进入运维/DLQ 处理。

### 5.5 为什么进度不能前端模拟

远程 Parser 可能 30 秒都没有细粒度进度。前端若用定时器从 40% 涨到 90%，用户会误以为真实完成。本项目只在 Job Step 完成真实单位时写进度；长调用期间续租和心跳，但不伪造百分比。刷新后从 PG Event 恢复。

## 6. 文件安全、Parser 与 OCR 链路

### 6.1 代码路线

- 文件检测/安全：`libs/parser-core/src/file-detection.ts`、`security-policy.ts`
- 处理用例：`libs/application/src/document-processing.service.ts`
- Parser Port：`libs/application/src/document-processing.ports.ts`
- 内置 Parser：`libs/document-parser-core/src/parser-registry.ts`
- PDF/DOCX/PPTX/XLSX：同目录各 `*.parser.ts`
- 独立服务入口：`apps/document-parser-service/src/parser.controller.ts`
- HTTP Parser/OCR Adapter：`libs/file-processing-providers/src/http-parser.adapter.ts`、`http-ocr.adapter.ts`

### 6.2 一次处理的稳定输入

Worker 不相信消息里携带的对象路径和权限事实。消息主要负责“唤醒”，真正输入从 PG 读取：当前 Document Version、受控 objectKey、content hash、Job/Lease、Provider Profile。这样旧消息不会把新任务带回旧状态。

### 6.3 处理阶段

```text
load trusted input
→ beginParseRun(冻结 parser/ocr profile)
→ stream object with size/deadline
→ preflight file detection and archive limits
→ content safety scan
→ parser returns normalized blocks
→ select low-coverage OCR targets
→ OCR and merge by targetId
→ normalize blocks / persist artifact
→ complete or manual review/reject/fail
```

### 6.4 为什么 Profile 要落库

同一文件用 Parser v1 和 v2 可能得到不同表格结构。只保存最终文本，无法解释为何两次索引不同。Parse Run 保存 parserProfileId、revision、protocol、OCR Profile 和输入 Hash，结果才可复现和比较。

## 7. 结构恢复、Chunk 与质量门禁

### 7.1 代码路线

- 结构恢复：`libs/chunking/src/structure-recovery.ts`
- Chunk 构造：`libs/chunking/src/chunk-builder.ts`
- Tokenizer：`libs/chunking/src/tokenizer.ts`
- 质量策略：`libs/chunking/src/quality-policy.ts`
- 审核策略：`libs/chunking/src/review-policy.ts`
- 用例：`libs/application/src/knowledge-processing.service.ts`
- PG：`libs/persistence-pg/src/postgres-knowledge-processing.repository.ts`

### 7.2 Chunk 身份为什么必须稳定

Chunk ID 应由内容、结构位置和 Profile 等稳定事实决定。重试同一次处理必须得到同一 ID，否则重复任务会不断膨胀索引，引用也无法稳定回溯。

### 7.3 质量门禁不是一个总分

项目检查非空 Block 比例、乱码率、重复率、OCR confidence、长时间无标题等。规则分为：

- 可通过：自动进入索引；
- 需要审核：保留结果但不自动发布；
- 拒绝：数据质量低到不应成为知识；
- 失败：基础设施/协议问题，可按分类恢复。

不能把“Parser 返回 200”直接等同于内容可用。

### 7.4 人工审核如何避免覆盖并发变更

审核时应携带版本/状态条件更新。如果审核员打开页面后系统重跑了新版本，旧页面不能把新结果误批准。数据库条件和状态机共同提供乐观并发保护。

| ------------------------------- | --------------------------------------- |

### 8.3 批量 Embedding 为什么有三种限制

- `batchSize`：单请求最多多少条；
- `maxBatchTokens`：避免少量超长 Chunk 把请求撑爆；
- `maxConcurrency/maxQueuedItems`：控制 Provider 并发和本进程内存背压。

只限制条数不够：32 条每条 8000 Token 和 32 条每条 100 Token 完全不是一个负载。

### 8.4 vectorId 为什么包含三个版本维度

项目按 `manifestId:chunkId:embeddingProfileId` 计算稳定 Hash。这样：

- 同一任务重试可以 Upsert 同一记录；
- 新 Manifest 不覆盖旧版本；
- 新 Embedding Profile 不与旧向量混淆；
- 对账能从 PG 推导期望主键。

### 8.5 Promote 为什么是短事务

耗时的 Embedding、Milvus 写入和评测都在事务外完成。真正发布只在 PG 短事务中校验 Candidate 状态、对账结果和当前 Head，然后切换 Head。长事务会锁住管理操作、放大失败范围。

## 9. 创建会话和 Run

### 9.1 代码路线

- HTTP：`apps/rag-query-service/src/conversation-runtime/conversations.controller.ts`、`runs.controller.ts`
- 用例：`libs/application/src/rag-run.service.ts`
- 生命周期：`libs/application/src/rag-run-lifecycle.service.ts`
- 状态机：`libs/domain/src/rag-run-state.ts`
- 敏感正文：`apps/rag-query-service/src/conversation-runtime/aes-gcm-sensitive-text.protector.ts`
- PG：`libs/persistence-pg/src/postgres-rag-run.repository.ts`

### 9.2 创建 Run 时冻结什么

Run Snapshot 至少包含：

- userId/roles 的受控身份摘要和授权版本；
- 已授权 Space 与 Active Manifest；
- Retrieval Profile；
- LLM/Embedding/Reranker revision；
- Prompt、Validator、Flow、Policy 版本；
- Feature Flags；
- Deadline。

为什么不在每个节点直接读当前 ENV？因为执行到一半配置可能变化，结果不可复现。热配置只影响下一个 Run；权限属于安全事实，在关键边界仍读取当前状态收窄。

### 9.3 问题正文和日志

问题正文使用 AES-256-GCM 保护并受保留策略约束。日志、Trace、指标和节点审计只保存长度、计数、Hash、版本、错误分类，不保存完整问题和证据。

## 10. 检索 LangGraph 逐节点

图在 `libs/rag-graph/src/hybrid-retrieval.graph.ts`。

### 10.1 `route_query`

输入：解密后的问题、历史实体。输出：`KNOWLEDGE` 等路由、精确字面量、初始 plan hash。

解决：不是每个消息都值得查知识库；编号、日期、金额等必须先提取并在 LLM 改写后恢复。

### 10.2 `build_plan`

从 Run Snapshot 和当前 allowedSpaceIds 编译 Filter，构造子问题、Profile 和第一轮计划。LLM 不能直接提供 Filter。

### 10.3 `rewrite_query`（条件节点）

复杂追问才调用改写 Provider。失败属于增强降级：保留确定性原问题计划，不扩大权限，也不让整次查询失败。

### 10.4 `query_embedding`

按 Run 冻结的 Embedding revision 生成 Query 向量。Cache Key 包含 Profile、revision、plan hash、auth scope hash 和 query hash，避免跨权限/版本复用。

### 10.5 `hybrid_retrieve`

对每个子问题和可见 Manifest 并行 Dense/Sparse，统一转成带 route 权重的排名列表，再调用 `weightedReciprocalRankFusion`。部分路线失败会标记 degraded；全部核心路线失败才阻断。

### 10.6 `source_recheck`

调用 PG `hydrateAndRecheck` 获取真实标题、内容、文档状态和当前授权。Milvus 只提供候选 ID，不能直接成为最终证据。

### 10.7 `assess_retrieval` / `retry_plan`

当有效候选少于 `minimumResults` 且还没达到最大两轮时，构造第二轮计划。有限循环防止成本失控。

### 10.8 `diversify`

按 `finalTopK`、每文档、每章节上限去除霸榜，输出给答案图的候选。这里是召回和生成之间的噪声控制。

## 11. 答案 LangGraph 逐节点

图在 `libs/rag-graph/src/answer-generation.graph.ts`。

### 11.1 `retrieve`

复用检索子图，得到 Run、问题、候选和 degraded 状态。

### 11.2 `rerank`

最多取 `rerankerMaximumCandidates`，调用专用 Reranker，检查返回 revision 与 Run Snapshot 一致。只有 TIMEOUT/429/网络/5xx 这类运行故障且 Feature Flag 允许时才回退原排名；Schema 或 revision 错误不能假装降级成功。

### 11.3 `expand_evidence`

从 PG 扩展 Parent、定位、Hash、权限和文档版本，再次剔除失效源。

### 11.4 `build_evidence`

把候选变成 Evidence Bundle，为每个来源生成受控 sourceId，建立子问题覆盖、权威等级和 Bundle Hash。

### 11.5 `route_evidence`

根据覆盖率、置信、冲突和是否已做 LLM 证据重排，选择：`ANSWER`、`PARTIAL_ANSWER`、`LLM_RERANK`、`CLARIFY` 或拒答类路由。不是任何候选都进入自由生成。

### 11.6 `llm_evidence_rerank`（条件）

只对复杂证据做一次 LLM 顺序建议，失败可降级，不能改变 sourceId 白名单或权限。

### 11.7 `build_context`

按 Token Budget 和每文档上限装箱，计算金额/日期等确定性事实。避免把全部检索结果直接塞给 LLM。

### 11.8 `generate_draft`

模型输出结构化 Draft：Claim、正文、Citation ID，而不是不可验证的一段自由文本。

### 11.9 `revalidate_citations`

生成完成后按当前时间再次检查来源是否仍有效，防止执行期间撤权或文档下线。

### 11.10 `rule_validation`

检查 Citation 白名单、Claim 覆盖、字面量、确定性计算和来源有效性。规则能判定的内容不浪费 LLM Judge。

### 11.11 `semantic_judge`（条件）

只判断确定性规则无法判断的语义 Claim 是否被证据支持。它不是权限裁判，也不负责修复数据库错误。

### 11.12 `final_validation` 与一次修复

如果结果为 `REGENERATE` 且只生成过一次，携带 issue code 再生成一次；第二份仍失败则转 `REJECT`，绝不无限循环。

### 11.13 `finalize`

只有这里产生客户端可见的 `FinalAnswer`。严格流式模式在此之前只发送阶段事件，不泄漏未校验正文。

## 12. SSE、Redis Stream 与断线续传

### 12.1 事件路径

```text
业务事务写 rag_run_event_outbox
→ run-event scheduler 发布 Redis Stream
→ SSE 用 stream ticket 订阅
→ 客户端记录 event id
→ 断线后携 Last-Event-ID 续传
```

代码：

- 事件发布：`libs/application/src/rag-run-event-publisher.service.ts`
- Redis Stream：`libs/persistence-redis/src/redis-rag-run-event-stream.adapter.ts`
- Scheduler：`apps/rag-query-service/src/conversation-runtime/run-event.scheduler.ts`
- HTTP/SSE：`apps/rag-query-service/src/conversation-runtime/runs.controller.ts`

PG Outbox 保证事件事实不因 Redis 短暂不可用而丢失；Redis Stream 提供低延迟和短期续传。保留期过后，客户端应从 PG Run 状态恢复，而不是认为 Stream 是永久事实源。

## 14. 故障时从哪里查

### 14.1 上传后一直排队

1. 查 `ingestion_jobs` 和 `outbox_events`；
2. Outbox pending：看 Scheduler heartbeat、DB lease、Redis 连接；
3. Outbox published 但未消费：看 BullMQ wait/active/stalled/DLQ；
4. 已有 Receipt：看业务 Step 是否终态或 Lease 被接管；
5. 不要只重启全部服务掩盖根因。

### 14.2 检索不到标准证据

1. Parser artifact 是否有该条款；
2. Chunk 是否保留标题、表头和数字；
3. 文档版本是否进入 Active Manifest；
4. Milvus expected/actual 对账；
5. 当前用户 Filter 是否过度收窄；
6. Dense/Sparse 各自排名；
7. PG recheck 移除原因；
8. 多样性/Reranker 是否把它排掉。

### 14.3 有证据但最终拒答

1. Evidence Route 是不足、冲突还是需澄清；
2. Context Builder 是否因 Token Budget 裁掉关键源；
3. Draft 是否引用白名单外 ID；
4. Citation 再鉴权是否撤销；
5. Rule/Semantic Validator 的 issue code；
6. 第二次生成是否仍失败。
