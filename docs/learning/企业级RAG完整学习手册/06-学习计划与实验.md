# 06：把项目真正学会的 30 天计划与实验

## 1. 学习方法

每个主题按四步循环：

1. 先画图并用自己的话解释。
2. 跑一条正常链路，记录输入输出和 ID。
3. 故意制造一个安全故障，先预测再观察。
4. 看代码和测试解释为什么系统这样恢复。

只读代码很容易产生“好像懂了”的错觉；能预测故障结果才算掌握。

## 2. 第一周：工程、契约和数据底座

### 第 1 天：进程与分层

- 画 Platform API、Query API、两个 Worker、Parser、Web 和五类基础设施。
- 找到每个 Nest App 的 `main.ts` 与 Module。
- 从一个 Controller 追到 Application Port，再追到 PG Adapter。
- 闭卷解释为什么 Domain 不依赖 Nest/Prisma/Milvus。

### 第 2 天：配置和双环境

- 对比 external-dev 与 intranet-production env。
- 把 Embedding Adapter 从 fixture 切 http，观察缺 metadata/revision 时如何失败。
- 练习判断“改 env / 写 Adapter / 加 Gateway / 改方案”。

### 第 3 天：PostgreSQL

- 运行 migration，查看 schema_migrations checksum。
- 画 Document/Version/Revision/Manifest 的关系。
- 在事务测试里制造重复 idempotency key，观察唯一约束。

### 第 4 天：Redis 和 BullMQ

- 观察 cache Redis 与 BullMQ Redis 的 Key 类型和配置。
- 暂停 Worker，上传文件，观察 PG Outbox 和 waiting Job。
- 重启 Worker，确认任务恢复且没有重复 Document。

### 第 5 天：MinIO

- 完成小文件和 Multipart 上传。
- 让 Complete 响应模拟丢失，再重试，验证 HEAD 补偿。
- 把 Endpoint 改成容器能解析、浏览器不能解析的名字，理解预签名 Host 问题。

### 第 6～7 天：复盘

- 用 10 分钟讲清 Outbox、Inbox、Lease、Heartbeat、幂等。
- 回答“为什么 BullMQ 成功状态不能作为业务真相”。

## 3. 第二周：文件解析、Chunk 和索引发布

### Parser/OCR 实验

- 各上传 PDF、DOCX、XLSX、PPTX、HTML、Markdown、Text、CSV、图片。
- 查看统一 Block 的 page/sheet/slide/bbox/table/originalText。
- 用混合 PDF 验证只对低覆盖页面 OCR。
- 模拟 OCR 返回未请求 targetId，确认契约拒绝。

### Chunk 实验

- 找一份有多级标题、表格和跨段规则的合成文档。
- 对比不同 Child Token 和 overlap 的 Chunk 数、Recall 与重复候选。
- 查看 Parent/Child/Neighbor/Source Block 关系。
- 手动回答：为什么表格问题不能只增大 Chunk。

### Embedding/Milvus 实验

- 调用 Provider metadata，核对维度、归一化、Tokenizer、Sparse 能力。
- 故意把维度改错，确认启动或发布失败。
- 停掉 Milvus，观察 Worker 是受控失败而不是进程崩溃。
- 构建候选 Manifest，在对账前确认 ACTIVE 仍是旧版。
- 对账通过后 Promote，再 Rollback。

## 4. 第三周：检索、证据和 LangGraph

### 手算和代码对照

- 给 Dense/Sparse 两个排名列表，手算 Weighted RRF。
- 设置同分候选，验证稳定 tie-break。
- 设置每文档最多 3、每章节最多 2，手算 diversify 结果。
- 构造金额/日期字面量，观察 exact literal 提取。

### 权限实验

- 两个 userId/roles 访问不同 Space。
- 让 Milvus 留下旧候选，再从 PG 撤权，确认 source recheck 删除候选。
- 尝试客户端提交恶意 Filter/spaceId/collectionName，确认被拒绝。

### LangGraph 实验

- 简单知识问题：rewrite 和 retry 应跳过。
- 复杂多跳问题：观察 subquestion 和 Evidence。
- 无答案问题：应 ABSTAIN，不允许 LLM 编造。
- 冲突版本：应 CONFLICT。
- 模糊问题：应 CLARIFY。
- 取消 Run：AbortSignal 应传播，最终状态不可被迟到结果覆盖。

详细真实 Run 参考 [逐节点演练](../证据生成与答案校验/08-real-langgraph-run.md)。

## 5. 第四周：生产与面试

- 建至少 50 条合成/脱敏 Golden，覆盖权限、无答案、数字、表格、多跳和 Injection。
- 分别记录 Recall@K、MRR、Citation、拒答正确率和 P95。
- 只改一个变量做对照，例如 Dense/Sparse 权重。
- 跑一次备份/恢复，确认 PG、MinIO、Manifest 和 Milvus 重建关系。
- 跑短时 Soak 和可恢复 Chaos；真正上线前在内网完成长稳。
- 每天随机抽 5 个面试题，要求先讲结论、再讲项目证据、最后讲取舍。

## 6. 一次真实问题的调试清单

以问题“预计总费用 6000 元的国内差旅需要哪些人审批，返程后最迟多久提交报销？”为例：

1. 找 conversationId/runId。
2. 查看 Run Snapshot 是否锁定正确 user/roles/space/Manifest/Profile。
3. 查看 route=KNOWLEDGE、plan/subquestions/exact literals。
4. 查看 Query Embedding metadata 和 cache hit。
5. 查看 Dense/Sparse 各自 TopK 与 RRF。
6. 查看 source recheck 删除了哪些候选及原因。
7. 查看 diversify 后文档/章节分布。
8. 查看 Reranker 输入数量、输出全集和降级事实。
9. 查看 Evidence 是否包含审批规则和 10 个工作日。
10. 查看 route_evidence=ANSWER，不应把住宿 650 元误判为冲突。
11. 查看 Context 是否因预算截掉关键证据。
12. 查看 Draft Claim 引用是否只用白名单 ID。
13. 查看 Rule/Final Validation。
14. 打开 Citation，重新授权并核对原文定位。

这套顺序也适合面试现场白板排障。

## 7. 结业项目

独立完成下面任务，不参考答案：

1. 新增一个模拟内网 Reranker Adapter，协议字段与标准不同。
2. 写 Contract Test 覆盖正常、超时、取消、429、5xx、Schema、版本、部分结果。
3. 通过配置选择新 Adapter，不修改 Answer Graph。
4. 建 Golden 对比有/无 Reranker 的 MRR、正确率和 P95。
5. 设计 Canary 与回滚条件。
6. 写一页 ADR：为何选择 Adapter 而不是让业务代码适配。

能独立完成，说明你不仅会用项目，也能迁移方法到下一套 RAG。

## 8. 自测题

不看资料回答：

1. 为什么 PostgreSQL 和 BullMQ 都要保存任务相关信息？
2. Outbox 保证 Exactly Once 吗？如果不保证，系统如何正确？
3. Query/Document Embedding 模板为什么必须版本化？
4. 什么时候 Dense 比 Hybrid 更合适？
5. 为什么 Milvus Filter 不能作为最终权限判断？
6. 为什么 Reranker 不直接处理全库？
7. Evidence Bundle 与 Prompt Context 有何区别？
8. Validator 服务挂了时普通 FAQ 和法务回答应如何不同处理？
9. Embedding 维度变化为什么不能原地更新 Collection？
10. 如何判断答案差是检索问题还是生成问题？
11. SSE 事件丢失后为什么还能恢复？
12. 内网 Provider 字段不同，为什么不是“多改几个 env”就行？
13. 24 小时 Soak 重点观察什么？
14. 权限撤销后缓存、Milvus、Citation 各自怎样保证安全？
15. 讲一个本项目真实发现并修复的生产问题。
