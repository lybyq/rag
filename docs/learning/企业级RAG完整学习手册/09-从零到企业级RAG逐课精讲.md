# 09：从零到企业级 RAG 逐课精讲

> 这一章不是名词表，而是一门可以真正跟着学的课程。每一课都按“先讲人话 → 再讲正式概念 → 放进本项目 → 解释失败后果 → 动手验证 → 口头复述”的顺序进行。不要一口气读完；每完成一课，关掉文档，用自己的话讲一遍。

## 第 0 课：先把 RAG 想对

### 0.1 大白话

LLM 像一个表达能力很强、读过很多公共资料，但没有进入你公司的新员工。你问它公司 2026 年差旅标准，它可能：

- 根本没见过这份制度；
- 见过旧版本，记忆已经过期；
- 把常识说得很流利，让人误以为是真的；
- 即便知识库里有答案，也可能引用错条款。

RAG 做的事情不是“让模型突然记住公司全部文档”，而是在每次回答前完成一次受控的开卷考试：

1. 先确认提问人能看哪些资料；
2. 从当前有效版本中找出可能相关的段落；
3. 把少量证据交给模型；
4. 要求模型逐项说明答案依据；
5. 服务端检查证据、数字和引用，检查不过就拒答。

因此，企业 RAG 的主体并不是聊天框，也不是某个向量库，而是一套“知识生产 + 检索决策 + 证据生成 + 安全治理 + 评测运维”的系统。

### 0.2 RAG 和这些技术有什么区别

| 技术         | 擅长什么                   | 不擅长什么               | 在本项目的位置                          |
| ------------ | -------------------------- | ------------------------ | --------------------------------------- |
| LLM 参数知识 | 通用语言和推理             | 私有、最新、可审计事实   | 负责改写、生成和可选语义判断            |
| 全文搜索     | 原词、编号、短语           | 同义表达、语义概括       | Sparse 路召回                           |
| 向量检索     | 同义语义、自然语言         | 精确编号、事务、当前权限 | Dense 路召回                            |
| SQL/业务 API | 精确结构化事实             | 非结构化长文理解         | 实时价格、余额等应走 Tool，而非硬塞 RAG |
| Fine-tuning  | 行为、风格、特定能力       | 高频更新事实和逐条引用   | 不是知识库更新的首选                    |
| RAG          | 私有、可更新、有证据的知识 | 不能天然保证答案正确     | 本项目对检索到发布答案做全链路控制      |

### 0.3 第一条选型原则

先问事实在哪里，再决定用什么：

- 事实是“当前余额、库存、行情”：走受控 API/SQL Tool。
- 事实是“制度、手册、合同条款”：走 RAG。
- 目标是“固定语气、分类、抽取”：考虑 Prompt、规则或微调。
- 目标是“跨资料总结并可引用”：RAG + 结构化生成。

面试官很喜欢用这一题区分“会套框架”和“会做系统”的人。不是所有问题都应该向量化。

### 0.4 学完检查

你应该能不用术语解释：为什么“把整份 PDF 塞给大模型”不是企业 RAG；为什么“接了 Milvus”也不等于知识库已经可上线。

## 第 1 课：先从业务风险倒推架构

### 1.1 不从组件清单出发

错误做法是先说“我要用 NestJS、BullMQ、Milvus、LangGraph”。正确顺序是先列业务风险：

| 业务风险                | 系统必须给出的保证             | 本项目的设计                                        |
| ----------------------- | ------------------------------ | --------------------------------------------------- |
| 无权用户看到制度        | 权限默认拒绝，查询前后都校验   | Space ACL、服务端 Filter、PG 回源、Citation 再授权  |
| 新旧文档混用            | 每次回答可证明用了哪个版本     | Manifest、Run Snapshot、Provider Revision           |
| 上传成功但任务丢失      | 数据库提交后任务最终一定被处理 | PG Outbox + Scheduler + BullMQ                      |
| Worker 重启造成重复数据 | 重复消息只产生一次业务效果     | 稳定 ID、唯一约束、Receipt、Lease、幂等 Upsert      |
| 模型编造引用            | 引用必须来自服务端证据白名单   | Evidence sourceId + Validator + Citation API 再鉴权 |
| 模型服务卡死            | 请求有总期限并可取消           | Deadline、单次 timeout、AbortSignal                 |
| 换 Embedding 后结果混乱 | 新旧向量空间不能混写混查       | 不可变 Profile、新 Collection、评测、原子发布       |
| 内网不能访问公网        | 构建和运行都不依赖公网         | Provider Port、ENV Profile、images.tar              |

这张表就是架构推导。每增加一个组件，都要能指出它解决哪一项风险；说不出来，就可能是过度设计。

### 1.2 为什么分成离线链路和在线链路

离线链路做“知识生产”：

```text
文件 → 安全检查 → 解析/OCR → 结构恢复 → Chunk → 质量门禁
    → Embedding → 候选索引 → 对账 → Manifest 发布
```

在线链路做“答案生产”：

```text
身份/问题 → Run 快照 → 查询计划 → Dense/Sparse → RRF
         → PG 回源 → Rerank → Evidence → 生成 → 校验 → FinalAnswer
```

它们的资源模型不同：离线链路允许分钟级任务、重试和人工审核；在线链路关注秒级 P95、取消和流式体验。把二者绑在一次 HTTP 请求里，大文件会拖垮查询服务，失败也无法可靠恢复。

### 1.3 为什么有多个进程但不是“每张表一个微服务”

本项目拆成：

- `platform-api`：管理面、上传、审核、索引发布、运维接口；
- `rag-query-service`：延迟敏感的问答、检索、答案生成；
- `ingestion-worker`：CPU/IO/模型密集的离线任务；
- `scheduler-worker`：Outbox、租约恢复、索引维护、评测调度；
- `document-parser-service`：隔离不可信文件解析；
- `web-console`：管理端和问答端。

拆分依据是资源类型、SLA、扩容方式和故障域，而不是追求“微服务数量”。如果只有 20 人使用、每天 10 份文档，可以把后端进程合并，但仍保留模块边界；如果问答 QPS 很高，再独立扩容 Query Service。

### 1.4 学完检查

给自己一个新场景：“300 人客服系统，每日 5 万次问答、文档每周更新一次。”请说明哪个进程先扩容，哪些组件不能跟着无脑扩容，以及为什么。

## 第 2 课：契约不是 TypeScript 接口那么简单

### 2.1 大白话

契约就像插座标准。业务代码只认“220V 三孔插座”，不关心电来自火电、水电还是光伏。内网模型服务只要遵守插座标准，换 URL 和密钥即可；如果它输出另一种字段结构，就要加转换器，不能假装改 ENV 就兼容了。

### 2.2 本项目有五类契约

1. **HTTP API 契约**：前端和 Controller 之间的请求、响应、错误码。
2. **事件契约**：PG Outbox、BullMQ、SSE 中事件名、版本、幂等键和顺序。
3. **Provider 契约**：LLM、Embedding、Reranker、OCR、Parser 的 HTTP 形状。
4. **Port 契约**：Application 依赖数据库/模型/队列时只看能力接口。
5. **数据契约**：表约束、状态机、唯一键和 Manifest 不变量。

只写 TypeScript 类型不够，因为类型在运行时会被擦除。外部 JSON 仍可能缺字段、把数字写成字符串或返回未知枚举，所以边界使用 Zod 做运行时校验。

### 2.3 用 Embedding 契约理解“为什么元数据很重要”

假设文档用 1024 维模型 A 建了索引，查询端却悄悄切成 768 维模型 B：

- 最好情况：Milvus 直接报维度错误；
- 更坏情况：维度相同但向量空间不同，系统正常返回完全错误的结果；
- 最隐蔽情况：模型名相同，服务端实际 revision 已更新。

所以启动和调用时不能只看 HTTP 200，还要核对：

```text
modelId + revision + dimension + normalizeDense
+ tokenizerRevision + queryTemplateVersion + documentTemplateVersion
+ sparseFormatVersion
```

这些共同组成 Embedding Profile。变化时建立新 Profile 和新 Collection，而不是原地覆盖。

真实契约见 [Provider HTTP 契约](../../contracts/provider-http-contracts.md)。配置校验在 `libs/config/src/app-config.ts`，Embedding Adapter 在 `libs/model-gateway/src/http-embedding.adapter.ts`。

### 2.4 Deadline、Timeout、AbortSignal 的区别

- **Deadline**：这次用户 Run 最晚什么时候必须结束，例如总预算 120 秒。
- **单次 Timeout**：某次 Reranker 调用最多等待 15 秒。
- **AbortSignal**：用户取消、服务关闭或总期限到达时，把取消向下游传播。

如果只有单次 timeout，没有总 Deadline，三次重试加两个模型调用可能把总耗时拖到几分钟。如果只有 Deadline，没有 AbortSignal，用户关闭页面后昂贵的 GPU 调用还会继续跑。

### 2.5 错误也属于契约

远程错误至少要区分：

- `TIMEOUT`：可能重试，但必须受剩余 Deadline 限制；
- `RATE_LIMITED`：按 Retry-After/退避重试；
- `UPSTREAM_5XX`、`NETWORK`：有限重试或降级；
- `SCHEMA_INVALID`：协议不匹配，重试通常无意义；
- `REVISION_MISMATCH`：快照被破坏，应阻断；
- `AUTHENTICATION_FAILED`：配置/密钥错误，应告警而非无限重试；
- `CANCELLED`：立即停止，不能进入 DLQ 重试风暴。

### 2.6 学完检查

请回答：“内网 Reranker 返回 `{ results: [{ index, relevance_score }] }`，项目要求 `{ scores: [{ candidateId, score, rank }] }`，为什么不能只改环境变量？”正确答案需要说到 Adapter、Schema、candidateId 映射、排序稳定性、版本和契约测试。

## 第 3 课：PostgreSQL、Redis、BullMQ、MinIO、Milvus 各自是什么

### 3.1 用物流系统类比

- PostgreSQL 是公司订单总账：订单是否存在、处于什么状态，以它为准。
- MinIO 是仓库：保存原文件和派生文件，不负责订单状态。
- BullMQ 是传送带：通知工人下一件货是什么，不是永久总账。
- Redis Stream 是短期广播和续传通道：让前端及时看到进度。
- Cache Redis 是便签：丢失后可以重新计算，不能承载权限真相。
- Milvus 是按“语义相似”找货的高速索引：可重建，不负责事务和授权真相。

### 3.2 为什么本项目使用两个 Redis

本项目分别配置 `REDIS_CACHE_URL` 和 `REDIS_BULLMQ_URL`。这是故障隔离：

- Cache 被热点 Key 或淘汰策略打满，不应拖死任务队列；
- BullMQ 需要稳定的持久化和内存策略，不能像普通 Cache 那样随意淘汰；
- 两者监控重点不同：Cache 看命中率，队列看等待年龄、stalled、DLQ。

在资源很小的开发环境可以共用实例，但至少分 DB、Key 前缀并明确风险；生产中型规模更适合独立实例。

### 3.3 BullMQ 到底解决什么

BullMQ 解决的是 Node.js 进程间的异步调度：延迟任务、重试、并发 Worker、stalled 检测。它不自动解决：

- PG 事务和 Redis 写入的原子性；
- 重复消息；
- 外部 API 已成功但本地未记录；
- 业务状态是否合法；
- Worker 迟到结果覆盖新结果。

这些由 Outbox、Receipt、稳定 Job ID、领域状态机和 PG Lease 补齐。

### 3.4 一次任务为什么可能被执行两次

场景：Worker 完成 Embedding，刚写完 Milvus，但还没向 BullMQ ACK 就崩了。锁超时后，另一 Worker 会再次拿到这个 Job。传输层无法知道第一次副作用是否成功，所以至少一次系统必须假设重复可能发生。

正确处理不是追求神奇的 Exactly Once，而是让副作用幂等：

- 向量 ID 由 `manifestId:chunkId:embeddingProfileId` 稳定计算；
- Milvus 使用 Upsert 或先查事实；
- PG 唯一键拒绝重复引用；
- Receipt 表记录已消费事件；
- 状态机拒绝从终态退回处理中。

最终得到的是“消息可能来两次，业务效果只有一次”。

### 3.5 为什么还需要 PG Lease

BullMQ 锁只说明“现在这条 Redis Job 大概由哪个 Worker 处理”。PG Lease 说明“谁有资格修改这个业务任务”。当 Worker A 卡住、Lease 到期后 Worker B 接管，A 即使迟到返回，也因 `leaseOwner` 不匹配而不能覆盖 B 的结果。

这就是分布式系统常见的 fencing 思想：不是相信旧 Worker 会自觉停止，而是在事实源写入时验证它是否仍有资格。

### 3.6 学完检查

请画出“PG 提交了上传任务，但 Scheduler 还未发 BullMQ 就宕机”的恢复过程，并说明为什么数据不丢；再画“BullMQ 已发两次”的过程，说明为什么不会生成两套有效知识。

## 第 4 课：文档不是字符串，Parser 也不只是读文本

### 4.1 企业文件的真实复杂度

一份 `制度.docx` 可能包含：标题层级、页眉页脚、合并表格、图片、文本框、超链接、嵌入对象、修订痕迹。扫描 PDF 可能一页有两栏和表格。Excel 可能有公式、隐藏 Sheet、十万行数据。

如果 Parser 只返回一大段纯文本，后面会丢失：

- “这段属于哪个章节”；
- “这个数字对应哪一列表头”；
- “答案在第几页”；
- “图片 OCR 应替换哪个区域”；
- “引用如何回到原文件位置”。

因此本项目先统一成可定位的 Block，再由 Chunker 面向检索组织知识。Parser 与 Chunker 必须分开，因为前者追求忠实恢复，后者追求召回和上下文。

### 4.2 为什么不能所有 PDF 都 OCR

OCR 不是“更高级的解析”，而是针对图像文字的补救：

- 原生 PDF 文本通常更准确；
- OCR 会把 `0/O`、`1/l`、小数点、表格列弄错；
- 全量 OCR 增加 GPU 成本和延迟；
- 同一页重复使用 Parser 和 OCR 还可能产生重复文本。

所以项目按页或 target 检查文本覆盖率，只对低覆盖区域调用 OCR，并记录 confidence。低置信结果进入质量门禁或人工审核。

### 4.3 文件安全为什么在 Parser 前

不可信文件可能伪造扩展名、制造 ZIP 炸弹、超深压缩、巨型图片或超大表格。解析库本身也可能存在漏洞。项目在读取前限制字节、Magic Bytes、压缩层级/比例、页数、像素和单元格；解析服务独立进程，降低对主 API 的影响。

内网不代表文件可信。邮件附件、供应商文档和员工上传都可能带来风险。

### 4.4 学完检查

比较三类文档：原生制度 PDF、扫描合同、产品编码 Excel。分别说明 Parser/OCR、Chunk 和检索策略的重点。不能回答成“三种都切 500 Token 后向量化”。

## 第 5 课：Chunk 是一次信息架构设计

### 5.1 为什么固定 500 字不是方案

固定长度容易实现，但会在句子、条款、表格行中间截断。检索命中“每晚住宿上限 650 元”时，可能丢掉标题“上海地区”；命中表格数字时，可能没有列名“经理级”。

Chunk 要同时解决两个矛盾：

- 小块更容易精确召回；
- 大块保留更多上下文。

本项目使用 Parent/Child：Child 用于检索，Parent 在入选后按需扩展上下文。标题路径注入 Child，表格保留表头和行列关系。

### 5.2 参数怎么从数据中定

项目默认 Child 512 Token、Parent 1500 Token、Overlap 64，只是中型通用文档起点。正确调参过程：

1. 建立 50～200 个真实脱敏问题和标准证据；
2. 统计证据自然长度、标题深度、表格比例；
3. 尝试多组 Chunk Profile；
4. 比较 Recall@K、重复率、平均 Context Token、答案正确率；
5. 找到收益开始变缓的位置，而不是只追最大 Recall；
6. 按文档域保留不同 Profile，记录 revision。

如果 80% 答案是完整制度条款，Chunk 可以偏大；如果是错误码/产品号，块可以偏小并强化 Sparse；如果是长表格，应做表格语义序列化或结构化查询，而不是无限 overlap。

### 5.3 Overlap 的代价

Overlap 能保护边界，但会导致：向量数量增长、Embedding 成本增加、多个相邻 Chunk 霸榜、LLM 上下文重复。本项目后面还要做每文档/章节多样性限制，就是为了防止同一位置的相似块挤掉其他证据。

### 5.4 学完检查

请给“100 页员工手册”和“200 万行商品编码表”分别设计 Chunk。第二个场景的好答案应质疑是否应该把每行都当自然语言 Chunk，并考虑 SQL/搜索引擎。

## 第 6 课：Embedding 与索引发布不是一个 API 调用

### 6.1 Embedding 是什么

Embedding 把文本映射到向量空间。相近含义在空间中距离更近。它不是摘要，也不保存可读知识；向量只能在同一个模型、revision、模板和归一化规则下比较。

### 6.2 为什么文档模板和查询模板分开

一些模型要求文档和查询使用不同前缀，例如“为检索表示这个段落”和“为搜索表示这个问题”。如果文档端换了模板，旧向量空间就变化；模板版本必须和模型一起进入 Profile。

### 6.3 为什么不能边写 Milvus 边让用户查询

假设一个知识空间应有 10 万条向量，Worker 写到 4 万条时服务重启。如果用户已经看见这个半成品索引，回答质量会随机下降。

本项目采用候选构建与原子发布：

1. 创建 Candidate Manifest；
2. 把所有目标文档成员和 Profile 冻结；
3. 批量 Embedding、写向量；
4. 对账 expected count、actual count、主键、Hash、Profile；
5. Golden 评测和可选 Canary；
6. 原子切换 `space_manifest_heads.active_manifest_id`；
7. 保留旧 Manifest 以便回滚，延迟清理。

用户要么看到完整旧版本，要么看到完整新版本，不会看到中间状态。

### 6.4 Milvus 为什么不是事实源

Milvus 中的 metadata 是发布时投影，可能滞后；删除或权限撤销也可能有短暂残留。PG 保存当前文档状态、空间授权、Manifest Head 和审计。Milvus 返回候选后必须回 PG 复核。

### 6.5 学完检查

请完整回答：“将 Embedding 从 1024 维 BGE 换成 768 维模型时如何无损上线？”必须包含新 Profile、新 Collection、全量构建、对账、评测、Canary、原子 Promote、回滚和延迟清理。

## 第 7 课：Dense、Sparse、RRF 和 Reranker 各做什么

### 7.1 一道示例题

用户问：“制度 FIN-2026-017 里住宿 650 元适用于谁？”

- Dense 容易理解“住宿标准”和“适用对象”的语义；
- Sparse 擅长锁定精确编号 `FIN-2026-017` 和数字 `650`；
- RRF 把两路不同量纲的排名合并；
- PG 回源剔除无权、旧版本或已撤销文档；
- 多样性限制避免同一章节的相邻块占满 TopK；
- Reranker 对问题与候选全文做更精细的相关性排序。

这些不是重复劳动，而是从“便宜、宽召回”逐渐走向“昂贵、精排序”。

### 7.2 手算 Weighted RRF

假设 `k=60`、Dense 权重 0.65、Sparse 权重 0.35：

```text
候选 A：Dense 第 1，Sparse 第 5
score(A) = 0.65/(60+1) + 0.35/(60+5)
         ≈ 0.01066 + 0.00538 = 0.01604

候选 B：Dense 第 3，Sparse 第 1
score(B) = 0.65/(60+3) + 0.35/(60+1)
         ≈ 0.01032 + 0.00574 = 0.01606
```

B 略高，因为两路都靠前，并且精确词路排名第一。RRF 使用名次而不是直接相加相似度，避免 Dense 的 0.82 和 Sparse 的 12.6 这种不可比分数。

### 7.3 为什么不直接让 Reranker 搜全库

Cross-Encoder/Reranker 需要同时读取 query 和每个 document，计算成本远高于向量/倒排搜索。它适合处理几十个候选，不适合扫描百万 Chunk。典型结构是召回 40～100 个，再 Rerank 到 8～15 个。

### 7.4 TopK 怎么判断

- 看 Recall@K 曲线：K 从 20 到 40 提升很多，就不能停在 20；从 80 到 120 只提升 0.2%，收益可能不值延迟。
- 看候选重复度：K 很大但都是同一文档相邻块，不是真正增加信息。
- 看 Reranker 最大候选和 GPU 吞吐。
- 看最终 Context Token 预算，Final TopK 不是越大越好。

本项目 initial 40、final 12、RRF k=60、Dense/Sparse 权重 0.65/0.35，是可测试基线，不是假装“万能最佳参数”。

### 7.5 学完检查

解释这三个场景应怎样调权重：制度自然语言问答、产品编码查询、中文同义表达客服库。答案必须提出用 Golden 验证，而不是只凭感觉填 0.8/0.2。

## 第 8 课：LangGraph 解决的是受控分支，不是为了显得高级

### 8.1 什么时候普通 Pipeline 更好

如果链路永远是 A→B→C，没有分支、循环、人工节点和状态审计，普通函数组合最简单。LangGraph 不是企业级认证章。

### 8.2 本项目为什么使用图

检索存在：是否改写、证据是否够、是否第二轮检索；答案存在：是否 LLM 证据重排、是否语义 Judge、是否再生成、是否拒答。图把有限状态、分支上限和逐节点观测显式化。

本项目刻意不用开放式无限 Agent：

- 检索最多两轮；
- 生成最多一次修复，即最多两份 Draft；
- 权限和 Filter 由规则决定，LLM 不能扩大；
- 每个节点继承 Deadline 和 AbortSignal；
- 节点审计只写计数/Hash，不写敏感正文。

这使成本、行为和故障边界可预测。

### 8.3 两层图

检索子图：

```text
route_query → build_plan → [rewrite_query] → query_embedding
→ hybrid_retrieve → source_recheck → assess_retrieval
→ [retry_plan → query_embedding] → diversify
```

答案图：

```text
retrieve → rerank → expand_evidence → build_evidence → route_evidence
→ [llm_evidence_rerank] → build_context → generate_draft
→ revalidate_citations → rule_validation → [semantic_judge]
→ final_validation → [一次修复生成] → finalize
```

完整代码导读见 [10-真实代码与数据全链路导读](./10-真实代码与数据全链路导读.md)。

### 8.4 学完检查

请说明为什么“LLM 判断用户能看哪些 Space”是错误设计；为什么“模型觉得证据不足就无限搜索”也不适合受控企业系统。

## 第 9 课：Evidence 和 Citation 才是从检索到可信回答的桥

### 9.1 候选段落不等于证据

检索候选只有“可能相关”。Evidence 还要具备：来源身份、Manifest、文档版本、定位、权限、权威等级、Hash、与哪个子问题相关。生成模型只能引用服务端颁发的 sourceId。

### 9.2 为什么生成后还要再校验权限

Run 创建到生成完成之间，管理员可能撤销权限或废止文档。只在检索前检查会有 TOCTOU 时间差。本项目在 Evidence 扩展和 Citation 发布前再次检查当前权限；失效引用会阻断普通成功答案。

### 9.3 如何降低幻觉

“Prompt 写一句只根据资料回答”远远不够。完整防线是：

1. 检索 Recall 足够，否则模型根本拿不到真证据；
2. 证据经过权限、版本和状态检查；
3. Context 按 Token 和文档多样性装箱；
4. 模型输出结构化 Claim 和 Citation；
5. Citation 必须属于白名单；
6. 金额、日期、比例等做确定性检查；
7. 规则无法判断的语义 Claim 才交给 Judge；
8. 不足、冲突或校验失败时拒答/澄清；
9. Golden 集持续验证回归。

### 9.4 为什么严格模式不直接流出 LLM Token

如果 Token 已经显示给用户，后面 Validator 发现它越权或数字错误也无法收回。因此严格场景只流式发送阶段状态，正文通过校验后一次性发布。低风险客服场景可选择流式草稿，但必须明确“未验证”并接受风险。

### 9.5 学完检查

回答：“已经有 Reranker，为什么还需要 Evidence Builder 和 Validator？”需要讲清相关性、事实支持、权限和引用是四个不同问题。

## 第 10 课：评测决定你是在调系统还是碰运气

### 10.1 分层评测

| 层         | 指标示例                                     | 回答的问题         |
| ---------- | -------------------------------------------- | ------------------ |
| Parser/OCR | 结构恢复、字符错误率、表格完整率             | 文档有没有读对     |
| Chunk      | 标准证据覆盖、重复率、平均 Token             | 知识有没有组织好   |
| Retrieval  | Recall@K、MRR、NDCG、权限泄漏率              | 真证据有没有找回来 |
| Rerank     | TopN Recall、排序增益、P95                   | 精排是否值得成本   |
| Answer     | Faithfulness、Citation Precision、拒答准确率 | 回答是否被证据支持 |
| Production | P95/P99、错误率、队列年龄、成本              | 系统是否稳定可运营 |

答案错误时不要立刻换 LLM。先定位：标准证据是否被解析 → 是否形成正确 Chunk → 是否进入 Active Manifest → 是否在 Initial TopK → 是否被 Reranker 排掉 → 是否被 Context 裁剪 → 模型是否错误总结 → Validator 是否漏检。

### 10.2 为什么公开榜单不够

公开榜单不能代表你的制度编号、中文简称、扫描表格、权限和无答案问题。企业选型必须用脱敏 Golden；公开榜单只适合缩小候选范围。

### 10.3 如何避免把“目标值”说成“生产成绩”

本项目配置和测试中的 Recall、P95、并发值是验收目标或基线，不等于真实生产数据。面试时要诚实区分：

- “我们代码里设的门禁是……”；
- “本地合成集测得……”；
- “进入真实内网后还要用业务 Golden/压测确认……”；
- 不要编造“线上日均千万 QPS”。

这种边界感反而更像真正做过工程的人。

### 10.4 学完检查

给你一个现象：“答案准确率下降 15%，但 Recall@40 没变。”请列出至少五个下一步排查点，不能第一句就说换更大模型。

## 第 11 课：如何判断当前架构需要演进

### 11.1 四个决策维度

任何 RAG 选型先写四张表：

1. **数据**：数量、增量、格式、扫描/表格比例、更新时效。
2. **查询**：QPS、问题类型、多跳、精确词比例、上下文长度。
3. **风险**：权限粒度、答错损失、审计、保留和合规。
4. **资源**：团队能力、已有中间件、GPU、离线限制、预算和 SLA。

### 11.2 几个演进信号

- pgvector 查询 P95 已超目标且向量持续增长：考虑独立向量库，而不是因为“Milvus 更企业级”。
- 80% 问题是编号/短语：增加全文/倒排，不要只升级 Embedding。
- 表格事实错误多：优化 Parser、表格结构化或 SQL Tool，不要只调 Prompt。
- 用户频繁追问“上一条里的它”：加强会话实体和摘要，不一定增加 TopK。
- 权限变更频繁：缩短授权缓存、加强版本键和回源，不能把所有 ACL 复制到向量库后不管。
- 模型调用成为成本瓶颈：先做路由、缓存、裁剪和小模型分级，再考虑砍掉校验。
- 文档近实时更新：缩短发布链路或引入增量索引，但仍保留可见性原子边界。

更完整的决策树见 [11-架构选型与换场景决策手册](./11-架构选型与换场景决策手册.md)。

## 第 12 课：你怎样才算真的学会

“看懂”不等于“会做”。达到下面四级才算掌握：

### Level 1：能讲名词

知道 Chunk、Embedding、Rerank、Outbox 是什么。这只能通过基础面试。

### Level 2：能沿项目讲链路

能从 Controller 讲到 Application、Port、Adapter、表和事件；能指出每个保护代码删除后的故障。

给出一次漏召回、越权、队列积压或模型超时，能用指标/Trace/表状态定位到层，而不是乱改参数。

### Level 4：能换场景重新设计

面对银行制度、制造维修、客服 FAQ、代码库、实时行情或百万行表格，能根据数据、风险、SLA 和资源重新选 Parser、索引、检索、校验与部署方式，并说明原项目哪些复用、哪些删除、哪些替换。
