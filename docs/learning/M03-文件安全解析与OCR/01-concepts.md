# 01｜先理解 M03 解决的不是“抽文字”，而是建立可信内容边界

## 1. 为什么上传成功还不能进入 RAG

M02 的 `HEAD` 只能证明对象存在、大小和上传计划基本一致，不能证明它真是 PDF、没有恶意载荷、没有压缩炸弹，也不能证明抽取顺序和页码可靠。M03 把不可信字节转换成下游唯一可消费的 `DocumentBlock`；在这条边界之前，文件始终位于 quarantine Bucket。

必须记住四个不同问题：

1. **真实性**：扩展名、声明 MIME 和内容魔数是否一致，流式重算的 SHA 是否等于上传事实。
2. **安全性**：内置危险签名/可执行魔数、宏、密码、嵌入对象、外链和资源规模是否允许；内置规则不等价于完整病毒库。
3. **可解析性**：Provider 能否稳定返回版本化、经过 Zod 校验的结构。
4. **可检索性**：内容是否已经变成带页/Sheet/Slide/bbox 的统一 Block。Chunk 是 M04 的职责。

## 2. 为什么要按页 OCR

一本 200 页 PDF 可能只有第 73 页是扫描件。整本 OCR 会带来三类问题：成本和延迟暴涨；可靠文字层被 OCR 错字覆盖；引用坐标更不稳定。因此 Parser 返回 `pages + ocrCandidates`，平台构造 PAGE/REGION/EMBEDDED_IMAGE/WHOLE_IMAGE 目标。只有 PAGE 会替换低可靠原生页，其余目标只补充缺失区域。

## 3. 原文和标准化文本为什么要同时保留

`originalText` 是取证与回归比较的基线，`text` 是统一换行和空白后的检索友好版本。若标准化直接覆盖原文，将无法解释“答案里的文字为什么与文件不同”，也无法在升级 Parser 后进行差异分析。

## 4. 三类失败是资源治理，不只是错误码

- `RETRYABLE_PROVIDER`：临时网络、429、5xx、超时，有限重试。
- `DOCUMENT_PROBLEM`：格式伪装、恶意、密码、超限，是确定性输入问题，继续重试只会浪费资源。
- `DEVELOPER_DEFECT`：Schema/协议/修订漂移，必须修代码或配置，不能把错误响应当正文。

面试追问时可以这样概括：**失败分类把“是否重试”从字符串猜测变成稳定业务决策，同时防止坏文档和坏 Adapter 制造重试风暴。**
