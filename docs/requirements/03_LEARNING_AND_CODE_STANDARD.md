# 教学型代码与学习交付标准

## 1. 目标

这个项目不仅要能上线，还要让学习者能够从零解释：为什么这样设计、请求如何流动、失败时发生什么、如何验证正确性，以及替代方案的取舍。学习交付与功能代码具有同等完成地位。

## 2. “详细解释代码”的落地方式

将注释分为三层，既满足逐步学习，也避免生产源码被重复语法注释淹没。

### 第一层：源码 JSDoc

每个源文件和导出符号必须说明：

- 它解决什么问题；
- 位于哪条业务链路；
- 输入、输出、不变量和副作用；
- 错误、幂等、权限、超时和事务语义；
- 为什么放在这一层；
- 对应需求编号。

示例：

```ts
/**
 * 将用户请求的知识空间与服务端授权空间取交集。
 *
 * 这里不能直接采用客户端的 requestedSpaceIds，因为客户端输入不可信；
 * 它只能缩小权限，不能扩大 AuthPort 已确认的范围。
 *
 * @requirement AUTH-011
 * @throws PermissionDeniedError 当交集为空且请求要求知识检索时抛出
 */
export function restrictRequestedSpaces(
  allowedSpaceIds: readonly string[],
  requestedSpaceIds?: readonly string[],
): string[] {
  // 未指定时使用全部已授权空间；这不是“无过滤”，后续仍会编译为显式过滤条件。
  if (!requestedSpaceIds) return [...allowedSpaceIds];

  // 使用 Set 避免嵌套循环，并确保只保留服务端已经确认的空间。
  const allowed = new Set(allowedSpaceIds);
  return requestedSpaceIds.filter((spaceId) => allowed.has(spaceId));
}
```

### 第二层：关键逻辑行内注释

必须详细注释：

- 领域状态转换和不变量；
- 事务边界、Outbox、Lease、幂等和补偿；
- 权限交集、FilterCompiler 和二次鉴权；
- Chunk、RRF、Token Budget、Coverage 和 Validator 算法；
- SSE 顺序、续传、持久化先后和取消传播；
- 缓存 Key 为什么包含某个版本；
- 降级、重试与“为什么不能重试”的分支。

简单 import、括号、类型可直接看懂的赋值不写“翻译式”注释。

### 第三层：逐行级 Code Walkthrough

每个模块提供 `docs/learning/Mxx/code-walkthrough.md`，按真实执行顺序引用文件和代码区段，逐句解释：

1. 请求从哪里进入；
2. 每个关键变量如何产生；
3. 每个分支为什么存在；
4. 数据在哪个事务中写入；
5. 异常如何分类与传播；
6. 指标和 Trace 在哪里记录；
7. 测试如何证明它正确；
8. 删除某段保护代码会造成什么问题。

Walkthrough 负责“行行学”，源码注释负责“长期维护”。二者都要交付。

## 5. 单个需求的教学实施节奏

实现每条需求时按以下顺序协作：

1. 先用通俗语言解释该需求解决的生产问题。
2. 画出最小数据流或状态变化。
3. 明确要新增/修改的契约和测试。
4. 先写一个能失败的测试，并解释失败说明什么。
5. 小步实现代码，讲解关键行和边界。
6. 运行测试并解释结果，不只报告“通过”。
7. 展示一条正常请求和至少一条失败请求。
8. 总结替代方案、当前取舍和生产风险。
9. 给出 3～8 个面试追问，让学习者先作答再校正。
10. 更新需求勾选和模块验收证据。

## 6. 测试的教学要求

测试名称必须表达业务规则，而不是只写函数名：

```ts
describe('[AUTH-011] requested space restriction', () => {
  it('客户端请求包含无权空间时只能得到已授权交集', () => {});
  it('未指定空间时仍返回显式授权集合而非无过滤条件', () => {});
});
```

每类测试要解释其价值：

- Unit：证明领域规则与算法边界；
- Contract：证明内外网 Provider 可以替换；
- Integration：证明数据库、Redis、MinIO、Milvus 的真实行为；
- Golden：证明文档和问题质量没有退化；
- E2E：证明用户完整流程；
- Load/Soak/Chaos：证明容量和故障恢复，而非业务功能。

## 7. 面试训练输出标准

每个问题不能只背定义，回答至少包含：

1. 业务场景；
2. 常见错误方案；
3. 当前系统的具体实现；
4. 数据一致性或安全保证；
5. 如何测试和观测；
6. 规模变化后的演进方式。

例如“为什么使用 Outbox”应能够讲清：数据库事务与队列不具备天然原子性、失败窗口、重复投递、消费者幂等、`SKIP LOCKED` 并发领取、积压指标和 DLQ 处理，而不只是回答“保证最终一致性”。
