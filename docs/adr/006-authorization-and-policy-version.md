# ADR-006：空间 ACL、语义角色与授权版本

- 状态：Accepted
- 日期：2026-08-16
- 关联需求：AUTH-006～AUTH-015

## 背景

内网只提供 `userId + roles`，但角色名由企业身份系统决定。若把“拥有某个角色”直接解释为“能访问所有知识空间”，一次错误映射就会造成横向权限泄漏。ACL 变化后，旧缓存也不能继续放行。

## 决策

1. 内网角色先通过配置映射为六种系统语义角色；未知角色不赋权。
2. 除 `SYSTEM_ADMIN` 外，语义角色不自动获得所有空间权限，而是作为 `ROLE` 主体参与每个空间的 ACL 匹配。
3. ACL 原子权限为 READ、WRITE、REVIEW、ADMIN；高权限蕴含完成工作所需的低权限。
4. 新建空间时创建者获得 USER/ADMIN 授权。空间只停用，不在业务 API 物理删除。
5. 任意授权改变都会递增空间策略版本和全局 `authzVersion`，同时主动清除本进程授权缓存。缓存 Key 包含 userId、排序后的角色 Hash 与 authzVersion。
6. 客户端请求空间集合只与服务端可见集合取交集；资源、引用、历史、候选和导出都通过资源到空间的反查重新鉴权。
7. 管理、授权、撤权和拒绝访问写审计日志；Token、Header 签名和共享密钥不进入审计载荷。

## 结果

这套模型牺牲了少量全局角色的便利，换来默认拒绝、可解释的最小权限和可靠撤权。全局授权版本会让一次 ACL 变更使所有用户的本地授权缓存失效；在中型规模（空间不超过 200）下代价可接受，后续可按用户/角色版本分片优化。
